# 第二篇结构重做 v10：让 AI 帮助形成方法，也让方法能够持续使用

日期：2026-10-07。状态：根据用户明确要求合并 Claude Code 与 Anthropic，将人机协同研究放第五项；其余展开待审阅；不是正文定稿。三部分文章目标保留，七维度清单从拟稿结构中撤回。正文 v6 为待替换历史稿。

## 本篇到底要回答什么

目标、成果、标准或方法尚未清楚时，怎样借 AI 的知识和实际反馈逐步形成做法；已经有方案时，怎样评价并改善；怎样把一次有效的合作保存成能继续使用的工作流。

最终让读者理解三个层次：借用已有方法；通过对话和尝试把方法用于自己的问题；将有效决定、步骤和检查安排留下来，下一轮按当前状态继续。

## 为什么 v6 不成立

1. OpenAI 的文件、上下文、阶段推进和技能实践被概括成“目标、阶段、证据”，关键操作及其作用消失了。为了避免与第三篇重复，推迟了理解本篇所必需的内容。第二篇应该讲怎么安排合作及为什么这样安排，第三篇再讲文件、仓库的具体管理。
2. 七维度混合背景、要决定的内容和验证动作，互相依赖；它也无法说明“不清楚”的原因。v6 重新放表，相当于让新手先填需求表。撤下正文清单，不换一张重新编号的表。
3. 第三部分只再次概括循环，没让读者看到自己的工作流怎样形成、如何启动、得到什么、怎样判断继续、怎样留下来。
4. 文风在两端摇摆：抽象词太多，关键过程太少；又用大量“这套实践……”“可以……”和提醒把解释打断。修订应围绕具体问题展开因果，提炼放在过程之后。

## 候选标题

- 想法还没想清楚，怎样和 AI 一起把工作做起来？
- 和 AI 一起工作：从模糊想法到自己的工作流

## 导语：一个模糊请求为什么也能成为起点

旅游网站是用户初步想到的成果，真实需要可能只是旅行准备更省事。也有人知道效果不会做，有人已有方案仍希望改善。用一个短场景引出：工作方法与需求可以在合作中形成。文章接下来先借鉴已有做法，再看怎样实际协作，最后留下自己的流程。

不要求读者先知道所有答案；不从填写表格开始；不再次介绍第一篇的功能地图。

## 一、别人怎样把 AI 协作组织起来

五种方法仍放在导语后。每项讲一个真正值得借用的机制，再展开操作、例子和限制，不只介绍出处和名称。

### 1. 双钻：问题本身也需要研究

旅行准备费劲 → 查看实际资料与操作 → 比较困难的来源 → 定义值得处理的问题 → 比较解法 → 用一次小尝试检验。

重点：需求可以在调查和试验中形成；“做网站”可能只是初始解法。写清试验发现什么会让人改变方向，不把四阶段当四个名词。

### 2. Anthropic 与 Claude Code：从理解任务到执行、检查和持续推进

将 Claude Code 官方最佳实践作为主线，Anthropic 工程文章解释相关机制，不再分成两个平级章节。产品使用建议与工程原理分别注明来源，但在同一段工作过程中解释。

这一节按问题推进：

- 需求不完整，先让 AI 读取材料、解释专业选项并主动访谈，形成可用规格。用户不知道专业答案时，由 AI 给例子、推荐及理由，不能只把难题反问回来。
- 方法不确定或改动复杂，先探索与规划再实现；小而明确的任务可以直接处理。预算示例将输入、使用行为与检查连接起来。
- 为执行提供可读的反馈：测试、构建结果、预期输出或截图。AI 实现、运行、读取结果再修正，报告证据；固定流程与动态诊断按实际任务选择。
- 将长期约定放在精简的 CLAUDE.md，特定知识与重复工作放入技能；必须执行的程序检查可以由钩子落实。说明为什么文字规则和实际执行机制作用不同，不展开配置教程。
- 长任务中的无关材料、失败尝试和过时决定会干扰推进。保留关键发现与状态，按需要整理上下文；使用独立上下文调查或检查，强调审查也须判断证据与实际影响。
- 从反馈中调整工作方式：探索时允许开放请求，执行时逐步具体；及时纠偏，不把完整流程强加给每次小任务。

重点：专业经验可以由 AI 帮助补足，任务要有实际反馈，长期执行还需要合适的信息与工具安排。这一节不列 Claude Code 命令大全，也不将其命令当成 Codex 操作。

### 3. OpenAI：让下一轮能读懂这一轮

这一节实质性重写，讲清官方示例怎样落地。准确名称为 AGENTS.md、PLANS.md，而不是将文件名写成界面模式。

按实际工作顺序展开：

- 将跨阶段有效的规则写入 AGENTS.md，例如先理解用途再改动、如何验证、不能改动的范围。它是 Codex 识别的可选指导文件，不代表启动多个智能体。
- 将路线和阶段顺序写入 PLANS.md；目标、完成条件和启动请求在示例中另有 GOALS.md、PROMPTS.md。说明这些是可选项目约定，GOALS.md 不等于 /goal，PLANS.md 不等于 /plan。
- 给当前阶段一个具体任务：目的、需要读取的材料、范围和检查办法；先做什么由当前计划决定。关键选择和阶段结果可以由用户审阅，不要求每个小动作都停下来。
- 阶段上下文保留影响以后工作的决定、发现及理由；例如“这轮只做单人编辑，因为当前首先验证行程调整，多人编辑另行评估”。不把全部聊天复制进去，也不预先虚构后续阶段的发现。
- build-log.md 记录实际进度与验证证据；区分“准备检查保存”与“刷新后确实读到新记录”。以后继续工作时先读取相关规则、计划、上下文与记录。
- 反复做的启动、交接与记录动作可以做成技能。官方示例中新技能漏了计划与进度记录，作者修正范围后才得到合适产物：技能本身同样需要审阅与调整。
- 项目完成后，根据真实返工与检查复盘：哪些步骤必要、哪些信息缺失、哪些记录重复。更新方法再用于下次。

旅游网站贯穿以上做法，另以公众号写作说明规则、计划、决定和检查在其他工作中也有对应内容。具体目录创建、GitHub 管理放下一篇，但本篇不能略去文件职责与读取更新过程。

### 4. Superpowers：把专业工作方法变成可复用技能

介绍实际构思与实施计划技能：设计回答要做什么及为什么，实施计划回答怎样分任务、检查；任务规模决定流程深度。明确社区方法不是 Codex 默认工作流，未实测不宣称效果。

与 OpenAI 的衔接：一个例子强调长期状态如何保存，一个例子强调专业步骤怎样组织。技能可以复用，但不能代替当前问题的判断。

### 5. 人机协同研究：不同工作怎样分工，同一工作怎样切换

前四项说明工作怎样组织，第五项讨论人在其中怎样参与，并自然引出第二部分的实际协作。

保留用户指定的 Centaurs、Cyborgs、Self-Automators 表及解释。不同工作和同一工作的不同阶段可以切换；共创适合一起形成认识，明确任务可分工，稳定常规工作可更多委托。参与少不等于可以省略必要检查。

宝洁与元分析用于说明知识补充及效果需要检验，研究阅读边界放研究记录或简短来源说明，不让多段免责打断主要解释。

五项比较放在本节之后，概括各自贡献：认识问题、组织执行、维持长期状态、复用专业方法、选择人的参与方式。它们是文章的五组参考，不能写成五个必须连续执行的阶段。

## 二、还没想清楚时，怎样和 AI 把事情想清楚

这一部分讲合作如何发生；不再给七维度表，不要求读者把未知准确归类。以下是文章片段的安排，不是对用户的完整分类。

### 1. 从能提供的东西开始，让 AI 推荐下一步

展开陌生领域、现有资料或模糊困难怎样成为输入。请求示例：

> 准备旅行时，这些攻略、聊天和表格需要来回整理。我不知道应该改工具还是改流程。先看材料，解释问题可能出在哪，给几种做法并推荐下一步；缺少的事实请指出，不要先假定一定要做网站。

AI 应基于材料提出理解和候选原因，解释行业常见做法，区别有依据与推测；不能将全部专业选择反问用户。若资料不足，提出一次可执行调查或样例，而不是交付一大份泛泛介绍。

补充同一句要求可以有不同解释：费用汇总与价格预测，用输入输出复述发现分歧。

### 2. 把“不知道什么才好”变成可以比较的判断

用户可以要求 AI 推荐标准并说明原因。以预算修改为例，比较表格与网站的使用过程、投入和限制；拿一份真实行程试用，观察重复整理有没有减少。

已有方案时，明确固定要求和可讨论部分，以现有方案为基线。AI 提供收益、代价和依据，保留原方案也是合理结果。

关键未知先查：多人共同编辑会影响保存和权限；字体可暂定。要求冲突时用具体影响帮助选择，不让用户先填“取舍标准”。

### 3. 将值得尝试的方向变成这一轮任务

计划模式用于读取项目、比较并形成方案。计划要写清这轮交付、需要材料、检查办法与尚未确定的事项。先完成可判断的小尝试，不强制把全部未知消除。

目标模式用于已形成可检验终点的持续任务；普通请求适合短任务。明确方法选择和结果判断怎样由双方分担，避免“帮我全做完”含糊目标。

### 4. 用真实结果纠正理解，决定往哪里改

用户说不清原因时，提供实际操作、截图、录制、样例对照和感受。AI 先诊断是实现、流程还是目标出了问题，再选动作。

包括两种不能混同的情况：功能没符合约定；功能符合约定但没有解决困难。前者修复和重测，后者回到问题或方案。研究与写作可用“事实正确但回答了错误问题”作短迁移例子。

新的信息可以引导当前任务，后续想法可以排队；只短引用第一篇，不重讲界面。

## 三、怎样形成自己的工作流，并让它越用越合适

前一部分讲对话怎样推进，这部分将它安排为可以启动、审阅、接续、改进的实际流程。必须回答读者能照着做什么及会留下什么。

### 一个可直接用于旅游网站的流程

| 环节 | 双方实际做什么 | 留下什么以及怎样继续 |
| --- | --- | --- |
| 看现状、提出方向 | 用户给资料或操作过程，AI 调查、解释并比较做法 | 初步问题、推荐与待验证假设；不熟悉领域时先补认识 |
| 用一次尝试选择办法 | AI 推荐判断依据和小试验，用户比较结果与用途 | 当前方案和选择理由；已有清晰方案可直接评估后进入执行 |
| 安排当前阶段 | AI 据现状形成计划，双方确认关键行为与检查 | 本轮范围、材料入口及完成条件；必要时 /plan |
| 实现并检查 | AI 操作工具、获取结果并修正，人试用关键体验 | 可用产物、实际证据、未完成项；持续任务可用 /goal |
| 留下决定、准备接续 | AI 更新相关规则、计划、决定与进度，人审阅重要变化 | 下轮从哪继续及应读什么；偏差决定回到实现、方案还是问题 |
| 复盘并复用 | 对照耗时、返工和效果，改进步骤，重复动作再做成技能 | 适合这类工作的版本化方法；无效步骤删掉 |

这是本文的综合应用示例，不叫统一官方标准，也不是要求每项任务都从第一行开始。

### 给读者一段启动自己工作流的请求

> 请根据当前材料和我的目的，推荐适合这项工作的协作流程。说明先做什么、这一轮会得到什么、怎样判断继续，以及哪些事情需要我参与。已有依据的部分直接利用，缺专业知识由你解释，缺事实则提出调查或试验。确定后，再帮我整理成可以执行和继续使用的计划。

正文要紧跟一份实际回应样例及用户怎样修订，不能只交付万能提示词。

### 从一次有效合作到长期使用

以最少必要记录起步，不要求新手一次创建全套官方示例目录。将长期规则、当前计划和实际进度区别保存，重要决定写清理由；后续任务增多再拆阶段文件。重复操作才考虑技能，不把第一次不成熟做法立即固化。

用于公众号写作时，调研、大纲、纯文字审阅、排版和归档有自己的顺序及标准；用于研究或经营则替换相应专业环节。通用的是认识、选择、执行、检查和修订的关系，具体流程根据任务形成。

最终落点：用户不需要在开始前拥有完整流程，可以请 AI 帮助形成；一套流程是否值得留下，要由实际结果证明。第三篇继续讲怎样管理这些材料、记录和项目文件。

## 文风与验收

段落从问题或动作开始，解释为什么这样做、结果怎样影响下一步。抽象概括紧跟例子，不以“目标、阶段、证据”“明确边界”等词组代替过程。

避免机械地让每项方法使用相同段落模版，也减少每段的“可以”“需要”。英文名称保留必要对应，中文解释放前。来源阅读限制归档，不在每个段落重复。

核对三个问题：读者能否说出每项方法值得借用的具体做法；能否在不知道专业答案时启动合作；能否按旅游案例形成并接续自己的工作流。
