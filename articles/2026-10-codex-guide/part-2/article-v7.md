# 想法还没想清楚，怎样和 AI 一起把工作做起来？

和 Codex 一起工作 · 第二篇

“帮我做一个旅游日程安排网站。”

这句话看起来已经有了明确需求：要做一个网站，用来安排旅行。但真正开始做，还会遇到一连串选择。行程怎样编辑？费用怎样计算？是否需要同行者一起修改？怎样保存？第一版要做到哪里？

更早的问题甚至是：旅行准备哪里最费劲，做网站能不能改善它？

这些问题，新手未必答得出来。进入一个陌生领域，连应该考虑什么都不知道，很难一开始就写出完整需求。已有经验的人也会遇到类似困难：方案已经有了，但不知道是否有更好的方法；结果已经做出来，却说不清为什么不满意。

**与 AI 合作，可以从这些不确定的地方开始。**它可以帮助解释领域知识、分析现有材料、提出做法，也可以执行、检查和修正。问题在于，怎样把这些能力组织起来，让讨论逐步形成判断，让判断能够进入行动，让行动又带回新的认识。

第一篇介绍了 Codex 的工作方式。这一篇继续讨论：已有方法怎样安排协作，需求不完整时怎样提问，以及怎样逐渐形成自己的工作流。

## 一、已有的方法，怎样组织 AI 协作

“先调研，再计划，最后执行”是一个起点，但还不够。什么时候应该多了解一点？什么时候可以动手？结果不对，应该修实现还是改方案？工作跨了几天，怎样继续？

下面五组方法与实践，分别提供了有用的回答。它们关注的方面不同，可以结合当前任务选择。

### 1. 双钻模型：问题与解法，都需要探索

准备旅行时，要在攻略、地图、聊天记录和表格之间来回切换，很容易想到“做一个网站，把所有内容放进去”。但工具分散只是一个现象，最影响使用的困难还没找出来。

英国设计委员会的双钻模型（Double Diamond），用两轮探索与收敛组织设计。第一轮发现并定义问题，第二轮发展方案，再通过测试和改进交付。尝试过程中也可以返回前面的阶段。[来源：设计委员会](https://www.designcouncil.org.uk/resources/the-double-diamond/)

**发现问题 → 定义问题 → 探索方案 → 测试和改进。**

第一步，先看一份实际行程和准备过程。信息在哪些地方重复填写？每次修改最花时间的是哪一步？同行者需要在哪里参与？AI 可以整理材料、比较不同环节，用户补充实际经历。

假如发现主要困难是“移动一天的景点后，需要重新整理时间和费用”，就有了更具体的问题：怎样让行程调整少一些重复操作？网站、改进后的表格、现有工具组合，都可以成为候选解法。

接着比较这些办法，再用一份三天行程试一试。调整景点后，原信息是否保留？费用是否随之更新？操作比原来省事多少？如果试用发现主要困难其实是同行者迟迟无法确定安排，就要重新看问题定义。

这套方法适合初始想法还不成熟的工作。用户不用先决定所有功能，可以请 AI 帮助了解问题、比较方向，并设计一次有意义的尝试。**需求会随着材料和试验逐渐形成。**不过，AI 对用户行为的推测仍需要实际反馈支持。

### 2. Anthropic 与 Claude Code：让理解、执行和检查接起来

Claude Code 的官方最佳实践包含探索、规划、实现与提交，但更值得学习的是：怎样让 AI 获得足够的信息，并在执行后检查自己的工作。[来源：Claude Code 官方最佳实践](https://code.claude.com/docs/en/best-practices)

需求不完整时，文档建议让 AI 主动访谈用户，询问使用情境、边界情况和取舍，最后形成规格说明。这里，AI 应帮助发现用户尚未想到的问题。

例如，用户只知道想做旅游网站。AI 可以追问“自己使用还是多人使用”“行程变化后哪些内容需要保留”，同时解释这些选择会带来什么影响。涉及不熟悉的专业做法，应给例子、比较和建议。连续抛出数据库、认证方式等术语，并不能帮助新手作决定。

方案逐渐明确之后，再读取现有项目，形成实施计划。已有的费用字段、页面和保存方式，会影响新功能怎么做。复杂改动先探索和规划；小而清楚的改动可以直接处理，流程深度要与任务相称。

接下来，给 AI 一个能实际检查的结果。假设 600 元住宿费由三个人均分，某人另有 100 元个人支出，那么这个人的示例预算应是 300 元。改变人数，检查结果是否相应变化；保存并刷新，再检查费用是否还在。

有了这些依据，执行就能形成循环：**实现 → 运行检查 → 读取结果 → 修正 → 再检查。**AI 应展示运行结果或截图，而不只是说“已经完成”。文档也讨论了目标条件、程序检查和独立审查等办法，让检查能够持续参与执行。

Anthropic 的工程指南进一步区分了固定工作流与动态行动。固定周报可以按取数、核对、生成的顺序处理；诊断预算为什么没更新，则需要根据每次检查的结果决定下一步。若计算正确就查更新过程，若界面更新但刷新后丢失，就继续查保存和读取。[来源：智能体工程指南](https://www.anthropic.com/engineering/building-effective-agents)

长期工作还有一个重要条件：提供给 AI 的信息要有用。Claude Code 文档将上下文管理放在显著位置，因为对话、读取的文件和命令输出都会占用上下文。无关任务、过时决定和失败尝试不断积累，会干扰后续判断。

因此，长期约定应写得简短，特定工作的知识和步骤按需使用。在 Claude Code 中，前者可以放在 **CLAUDE.md**，后者可以做成技能；必须执行的程序动作可以通过钩子安排。调查和审查也可以在独立上下文中进行，再带回相关结果。

文字规则能指导行动，工具和程序检查负责取得实际结果。二者需要配合。规则越来越多、对话越来越长，并不自然意味着合作越来越可靠；应观察它们是否减少了错误、遗漏和返工。

这些是 Claude Code 的使用实践及 Anthropic 的工程思路。用于 Codex 时，借用的是协作原则，具体文件和命令要按相应产品安排。

### 3. OpenAI：把一段长期合作变成可接续的工作

第一次讨论旅游网站，双方决定先做行程编辑和预算。几天后继续，AI 又建议加账号和多人协作，预算还没检查，任务却越做越大。

OpenAI 的一个 Codex 工作流示例，具体讨论了怎样用规则、计划、阶段材料和进度记录组织这种长期合作。[来源：OpenAI 工作流实践](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)

先将跨阶段适用的要求写进 **AGENTS.md**。例如，改动前查看现有功能，完成后实际运行检查，不破坏已有行程编辑。它是 Codex 识别的可选指导文件，作用是保存项目的工作约定。用户可以让 Codex 根据现有项目拟出规则，再检查是否符合要求。

接着安排路线。示例用 **PLANS.md** 保存计划，再将各阶段任务拆开，写明目的、所需材料、范围和完成条件。另有 **GOALS.md** 保存目标与成功条件，**PROMPTS.md** 保存启动工作的请求。这些名称是示例中的可选约定。

预算阶段的任务于是具体到：费用变化后总额更新，刷新后能读到已保存记录。账号和多人编辑仍是以后评估的事项。AI 知道当前做哪里，用户也知道这轮应该看什么。

执行时还会产生新发现和决定。双方为什么暂不做多人编辑？因为当前首先验证单人调整行程是否方便，多人使用尚未调查。这样的理由值得保留在阶段上下文中，否则下一轮只看到功能缺失，可能又重新提出相同建议。

上下文记录有选择：保留会影响后续工作、判断或验证的决定与发现，资料指向原文件，无需复制整段聊天。阶段未开始，就不提前编写它的执行发现。

随后，**build-log.md** 记录实际进度和检查证据。“准备检查刷新保存”属于计划；“刷新后读到了新费用”才是观察到的结果。计算通过、保存尚未检查，也应分别写清楚。

下一轮开始时，Codex 读取相关规则、当前计划、重要决定和实际进度，就有依据接续。**文件的作用，要在实际读取和更新中体现。**只创建名字正确的文件，却不依据它们执行，并没有解决状态混乱。

这些步骤反复出现，手动安排会变得繁琐，示例便进一步用技能复用。不过，新生成的技能最初漏掉了计划文件和进度记录，作者检查后纠正了范围。这也说明，技能需要通过实际使用调校。

项目结束，再根据返工和验证结果复盘。保存功能为什么反复出错，是需求遗漏、检查缺失，还是已有结果没有记录？对应改进任务、检查或交接方式，下一次就能使用更合适的流程。

这里还需区分：**PLANS.md 是计划文件，计划模式用于形成方案；GOALS.md 是目标说明，目标模式用于持续推进任务。**文件与模式可以配合，作用不同。

### 4. Superpowers：将专业方法写成可以复用的步骤

一套方法经过几次使用，怎样避免每次重新交代？Superpowers 这个社区项目，将构思、规划等开发方法写成了技能。

其中的构思技能强调理解意图、比较方案和形成设计，并根据可行性试探、有限改动或架构性工作安排不同深度。[来源：构思技能快照](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/brainstorming/SKILL.md)

设计首先回答成果怎样使用、为什么采用这种做法。预算需要区分个人与共同支出、支持人数变化，这些属于设计决定。实施计划随后把决定落实为任务：费用记录包含什么，怎样计算和显示，怎样保存，用什么样例检查。[来源：实施计划技能快照](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/writing-plans/SKILL.md)

这样，“开发预算功能”才被拆成有明确结果的工作。计划还要写清执行者无法自行猜出的决定，否则任务分得再细，也可能各自实现了不同理解。

这一做法帮助复用专业流程，但复用仍要与当前问题匹配。短试验可以只回答一个可行性问题，新项目则需要更充分的设计与检查。写作、研究和运营也应采用各自的方法，不能直接复制软件开发步骤。

Superpowers 是社区方案，本篇未安装或验证其效果。它提供的启发是：**稳定有效的专业方法，可以保存为 AI 能读取和遵循的流程。**仍不确定的选择，需要留在当前合作中继续判断。

### 5. 人机协同研究：不同工作可以采用不同模式

前四项讨论工作怎样组织，接下来还要决定：人在其中怎样参与？

HBS AI Institute 的研究解读介绍了三种观察到的协同模式。[来源：人机协作研究解读](https://aiinstitute.hbs.edu/the-three-ways-professionals-work-with-ai-which-one-are-you/)

| 模式 | 通俗理解 |
| --- | --- |
| 分工协作（Centaurs） | 人主导问题和做法，将部分任务交给 AI |
| 持续共创（Cyborgs） | 人和 AI 不断交替提出、评价和修改想法 |
| 大量委托（Self-Automators） | 大部分流程交给 AI，人较少介入和检查 |

这些是行为模式。机构解读指出，常规任务中的整体委托可能有效；需要判断的工作，放弃评价容易带来问题。

**不同工作可以采用不同的协同模式，同一工作的不同阶段也可以切换。**写陌生领域的文章，先与 AI 讨论问题、比较论点，再依据资料调整结构，偏向持续共创；结构明确后，把资料整理等任务交给 AI，自己审阅关键事实，就可以按任务分工。

旅游网站同样如此。先共同分析旅行准备的困难，再委托实现明确功能，最后试用并讨论体验。这几步的参与方式可以不同。格式固定、容易检查的文件整理，则可以让 AI 承担更多执行。

决定参与程度，要看任务有多不确定、结果能否可靠检查，以及错误的影响。低参与接受结果，与有标准、有检查、有异常处理的自动化，仍有区别。

宝洁产品创新现场实验也提供了一个相关视角：AI 使用者的方案更能结合技术与商业知识，在该任务中，使用 AI 的个人表现达到未使用 AI 的团队水平。这支持 AI 参与补足知识视角，但实验对象是专业人士，不能据此认为新手可以省去所有专业判断。[来源：作者论文条目](https://www.nber.org/papers/w33641)

较早的人机协作元分析则提醒，合作并不总能超过人或 AI 单独工作中更好的一方，收益与任务有关。它不能代表当前 Codex 的表现，却说明协作方式也需要接受实际检验。[来源：作者论文](https://arxiv.org/abs/2405.06087v2)

将五组参考放在一起，双钻帮助认识问题，Anthropic 与 Claude Code 连接理解、执行和反馈，OpenAI 组织长期状态，Superpowers 复用专业方法，协作研究帮助考虑人的参与。接下来，要把这些做法用到自己的问题中。

## 二、还没想清楚时，怎样与 AI 一起形成做法

开始合作，不需要先把未知分成几类。更有用的是提供当前能提供的东西，说明哪里拿不准，让 AI 推荐怎样取得下一步进展。

### 从现有材料开始，也可以从一个困难开始

进入陌生领域时，可以这样提出请求：

> 我不熟悉这类工作。先解释通常要处理哪些问题、有哪些做法、怎样判断成果好坏，再结合我的条件推荐如何开始。专业选择请给例子和建议。

这轮应帮助用户认识领域、理解选择，得到有依据的起步办法。泛泛介绍一大堆知识，却没有连接当前条件，仍难以进入工作。

已有材料时，就直接让 AI 看材料：

> 这些是准备旅行时使用的攻略、聊天记录和表格。我觉得来回整理很麻烦，但不知道该改工具还是改流程。先分析问题可能出在哪里，比较几种做法，推荐一个值得尝试的方向。

AI 可以检查材料、归纳困难、提出假设。缺少实际操作信息，就请用户补一次演示或录制；有足够依据的部分，先形成判断。用户不用事先把每个困难翻译成专业需求。

有参考效果时，图片可以帮助说明布局和风格，操作录制可以帮助说明流程。但图片无法证明点击后发生什么。让 AI 区分能观察到的部分和需要补充的部分，再给样例对照，往往比反复描述“就是那种感觉”更容易推进。

双方还要检查是否理解一致。“自动算预算”可能指汇总已填写费用，也可能指根据目的地预测价格。请 AI 用一个输入和输出的例子复述，就能更早发现差异。

### 标准不知道，可以让 AI 推荐并解释

新手不知道什么才好，可以请 AI 根据用途提出评价办法。旅游预算功能是否合适，至少要看计算是否符合约定、修改是否方便、记录能否保存，以及实际使用是否减少重复整理。

这些判断对应不同证据：算例检查计算，刷新检查保存，实际调整一份行程检查操作。页面能打开，并不能证明旅行准备更省事。

选择路线也应使用同样思路。表格与网站哪个更合适，要比较它们怎样处理当前困难、投入多少、受到什么限制。拿一份行程试一试，再决定是否继续开发，可能比一开始完成所有功能更有价值。

已有方案时，可以换一种请求：

> 这些要求必须保留。请比较现有做法与值得考虑的替代方案，说明改善在哪里、增加什么成本，以及怎样验证收益。不要为了增加功能而扩大项目。

AI 应以当前方案为基线。保留原方案、调整某个步骤、改变验证方法，都可能是合理结果。

影响方向的疑问先处理。例如，是否多人共同编辑，会影响访问和保存的安排；字体暂未决定，通常不妨碍先验证费用计算。若几个要求冲突，让 AI 讲清实际影响，再共同取舍，无需用户先写一份抽象标准表。

### 把方向变成这一轮可以执行的任务

认识问题和比较方案之后，计划要落实到当前阶段。第一篇的计划模式，此时就能用上：

> /plan 请检查现有旅游网站，比较怎样减少修改行程时的重复填写，并让预算随费用变化更新。推荐第一轮范围，写清交付内容、所需材料和检查方式。先形成方案，暂时不要修改代码。

用户审阅的是用途与范围：原有编辑是否保留，新增行为是否对应问题，还有哪些假设需要试验。具体实现可以让 AI 推荐并解释，不必先学会所有技术。

计划达到能够推进当前阶段的程度，就可以执行。有明确终点的持续任务，可以使用目标模式：

> /goal 按确认方案完成这一轮：费用变化后预算更新，保存并刷新后记录仍在，原有行程编辑可用。实际运行并检查这些行为，修复问题。最后给出使用入口、检查结果和未完成事项。需要改变关键要求时，说明原因。

计划模式帮助调查并形成方案；目标模式支持在当前对话中持续推进可验证目标。持续执行仍受权限、运行环境、预算和具体阻碍影响。短任务也可以使用普通请求。[来源：官方提示词指南](https://learn.chatgpt.com/docs/prompting)、[目标模式实践](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

### 反馈说清发生了什么，再决定改哪里

用户不必先判断故障原因。“移动景点后原信息丢了”“刷新后费用变回旧值”，已经是有用的反馈。补充实际操作、预期行为、截图或录制，AI 就能进一步检查。

> 我希望移动景点后保留原信息，现在却要重新填写。请先看这段操作，判断是实现错误、流程不合适，还是之前遗漏了要求，再说明应该改哪里、怎样检查。

如果实现没有符合约定，修复并重测；如果方案本来就要求重复填写，重新讨论操作流程；如果功能都做对了，旅行准备仍然费劲，就要回到对问题的认识。

写文章也是如此。结构没有回答读者的问题，继续润色句子可能只是让错误结构更顺畅。**反馈要帮助找到该修改的层级。**说不清不满意的原因，可以请 AI 提供对照、解释差异，再逐步定位。

第一篇介绍的引导（Steer）适合纠正当前方向，排队（Queue）适合安排后续事项。影响当前工作的发现要及时处理，新想法则先判断是否值得加入这一轮，避免任务不断扩大。

## 三、形成自己的工作流，并让它能够继续使用

前面的做法，可以组成一套适合当前任务的流程。它的顺序和深度要由实际问题决定：已经清楚的部分直接利用，不清楚的部分通过解释、调查、比较或试验推进。

![人机协作流程：补足关键信息，执行验证，根据结果修正并接续](/Users/olivialee/Documents/ChatGPT/公众号/articles/2026-10-codex-guide/part-2/assets/collaboration-flow-v1.png)

以旅游网站为例，一轮合作可以这样组织。

**先了解困难。**用户提供旅行资料和整理过程，AI 分析重复操作、比较可能原因。当前留下的是问题理解和候选方向。若真实困难尚未定位，就先补一次操作观察，而不是全面开发。

**再选择值得尝试的办法。**AI 比较表格、现有工具与网站，解释成本和限制。双方选择一个小尝试，用真实行程观察是否省事。留下当前方案、依据和待验证假设。

**安排当前阶段。**如果选择网站，就让 Codex 查看已有项目，形成行程编辑与预算阶段的计划。哪些行为要实现，怎样检查，哪些事项暂不做，都进入这一轮任务。

**执行并取得证据。**Codex 实现、运行和检查，用户试用关键操作。计算和保存有相应证据，体验问题通过实际使用反馈。符合原需求却没有改善困难，就重新讨论方案或问题。

**整理结果，再决定下一轮。**记录已完成工作、重要决定、检查结果和未解决项。本轮达到约定标准，可以收束；新的想法放入后续选择，不必全部立即实施。

这份安排也可以由 AI 帮助形成：

> 请根据现有材料和我的目的，推荐适合这项工作的协作流程。说明先做什么、这一轮会得到什么、怎样判断继续，以及哪些事情需要我参与。缺少专业知识由你解释，缺少事实则提出调查或试验。确定后，整理成可以执行和接续的计划。

一个有用的回应，应当结合材料给出实际安排。例如，先查看一次行程调整过程，判断主要重复在哪里；若预算修改是主要困难，就用现有表格做一次小尝试，再决定网站是否值得开发。它应说明每一步为什么需要、会获得什么，遇到什么结果需要改变方向。

当这轮安排开始执行，就值得留下几类材料。**长期规则**保存一直有效的约定；**当前计划**保存阶段和任务；**重要决定**说明选择与理由；**进度记录**说明实际成果和证据。可以让 AI 根据项目规模整理，不必在起步时复制完整示例目录。

下一次开始，先读取这些相关材料，再决定当前动作。要求变化，更新对应计划与决定；记录过时，标清新的有效状态。对话历史可以帮助理解，项目材料则让关键内容更容易查找和接续。

做过几轮之后，再复盘流程本身。哪些步骤发现了真实问题？哪些审阅重复却没有帮助？哪次返工来自缺资料、误解或检查不足？据此保留必要步骤、补上缺口、删掉无效负担。

稳定而反复出现的部分，才适合做成技能。比如，读取当前阶段和材料，整理待处理事项，执行指定检查，再更新进度。专业流程中的判断仍要结合当前条件；模型、工具或工作要求改变，也应重新看旧方法是否合适。

用于公众号写作，同样可以形成调研、结构审阅、纯文字修订、排版与归档的流程，每个阶段有相应产物和判断办法。用于研究、经营或运营，则需要换成那些领域的调查与验证方法。

**一套自己的工作流，是从实际合作中逐渐形成、留下来并继续改进的做法。**开始时可以模糊，每轮仍应取得能够说明的进展：更理解了什么，决定了什么，做出了什么，实际检查到了哪里，下一步为何这样安排。

有了这些内容，一次次对话才能连成长期工作。下一篇继续讨论，怎样管理项目、文件和版本，让合作中的材料与成果更容易保存和复用。
