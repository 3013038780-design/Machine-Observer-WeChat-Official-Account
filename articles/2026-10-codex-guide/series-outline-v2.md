# 《和 Codex 一起工作：从产品地图到真实上线》六篇系列候选大纲

状态：待用户审核；六篇均为写作逻辑与结构，不是完整纯文字稿。

## 系列总逻辑

六篇按一个 AI 小白能力的形成顺序推进：先认识 Codex 的组成和边界，再学会提出可交付的请求，然后学会把稳定流程做成可复用能力，接着把方法迁移到不同身份，最后理解 GitHub、云服务、网站和网址怎样承接成果，并用一个完整项目走完循环。

贯穿案例仍是“做一个可以在手机 App 中运行的简单 2D 游戏”，但每篇都补充研究、内容、创业、运营和个人项目的对应场景。产品事实、编辑方法、社区项目和案例假设分开标注。

# 第一篇：认识 Codex 的工作地图

候选标题：《Codex 到底是什么：工作区、任务、终端与远程工作的基础地图》

### 核心内容

- Codex 与普通 Chat、ChatGPT Work、代码编辑器、终端、IDE 集成的关系。
- workspace、project、task/chat/thread、repository、folder、worktree 的边界。
- 桌面 App、CLI/终端、VS Code/JetBrains 等 IDE、Codex Cloud、Remote 的差异。
- Plan、普通提示、Goal、side chat、Queue/Steer、上下文压缩。
- 本地文件、云端环境、沙箱、网络、端口、预览、快照和生成产物。
- Voice、文件、图片、屏幕/电脑上下文、浏览器、Computer Use、Record & Replay。
- Skills、Plugins、MCP、Harness、Jev 等名称分别处于哪一层。
- 模型选择：代码理解、推理深度、速度、成本、视觉、图片和视频工具的边界；不把外部生成模型误称为 Codex 内置模型。
- Git、diff、review、pull request、安全审阅、回滚为什么属于 Codex 工作环境的一部分。
- Memory、Scheduled Tasks、后台运行、用量、限额和失败恢复。

### 读者带走的能力

开始工作前能回答：我在哪个环境工作？AI 能看到和操作什么？当前任务的完成证据是什么？哪些动作需要我批准？

# 第二篇：怎样写提示词，才能让 AI 把事情做完

候选标题：《不是会提问就够了：让 AI 真正交付的提示词方法》

### 核心内容

- 区分问知识、要建议、要计划、要执行、要审阅、要交接。
- 当自己不知道流程时，让 AI 先提问、比较路径、列出依赖、风险、成本和最小验证成果。
- 六段式协作协议：背景与现状、目标结果、范围与不做事项、资料/工具、交付格式、验收证据与停止条件。
- 要求 AI 先复述理解、列出未知和假设，再开始执行。
- 把复杂项目拆成勘察、计划、原型、实现、测试、审阅、修订、交接。
- 文字、图片、HTML、视频、录音/录屏、网页操作分别需要什么提示词。
- 工具调用提示：何时使用终端、浏览器、MCP、插件、Computer Use；如何限制权限、报告副作用。
- 项目级上下文：`AGENTS.md`、`PLANS.md`、README、决策记录与任务提示的分工。
- Skill 触发提示、Harness 任务契约、失败恢复提示和状态摘要。
- ASD-STE100 作为清晰技术写作约束，而不是万能提示词。
- 用测试、结构化输出、trace、grader、数据集和回归检查判断“真的完成”。

### 读者带走的能力

能把“帮我做一个网站/游戏/报告”改写成有范围、有证据、有停止条件的阶段任务。

# 第三篇：从提示词到 Skills、MCP、Harness 和新型工作流

候选标题：《提示词之后：如何把一次成功协作变成可复用工作流》

### 核心内容

- 一次性提示词、项目规则、Skill、MCP/工具、插件、Harness、Agent Runtime 的层级关系。
- Skill 的组成：`SKILL.md`、references、scripts、assets、版本和渐进披露。
- 怎样判断一个流程值得做成 Skill：重复、稳定、输入输出清楚、可验证。
- MCP 提供数据和动作；Skill 说明什么时候调用、怎样组合、失败如何处理。
- Harness 管理模型—工具循环、环境、会话状态、审批、事件、恢复和多代理。
- 沙箱、自托管环境、端口、文件挂载、网络和凭证的边界。
- 多代理、子任务、handoff、并行研究、合并结果和责任归属。
- Jev/TypeSafe/JevHarness 等新兴决策或评估工作流：路由、门控、快速判断、轨迹评估；标明它们是外部/社区生态，不是 Codex 自带保证。
- Skills、MCP、插件和社区 Harness 的安全审查：来源、代码、权限、数据流、提示注入、版本和回滚。
- 何时不该搭 Harness：先把流程跑通，再自动化；复杂架构不能替代不清楚的目标。
- 用 trace、evals、grader、成本和失败率评估工作流，而不是只看一次成功演示。

### 读者带走的能力

知道什么时候继续写提示词，什么时候建立 Skill，什么时候接工具，什么时候才需要完整 Harness；能审查一个新工作流再给它权限。

# 第四篇：不同身份如何建立长期工作流

候选标题：《不同身份如何用 Codex 建立自己的长期工作系统》

### 核心内容

- 按工作特征分类：探索、研究、创作、开发、运营、管理；同一身份可以同时拥有多种工作。
- 个人创作者：选题、资料、写作、配图、排版、发布和素材归档。
- OPC/独立开发者：需求、原型、代码、测试、发布、反馈和维护。
- 创业者/小团队：市场问题、产品定义、用户反馈、销售材料、技术实现和决策记录。
- 研究者/分析师：问题定义、证据、来源台账、分析、图表、报告和复核。
- 内容团队/运营团队：选题池、素材生产、多版本适配、日历、审批和数据复盘。
- 什么时候拆主任务、side chat、子任务、多代理、worktree 或新项目。
- Scheduled Tasks、Record & Replay、Skills、MCP 和 Harness 在不同身份中的适用程度。
- 团队治理：谁能安装 Skill、连接 MCP、批准操作、查看日志、修改规则和发布结果。
- 数据、隐私、客户资料、录音、屏幕内容、密钥和第三方账号的分级管理。
- AI 可以提出 SOP、RACI、Skill 或 Harness 草案，但人负责选择流程、承担责任和批准风险。

### 读者带走的能力

能把自己的身份和任务翻译成一套可持续工作系统，不必照抄程序员的工作方式。

# 第五篇：从代码到产品：部署、运营与真实世界

候选标题：《Codex 做完之后怎么办：从代码到可使用、可维护的产品》

### 核心组织轴

不是按厂商或产品名称排列，而是按“成果离开开发环境后，怎样被构建、运行、访问、观察、保护和持续更新”的生命周期排列。GitHub、腾讯云、阿里云和网站服务只作为不同层的例子。

### 章节结构

1. **先定义交付物**：一个代码仓库、一个可下载 App、一个网站、一个 API、一个内部工具或一个自动化任务，后续基础设施会不同。
2. **代码协作层**：Git、GitHub、分支、commit、issue、Pull Request、Review、Actions、Release、权限、组织和回滚。说明版本控制解决“谁改了什么”，不等于解决“产品能否运行”。
3. **构建与发布层**：依赖安装、构建、测试、制品、CI/CD、预发布、生产、灰度、签名、版本号和回滚；解释部署流水线如何把代码变成可运行产物。
4. **运行环境层**：本地机、虚拟机、容器、云服务器、云函数、托管平台和边缘运行；说明计算资源、操作系统、端口、进程和环境变量的责任。
5. **数据与状态层**：关系数据库、文档数据库、对象存储、缓存、队列、搜索、备份和迁移；说明网站/App 的数据为什么不能只放在代码仓库里。
6. **网络与访问层**：域名、DNS、URL、页面路由、API 地址、HTTPS、证书、反向代理、CDN、WAF、跨域和身份认证；把“一个网址能打开”拆成多个动作。
7. **云服务商只是实现路径**：腾讯云和阿里云可以提供计算、存储、数据库、网络、CDN、域名、证书和监控等服务，但它们不是同一个抽象产品，也不是 Codex 自动完成的部署按钮。选型按需求、地域、权限、服务等级、迁移成本和计费口径判断。
8. **产品与用户层**：网站、网页、移动 App、API、管理后台、登录、支付、邮件、短信、推送、文件上传、分析和客服；说明“能部署”与“用户能完成任务”之间的差别。
9. **可观测与运营层**：日志、指标、trace、错误监控、告警、健康检查、备份恢复、事故处理、用户反馈和版本复盘；解释没有观测就无法判断 AI 改动是否真的改善产品。
10. **安全、合规与责任层**：密钥、账号、个人信息、权限分级、数据保留、隐私说明、开源许可证、第三方条款、支付和行业要求；Codex 可生成清单和配置建议，不能替人承担法律或生产责任。
11. **成本与供应商管理**：模型、构建、云计算、数据库、带宽、存储、CDN、域名、第三方 API、监控和人工审阅分别产生什么成本；区分官方价、促销价、地域价和实际用量。
12. **Codex 在每一层能做什么**：生成配置、解释日志、写迁移脚本、检查构建、审阅 PR、准备发布清单、模拟故障和设计回滚；每项都要有权限范围和验证证据。
13. **上线不是终点**：发布、观测、反馈、修复、回滚、备份、迁移、扩容、停用和归档构成完整生命周期。

### 读者带走的能力

理解一个成果如何从开发目录进入版本库、构建流水线、运行环境、数据系统、网络入口和用户界面，并知道每一层的负责人、成本、风险和回退方式。

### 研究要求

腾讯云和阿里云必须分别查官方文档、官方计费页和查询日期；没有官方公开价或存在地域/规格差异时明确标注。GitHub、域名注册商和云厂商的功能不能互相替代地描述。

# 第六篇：从一句想法到一个 App：完整项目案例

候选标题：《从一句“我想做个游戏”到一个真实可访问的 App》

### 核心内容

1. **原始想法**：让 AI 先识别未知、提出问题和设计三条路径。
2. **项目定义**：玩法、用户、平台、技术栈、素材边界、完成证据和暂不做事项。
3. **项目启动**：创建工作区、仓库、`AGENTS.md`、`PLANS.md`、任务结构、权限和归档规则。
4. **学习与原型**：用小实验理解输入、状态、碰撞、计分和重开。
5. **垂直切片**：完成开始、操作、胜负和重开的一条可玩路径。
6. **代码、图片和界面**：分别写代码、图像、HTML 和界面提示，记录素材来源、尺寸、风格和替换方法。
7. **Skill 与重复操作**：把稳定的导出、检查、素材整理或构建流程沉淀为 Skill；必要时使用 Record & Replay。
8. **视频和录制**：区分屏幕演示、流程录制、游戏宣传视频和生成式视频；核实实际工具和模型。
9. **GitHub 协作**：分支、commit、pull request、测试、review、修订和合并。
10. **云端与网址**：部署测试版本，连接云资源，配置域名/DNS/HTTPS，生成可访问 URL；明确 App、网站和 API 的关系。
11. **测试与发布**：模拟器、真机、浏览器、不同屏幕、错误复现、日志、回归、签名、隐私、素材许可和商店资料。
12. **上线与维护**：反馈进入任务池，监控、回滚、备份、成本和版本管理。
13. **复盘与沉淀**：哪些提示词、Skill、规则文件和检查表值得保留；哪些假设和自动化需要撤销。

### 读者带走的能力

能从模糊愿望开始，形成项目定义、工作流、提示词、代码仓库、云端运行环境、网址、验收证据和维护记录。

## 共用附录

- 术语关系图：Chat / Work / Codex / project / workspace / repository / environment / harness。
- 六段式任务提示模板。
- `AGENTS.md`、`PLANS.md`、Skill 的最小示例。
- GitHub 分支与审阅清单。
- 云服务和网站上线检查表。
- 模型/工具/服务商选择记录表。
- 项目状态交接模板。
- 成本、权限、来源、版本和失败记录表。
