# 交付形式专题的基础想法与讨论留存

日期：2026-10-22。以下是讨论素材，不是已经验证的能力结论或正文。

## 用户提出的核心想法

很多人从未做过三维、建筑或工程技术图纸，不会主动想到向 AI 要这类成果。第一次尝试时，会发现原来还可以这样工作。文章要让读者跨出熟悉的表达形式，在不同工作、任务需求中，尝试意想不到但更有效的成果，同时保留探索的乐趣。

不能只推荐 HTML，也不能把“浏览器中阅读适合 HTML”当作价值解释。要回答换一种形式究竟省掉哪些工作，帮助看清什么。

用户明确举出的方向：

- 一直要求图片的内容，可能用可以操作的模型表达更好。
- 会场效果展示可以研究使用 Blender 构建场景，而不只反复生成平面效果图。
- 装修时可以研究让 AI 协助做 CAD 图纸。
- 不熟悉三维、建筑、工程的人，也应有机会通过 AI 从简单任务尝试这些形式。
- 交付物全景表要完整保留；本轮决定移入独立文章，不再塞进第四篇。

## 已形成的讨论判断

1. 交付不止新文件，还包括应用、交互界面、可重复执行的流程，以及原有系统里已经完成的修改。
2. 数据处理中间用的格式，与最后给人使用的形式可以不同。CSV 适合行列记录；JSON 可以保留产品、评价、来源之间的层次关系；最终可转成报告、工作簿或页面。
3. 同一份销售分析，可以交付结论报告、带公式工作簿、可筛选看板、每月运行的分析程序，或供其他系统调用的接口。
4. 看结果、操作结果、继续编辑、换输入重新生成、接入其他系统，是不同的交付层次。
5. 三维是表达方式，Blender 是制作工具；演示是使用场景，PowerPoint 是工具。工具与成果不能混为同一组选项。
6. 完整交付可能是成品、原始数据、来源与源文件的组合，根据后续用途选，不要求每次生成全部格式。
7. HTML 推荐要依赖具体价值：并排比较、筛选、选择与回传，减少记忆、翻找及口头描述。普通页面的点击不会自动回传 AI。
8. 比较效率要包括制作、转换、检查、阅读和修改，不能只比较生成时间或 token 数量。

## 三维成果的不同交付层次

| 读者要做什么 | 可以交付什么 |
| --- | --- |
| 看最终效果 | 渲染图、展示视频 |
| 自己观察 | 可旋转、缩放或切换材质的三维展示 |
| 继续修改 | 模型、材质、灯光、动画等工程文件 |
| 换尺寸再生成 | 根据输入生成模型的程序或参数化工程 |
| 放到别的系统使用 | 目标软件或展示平台可接收的模型文件 |

桌面收纳架作为初步尝试例已写入历史第四篇 v5：先观察立体形状、换角度，再调整抽屉位置和大小；有对应工具时保留模型与尺寸图。该例未实际制作，不能写成已验证案例。

## 自动化：用途、实现与完成状态

核心解释：除了这次做完，还可以交付以后能重复执行的办法。

| 用途 | 具体例子 |
| --- | --- |
| 批处理 | 一次把 100 张图片缩放、重命名和分类 |
| 定时整理 | 每周五汇总订单，生成周报 |
| 监测 | 定期检查页面或数据，发现价格变化、新增记录后执行指定动作 |
| 自动生成 | 新一期数据输入后，按模板生成图表、报告或证书 |
| 系统间同步 | 把系统 A 新增订单按约定更新到系统 B |

实现方式：脚本保存具体处理步骤；工作流将多个步骤连接起来；定时任务按时间启动；机器人通常是收到消息或事件后执行工作的程序。几者可组合，不是互斥格式。

以订单整理为例，三种不同的完成状态：

1. 一份已整理表格：完成本次工作。
2. 表格加处理程序：以后可以放入新订单，再运行。
3. 已配置并验证的自动流程：按时或遇到事件运行，结果和失败状态可查看。

写出程序不等于已经配置自动运行。说明输入在哪里、何时启动、输出去哪里、失败如何发现；不是 AI 凭空记住未来任务。这里只归档讨论，本轮没有创建定时任务或运行服务。

## 研究边界

用户的 Blender 会场、CAD 装修、交互模型等例子是后续案例方向，不视为已证明的通用优选。需要分别判断：只要快速看氛围，还是要多角度一致、按尺寸修改、进一步制作；再实测相应路径。正式工程用途与探索性预览应从成果用途上说清。
