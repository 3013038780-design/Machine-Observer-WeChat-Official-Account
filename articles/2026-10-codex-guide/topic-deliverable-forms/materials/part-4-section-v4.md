# 从第四篇 v4 保留的交付形式材料

2026-10-22 归档。历史稿件摘存，不是新专题定稿。

## 四、需要比较和判断时，优先考虑 HTML

如果成果需要看图、比较、筛选，值得优先让 Codex 做成 HTML 页面。格式本身就能帮人理解问题。

回到雨衣调研。假设已经收集了几款产品的价格、重量、背包覆盖方式、透气设计、图片和资料出处。

写成长文，可以一款一款介绍。但读到第四款时，读者得记着前三款的区别，再自己比较。即使资料完整，这部分理解工作仍然留给了人。

页面可以把关键差异并排摆出来：图片旁边就是参数，同一项设计横向比较；选中“需要覆盖背包”，只看符合条件的产品；想确认某条说法，直接打开对应来源。

这时 HTML 的价值很具体：它把原本需要在脑中完成的比较，变成眼前可以查看的关系。报告越依赖图片、对比和筛选，这种表达越值得优先考虑。

HTML 本身是描述页面结构和样式的文本，浏览器负责把它显示出来；需要按钮、筛选等功能时，再加入相应的交互。Codex 可以生成这些内容，打开页面检查，再修改布局或功能。它也能保留模板，让后面的更新沿用同一套表达。

这并不意味着“生成了代码”就等于交付成功。图片打不开、筛选条件没有生效、页面把重要信息挤到了看不见的位置，都需要检查。能读到页面源码，和实际看到页面效果，是不同的检查。

页面还可以成为合作过程中的临时界面。例如，在候选产品旁放一个“保留”选项，负责人勾选之后，把选择导出成文件，交给 Codex 继续分析。这样，比反复描述“留下第一款、删掉第三款、第五款再看看”更容易核对。

但这需要明确的回传方式。普通页面里的点击，不会自动变成 Codex 知道的信息；需要保存选择、导出结果，或者建立实际连接。

Thariq Shihipar 在一篇关于 Claude Code 的[实践文章](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html)中，展示了类似的做法：用 HTML 表达复杂信息，制作可以选择和编辑的界面，再把人的选择交回 AI。这个思路也值得用于与 Codex 的合作：让成果承担一部分沟通工作，减少人来回描述的负担。

具体选择，可以从接下来要做什么出发：

| 当前要完成的事 | 优先考虑 | 推荐理由 |
| --- | --- | --- |
| 反复修订观点和文字 | Markdown 或纯文字 | 直接修改和比对，避免内容没定就反复调布局 |
| 阅读、比较方案、查看图示与筛选 | HTML | 把差异摆出来，也能加入筛选和交互 |
| 正式文档修订、批注、沿用固定模板 | 原生 Word 文档 | 便于接入后续编辑流程，减少格式转换带来的问题 |
| 修改输入、保留公式、持续测算 | Excel 等工作簿 | 保留数据和公式之间的关系，输入变化后还能继续算 |
| 提交需要继续编辑的会议材料 | 原生 PPT | 保留可编辑的文字、图表和其他对象 |

这里的推荐是明确的：浏览器中阅读、比较和操作的成果，先考虑 HTML；以持续改文字为主，先留简单底稿；后续工作依赖 Word、Excel 或 PPT 的编辑能力，就直接制作相应文件。

做网页并不妨碍 Codex 生成其他格式。它可以借助不同的工具制作文档、工作簿、演示稿、图片和 PDF。选择交付路径，要看成果需要怎样继续使用。网页的截图无法代替可编辑的幻灯片，静态表格也无法代替会重新计算的工作簿。

同样，没有必要为了“显得完整”，同时生成所有版本。多一种格式，就多一份需要检查和保持一致的结果。

HTML 也未必生成得最快。一个带布局和交互的页面，可能比一份简单文字稿需要更多内容和检查；正式文档则要处理样式、分页和兼容。真正值得比较的，是从制作、检查到人的阅读、修改，整项工作一共花了多少力气。

理解 Codex 的工作方式，最后会改变交办工作的方式：把会影响判断的信息带给它，让它选择合适的方法去执行，用实际结果推动下一步，再把成果做成人能够判断和使用的形式。

更好的合作，应当让你少接手一些查找、搬运、计算和转换的工作，也让你更容易看清结果，然后作出决定。
