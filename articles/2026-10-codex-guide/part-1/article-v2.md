# Codex 到底是什么：小白开始长期工作的第一张地图

第一次打开 Codex，很容易把它理解成一个“更会写代码的 ChatGPT”。

于是第一反应通常是：

> 我要做一个网站，你帮我写。
>
> 我要开发一个 App，从头开始帮我做。
>
> 这是我的需求，你直接实现吧。

如果只是做一个下午就能结束的小 Demo，这样也许可以开始。但如果准备做的是一个持续几周、几个月的项目，期间还会修改需求、调试、测试、推翻方案、重新设计，那么真正需要先弄明白的，并不是第一条提示词怎么写。

而是：

> **Codex 到底在哪里工作？它能看到什么？它能改什么？一项长期工作应该放在哪里？它怎么知道自己做到哪了？又凭什么判断已经完成？**

这些问题没有分清，后面很容易出现一种奇怪的体验：Codex 明明很聪明，项目却越做越乱。

它忘记之前为什么这样设计；修一个问题时顺手改掉另一个东西；开了很多对话，却不知道哪个才是主任务；它说“完成了”，程序却根本跑不起来。

问题往往不只是模型能力，而是还没有给它建立一个稳定的工作现场。

这篇文章先把这张地图画出来。后续文章再讲提示词、项目规则、GitHub、Skills、云服务和上线维护。

## 一、Codex 不只是“回答代码问题”

普通聊天最容易形成一种习惯：我问一句，它答一句。

比如：

> Python 这个报错是什么意思？

> 帮我写一个登录页面。

> 这段代码有没有 bug？

在这种使用方式里，AI 最重要的产物是回答。

Codex 更接近另一种工作方式：你给它一个目标和一个真实的工作环境，它读取文件、修改代码、运行命令、查看结果、发现失败，然后继续修复。

所以 Codex 和普通聊天的区别，不只是代码写得更好，而是它可以在获得授权后进入项目现场，围绕文件、命令、测试和改动持续工作。

这也解释了为什么一句话不能脱离环境单独判断。让 Codex“修复首页打不开”，至少要知道代码在哪里、项目如何启动、依赖是否安装、错误能不能复现，以及什么结果才算修好。

可以先记住一句话：

> **普通聊天主要生产答案；Codex 可以在真实环境里持续采取行动。**

## 二、先记住这张最小地图

第一次使用 Codex，不需要先背一堆术语。先把下面几件事分开：

| 需要想清楚的东西 | 最简单的理解 |
| --- | --- |
| 项目与仓库 | 我们到底在改什么 |
| 工作环境 | Codex 在哪台“电脑”上工作 |
| 任务与对话 | 这一轮具体要完成什么 |
| Plan | 这件复杂的事准备怎么做 |
| Goal | 长期工作最终要达到什么状态 |
| 权限 | Codex 被允许看到和动到哪里 |
| 完成证据 | 什么事实可以证明它真的完成了 |

最后一项最容易被漏掉。

很多新手只写：

> 帮我把网站做完。

但长期工作真正需要的是：

> 哪些页面必须能打开？
>
> 哪些测试必须通过？
>
> 哪些命令可以验证？
>
> 哪些现有功能不能被破坏？
>
> 什么情况出现时，应该停下来问我？

这张地图不是术语表，而是开始工作前的检查表。后面每个概念，都在回答其中一个问题。

## 三、项目和仓库：我们到底在改什么

假设要做一个网站，项目文件夹可能长这样：

```text
my-project/
├── src/
├── public/
├── package.json
├── README.md
└── ...
```

这就是 Codex 的现实工作对象之一。它不只靠聊天记录理解项目，还会通过目录、配置、测试、Git 历史、项目文档和命令结果理解项目。

所以对于长期工作，一个重要认知是：

> **聊天记录不是项目本身。项目文件和项目状态才是。**

今天在聊天里告诉 Codex“首页不要使用渐变”，两周后这句话可能很难被准确找回。若这条要求长期有效，就应该进入项目规则或设计文档，让它成为项目的一部分。

这里要区分几个容易混在一起的词。

**项目**是长期工作的主题和范围。它可以收纳目标、资料、说明和多次协作。

**仓库**是代码及其版本历史的载体。它记录哪些文件被修改、什么时候修改，以及不同版本之间有什么差异。

**文件夹**是某个环境中的实际目录。Codex 能不能读到它，取决于当前工作环境和权限。

**任务或线程**是一段围绕具体目标展开的协作。例如“建立游戏骨架”“修复触摸操作”“检查发布包”，都可以有各自的任务边界和完成条件。

**worktree**可以把不同任务隔离到不同的工作目录，减少两个任务同时修改同一份代码造成的冲突。

一个游戏项目可以有一个长期项目说明、一个主开发任务、一个专门排查触摸操作的任务，以及一个用于尝试新界面的隔离 worktree。它们互相配合，但不是同一个对象。

这一区分很重要，因为“把资料放进项目”不等于“让所有任务自动拥有全部操作权限”。

## 四、工作环境：Codex 到底在哪里工作

可以把工作环境理解成 Codex 获得的一张工作台。

工作台上有什么，它才能直接使用什么：

- 项目文件；
- Git；
- Node.js、Python 等运行时；
- npm、pnpm 等依赖工具；
- 浏览器或测试工具；
- 环境变量；
- 网络访问；
- 模拟器、数据库或其他外部服务。

因此，“Codex 在想什么”和“Codex 在哪里执行”不是同一件事。

同样一句“运行项目，找出首页为什么打不开”，如果环境里有代码、依赖、正确的环境变量和启动命令，Codex 可以真正运行项目、看到错误、修改并重新运行。

如果环境里没有这些东西，它再聪明，也只能根据描述猜测。

这也是很多人把“没有进入现场”误认为“模型产生幻觉”的原因。它可能不是不知道答案，而是没有足够的现场证据。

### 本地、终端、Cloud 和 Remote

**本地工作**发生在当前电脑上。它可以接触本地文件、已经安装的依赖、模拟器和设备，但电脑、文件和权限都受这台机器控制。

**CLI 或终端**是通过命令行进入 Codex。它适合脚本化操作，或把任务直接放进已有的开发目录。终端不是更高级的聊天框；当前目录、命令、环境变量和批准方式都会改变结果。

**Codex Cloud**是在 OpenAI 管理的计算机或云环境中运行任务。它适合让任务在本地电脑休眠时继续，但云环境能访问什么仓库、依赖、网络和凭证，要看环境配置与权限。

**Remote**解决的是从另一台设备查看或控制正在运行的桌面任务。它不等于把本地电脑变成云服务器，也不等于手机自动拥有本地模拟器、文件和凭证。

比如，游戏项目可以在连接了模拟器的 Mac 上本地运行；不依赖本地设备的测试可以交给 Cloud；人不在电脑旁边时，用手机 Remote 查看进度和审阅结果。三者的文件、设备、凭证和失败原因都可能不同。

所以开始任务前，先问四个问题：

1. 代码和资料在哪个环境？
2. 任务需要哪台设备或哪种系统？
3. 它是否需要网络、第三方账号或本地凭证？
4. 如果当前环境不可用，任务应该暂停、换环境，还是只做分析？

## 五、任务和对话：一次协作不等于整个项目

有了项目和工作环境，才轮到“这一次具体做什么”。

比如：

```text
调查登录偶尔失效的原因。
```

```text
把首页移动端布局完成，并补齐测试。
```

```text
检查当前数据库 schema，提出迁移方案，先不要修改。
```

这些才接近一个有边界的任务。

长期项目不适合把所有事情塞进一个无限增长的聊天窗口：

> 做首页。
>
> 顺便修登录。
>
> 对了数据库也改一下。
>
> Logo 换掉。
>
> 昨天那个动画还是恢复。
>
> 顺便研究一下支付。

这像是把设计、后端、测试和产品决策叫进同一个房间，然后每隔几分钟更换议题。模型再强，也会逐渐失去边界。

更好的理解是：

> **项目是长期存在的，任务是阶段性的。**

判断要不要开新任务，不必先问“我要不要新建聊天”，而可以问：

> 这件事能不能单独定义完成条件？

如果能，它通常值得拥有独立的任务边界。这样主任务负责推进，旁支任务负责调查或解释，结果再回到主线。

## 六、Plan 和 Goal：路径、下一步与终点

面对复杂需求，新手很容易直接说：

> 好，开始做吧。

但更稳妥的第一步往往是：

> 先调查，先计划，先不要修改。

**普通提示**要求 Codex 做下一步明确动作，例如读取项目结构并列出缺口。

**Plan**讨论实施路径，适合目标不清、涉及多个文件、需要选择技术方案，或者做错会带来较大返工的任务。它回答的是：准备怎样接近这个问题？

**Goal**记录一个需要持续追踪的结果。它适合路径可能变化、但终点可以说清楚的工作。它回答的是：做到什么才算完成？

例如，用户可以设定这样的 Goal：

> 完成一个能在指定模拟器启动、能完成一局游戏，并通过验收清单的最小版本。

然后让 Codex 先形成 Plan：

1. 盘点项目和依赖；
2. 建立最小启动页面；
3. 实现操作和游戏状态；
4. 加入胜负与重开；
5. 运行测试和构建；
6. 在模拟器中验证；
7. 汇报仍未完成的事项。

Plan 可以因为现实情况改变，Goal 则应该保持清楚。计划回答“怎么走”，目标回答“走到哪里”。

这两个概念也不替用户做产品取舍。Codex 可以比较技术路线，但不能自动知道玩法是否值得做；它可以列出风险，但不能替用户承担发布责任。

## 七、输入方式和权限，决定 Codex 能做什么

Codex 不只接收文字。文件、图片、语音、终端输出、网页状态、屏幕内容和电脑操作，都可能成为工作上下文，但它们的含义和风险不同。

文件可以提供代码、需求、日志和参考资料；图片可以说明界面问题或错误提示；语音可以快速描述想法；终端输出可以提供命令真实执行后的结果；浏览器和电脑上下文可以让 Codex 观察或操作界面。

Record & Replay 则是把一次可重复的电脑操作记录成可复用流程。它和普通录屏、会议录音、游戏宣传视频不是同一种能力。

每增加一种操作能力，也会增加权限问题：

- 读取一个项目目录，和修改整个磁盘，不是同一个风险；
- 运行测试命令，和执行删除、部署或发送请求，不是同一个风险；
- 查看网页，和使用已登录账号提交表单，也不是同一个风险。

更稳妥的做法是让权限跟阶段匹配：分析阶段先读；修改阶段限定目录；部署阶段使用专门环境和凭证；涉及真实用户数据、支付或发布时保留人工审批。

密钥、云账号密码、SSH 私钥、支付凭证和客户资料，不应该直接写进提示词、公开仓库、录制过程或截图。

能操作，不等于应该操作。

## 八、别让项目只活在聊天记录里

一个项目如果持续三个月，Codex需要知道：为什么数据库这样设计，哪个方案失败过，当前做到第几阶段，下一个里程碑是什么，哪些问题暂时接受，哪些问题上线前必须解决。

这些信息不应该只依赖聊天记录。

长期项目需要把稳定信息写进项目本身。文件名可以不同，但通常至少需要几类内容：

```text
PROJECT.md   项目要做什么
PLAN.md      分几个阶段完成
STATUS.md    现在做到哪里，下一步是什么
AGENTS.md    在这个项目里工作要遵守什么规则
```

这里先记住一个原则：

> **重要知识不要只告诉 AI，也要沉淀到工作环境里。**

下一篇会专门讲怎样写提示词，以及这些项目文件如何配合。本文只需要知道：聊天记录负责当前协作，项目文件负责长期状态。

## 九、完成不是一句“已经完成”

AI 很容易说“已完成”，人也容易看到页面差不多，就觉得应该好了。

但工程里的完成最好是一组可以检查的事实：

```text
完成条件：

- npm test 全部通过
- npm run build 成功
- 首页、登录页和设置页可以访问
- 手机宽度 390px 下没有横向滚动
- 旧用户数据仍能读取
- README 已更新
- 没有新增 console error
```

这就是完成证据。

因此，不要只告诉 Codex：

> 做一个漂亮的登录页面。

可以告诉它：

> 完成登录页。保持现有设计系统。桌面和移动端都要正常显示。不修改认证逻辑。运行现有测试和 build。最后说明修改了哪些文件、运行了哪些验证，以及还有哪些问题。

前一句是在描述愿望，后一句是在定义工作。

## 十、第一条消息应该怎么写

如果现在要开始那个手机游戏项目，第一条消息不需要要求 Codex 生成完整产品。先让它建立共同理解：

> 我想做一款最终可以在手机上运行的简单 2D 游戏，目前没有编程经验，也没有确定技术栈。
>
> 这一轮先不要写代码，也不要创建项目。请先完成四件事：
>
> 1. 列出这个目标缺少的关键信息，最多提出 8 个必须回答的问题；
> 2. 给出三条从最小原型到手机运行的可行路径，比较学习成本、工具、风险和后续发布难度；
> 3. 为每条路径定义一个可以在一天内验证的成果；
> 4. 推荐一条路径，并说明依据和仍需要我决定的事项。
>
> 输出使用：已知条件、未知问题、方案比较、推荐方案、待我决定。不要把假设写成已经确认的事实。

这条消息没有要求 AI 猜着做完整项目，而是让它先暴露未知、比较路径、提出建议，并留下人的决定位置。

等路线确定后，再进入项目初始化；等项目初始化后，再进入第一条可玩的路径。

这就是长期协作的基本节奏：先建立现场，再定义任务；先形成路径，再开始修改；每轮都留下证据，再决定是否继续。

## 十一、Codex 能推进工作，但不能替人承担所有判断

Codex 的边界可以分成五类。

**判断边界**：玩法是否值得做、目标用户是谁、哪些功能应该删除，属于产品判断。

**事实边界**：平台规则、模型状态、云服务价格、第三方 API、设备兼容性和素材授权需要查一手资料。

**验证边界**：没有运行过的代码、没有覆盖的设备、没有复现的错误、没有检查的部署配置，不能只凭模型的描述视为完成。

**权限边界**：能访问文件、网络和账号，不代表应该执行所有操作。真实数据、支付、发布、删除和大范围修改，需要更严格的审批和回滚方案。

**责任边界**：Codex 可以写代码、整理清单、解释日志、提出下一步，但产品取舍、版权确认、账号责任、生产风险和对用户的承诺，仍需要人承担。

小白不需要先变成专业开发者。更实际的做法是，让 Codex 把专业流程解释出来，把每一轮工作缩小到可以观察和判断的范围，再用证据决定是否继续。
