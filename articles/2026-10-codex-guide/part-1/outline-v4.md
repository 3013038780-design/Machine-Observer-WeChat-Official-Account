# 第一篇提纲 v4：Codex 与 OpenAI 工作系统的第一张地图

## 重新确定文章定位

这篇不是“如何开始写第一段代码”的入门短文，也不是 OpenAI 全部产品的产品目录。它要做的是一张**与长期复杂工作有关的系统地图**：读者需要知道自己面对的是 ChatGPT、Work、Codex、API/Platform、连接的工具还是外部生成模型；这些部分怎样接起来；每个部分解决什么问题；哪些事情仍然需要人判断。

第一篇覆盖全景，后续文章再深入工作流、GitHub、Skills、部署和长期运营。全景不等于把每个按钮讲完，而是把层级、关系、边界讲完整。

贯穿案例仍是“一个没有编程经验的人，想做一款最终放进手机 App 的可玩小游戏”。每次引入产品或功能，都回答这个案例在当前阶段遇到的一个问题。

## 正文结构

### 开头：为什么“帮我做完”不是一个完整任务

用小游戏案例展示长期项目会同时涉及：想法、代码、素材、运行环境、测试、手机预览、发布和维护。由此引出：需要先认识整套工作系统。

### 一、先分清产品层：ChatGPT、Work、Codex 与 API/Platform

- ChatGPT：适合对话、研究、分析、文件和多种内容工作。
- Work：把聊天、文件、项目指令、计划任务和连接的工具组织到持续工作中。
- Codex：以软件开发和技术执行为中心，可以进入代码工作环境、读取文件、运行命令、修改并验证。
- API/Platform：把模型、工具和智能体能力接入自己的应用或服务。
- 边界：不能把所有 OpenAI 能力都统称为 Codex；图片、视频、语音、网页或外部工具可能由不同产品、模型或连接提供。

### 二、Codex 有哪些入口：桌面、终端、IDE、Cloud 和 Remote

- 桌面 App：图形化管理任务、工作区、审阅和环境。
- CLI/终端：命令行、脚本、当前目录和本地工具链。
- IDE：在编辑器里协作，适合边看代码边修改。
- Cloud：OpenAI 管理的计算机和可复用环境，任务可在本地电脑休眠时继续。
- Remote：从手机或另一处设备控制正在自己电脑上运行的任务。
- 关键区分：控制入口在哪里，代码实际在哪里执行。

### 三、工作空间和 worktree：两个容易混淆的“工作现场”

这一节单独拆开说明：

- **工作空间（Workspace）**是更大的工作边界：它决定项目、成员、工具、环境、权限和可用资源如何组织。
- **仓库/文件夹（Repository/Folder）**是实际保存代码、素材和配置的目录。
- **worktree**是同一个 Git 仓库的一份隔离工作副本，适合让主线、实验、修复或不同任务并行修改。
- **任务/Thread**是在某个工作空间和工作副本中推进的一段具体工作。
- **Artifact**是可以交付、预览或审阅的结果。

用一张关系图说明：工作空间规定“在哪个工作系统里做”，仓库规定“改哪份材料”，worktree规定“这次修改使用哪份隔离副本”。它们不能互相替代。

重点解释两个常见误解：项目放进工作空间，不代表每个任务自动共享所有未提交修改；创建 worktree，也不等于创建了一个新的项目。

### 四、一次协作怎样推进：Prompt、Plan、Goal、Queue、Steer、Side chat、Compact

- Prompt：请求下一步动作。
- Plan：先讨论路径，避免高风险修改。
- Goal：为持续迭代设定完成条件和证据。
- Queue：当前动作结束后再交给下一项任务。
- Steer：任务进行中需要改变方向时介入。
- Side chat：把旁支问题从主线中分出来。
- Compact：上下文变长后保留工作重点。
- 用一个小游戏开发日程说明它们不是同一组按钮，而是不同的协作控制方式。

### 五、输入与操作能力：文字、文件、图片、语音、屏幕、浏览器、Computer Use、录制与回放

这一节必须专门讲“录制”：

- 文件和代码提供项目材料；
- 图片提供界面、错误和视觉参考；
- 语音适合快速描述和讨论；
- 屏幕上下文让系统看到当前界面；
- 浏览器工具用于访问和验证网页；
- Computer Use 让模型通过鼠标键盘等界面动作操作受控环境；
- Record & Replay 把一次可重复的电脑操作记录下来，之后按流程复现；它不是普通录屏，也不是视频生成。

同时说明“看见”“建议”“操作”“录制复现”是四种不同能力，不要混为一谈。

### 六、能力从哪里来：模型、工具、Skill、MCP、Plugin、Harness

用分层图解释：

- 模型负责理解、推理和生成；
- 工具负责读取、运行、浏览或操作；
- Skill 把某类任务变成可复用流程；
- MCP 提供外部数据或工具连接；
- Plugin 把 Skills、MCP 和其他资源打包分发；
- Harness 是围绕模型组织上下文、工具、权限、循环和验证的执行框架。

这一节只讲关系和选择时机，详细配置放第三、四篇。特别说明：有工具不等于模型自动知道正确流程，有 Skill 也不等于事实已经核验。

### 七、文字、代码、图片、视频和网站：不同交付物不是同一种提示词

- 文字稿、代码、图片、视频、HTML、网站和部署产物的输入、验证方式不同。
- Codex适合组织代码、文件、测试和交付流程；图片/视频生成可能由专门模型或连接的工具负责。
- 解释网页、网站、URL、API 地址、预览链接和部署产物的关系，但不在本篇展开云服务部署。
- 例子：游戏的代码、角色图片、宣传视频、网页预览和手机安装包，必须分别验收。

### 八、权限、凭证、事实和责任边界

- 文件、网络、账号、密钥、真实数据和发布权限分层管理。
- 当前产品能力、模型状态、价格、地区与套餐必须查官方资料。
- 没有运行、测试或复现的结果不能当作完成证据。
- Codex可以帮助发现工作流，但不能替人承担产品、版权、安全、发布和用户责任。

### 九、回到小游戏：一张真正能使用的工作地图

用一张表回收：

| 现在要解决的问题 | 选择的入口/能力 | 留下的证据 |
| --- | --- | --- |
| 先理解目标 | ChatGPT/Work 对话 | 需求和未知问题 |
| 规划技术路线 | Codex Plan | 方案与风险 |
| 修改和测试代码 | 本地/CLI/IDE | diff、日志、测试 |
| 让任务持续 | Goal、Queue、Side chat | 状态与下一步 |
| 操作网页或设备 | Browser/Computer Use/Remote | 截图、录制、复现结果 |
| 交付产品 | 构建、预览、部署 | 安装包、URL、发布记录 |
