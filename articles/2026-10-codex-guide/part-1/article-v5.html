Codex 到底是什么：从聊天到交付的完整工作地图

和 Codex 一起工作 · 第一篇

本篇导读

从一个手机小游戏的想法出发，看懂产品入口、工作空间、执行环境、录制回放和可复用能力，以及怎样判断一项工作真正完成。

本文依据 OpenAI 官方文档核验，资料查询日期：2026 年 10 月 3 日。OpenAI 的产品入口、套餐和功能仍在快速变化，因此本文重点解释相对稳定的层级、关系和工作方式，而不是某个按钮当前位于界面的哪个位置。假设你完全没有编程经验。某天，你有了一个想法：我想做一款小游戏。它最后真的能在手机上打开、玩起来，然后发给朋友。你打开 ChatGPT，说：帮我把它做完。这当然可以成为一个开始。但很快，你会发现，“做完”其实包含很多完全不同的事情：你要把模糊想法变成规则；确定游戏运行在哪个平台；建立代码项目；制作角色图片和声音；修改程序；运行测试；在浏览器或者手机上看效果；修 bug；保存版本；也许接入服务器；最后生成安装包、网页地址，或者提交到应用商店。其中一些事情是思考问题。一些是修改文件。一些要运行程序。一些要操作浏览器和软件界面。一些要调用图片、语音或者其他模型。还有一些，AI 即使可以帮你执行，最后仍然必须由你决定：这个游戏是否真的好玩？素材有没有版权问题？是不是应该发布？某个操作是否值得授权？所以，在真正开始长期项目之前，最重要的第一步往往不是学会一条更厉害的 Prompt。而是先画出一张地图：你究竟在和什么工作？它在哪里工作？它能看见什么？能修改什么？什么算真正完成？这就是这一篇要解决的问题。

01

先别把所有东西都叫 Codex

第一次进入 OpenAI 现在的工作体系，很容易产生一种感觉：ChatGPT 会写代码，Codex 也会聊天；Work 会操作文件，Codex 也能操作文件；桌面 App 里同时又有 Chat、Work 和 Codex。它们是不是其实都是一个东西？不是。理解它们最简单的方法，不是背产品名称，而是问：我现在需要解决的到底是哪一层问题？

ChatGPT：先把问题想清楚

ChatGPT 是最宽的一层入口。你可以用它讨论想法、研究资料、分析文件、写文字、看图片、解释代码，或者解决一个暂时还不需要真正进入工程环境的问题。比如小游戏刚出现的时候，你甚至还不知道：

  • 是做一个点击游戏还是解谜游戏；
  • 用网页技术还是原生 App；
  • 玩家为什么愿意玩第二次；
  • 第一版到底应该做到什么程度。

这时最需要的不是立刻创建代码仓库，而是把问题说清楚。

ChatGPT Work：从“回答”转向“完成一项工作”

当问题不再是“一问一答”，而是需要查资料、读取文件、连接已有工具、持续执行多个步骤，并最终产出文档、表格、幻灯片、网站或其他交付物时，Work 更接近你真正需要的工作方式。OpenAI 当前把 ChatGPT Work 定义为面向较长、多步骤工作的 agent。它可以结合文件、应用、浏览器和被授权的工作上下文来完成任务，并允许用户查看进度、改变方向和批准重要操作。比如：帮我整理小游戏的需求，研究三种实现方案，比较风险，形成一份开发计划，并把第一周任务拆出来。这已经不是简单“回答一个问题”，而是在推进一个工作成果。

Codex：进入软件真正发生的地方

当事情进入代码、仓库、命令、依赖、测试、Git 和运行环境时，Codex 的角色开始变得明确。OpenAI 当前将 Codex 定义为面向软件开发工作的 coding agent；它可以出现在桌面 App、CLI、IDE、Web 和 Cloud 等不同入口中。比如你现在已经有一个游戏项目，目录里至少有：

  • src/：程序代码；
  • assets/：图片、音效等素材；
  • package.json：依赖和运行脚本；
  • README.md：项目说明。

你希望 AI：

  • 阅读现有代码；
  • 修改 src/game.ts；
  • 安装依赖；
  • 启动开发服务器；
  • 运行测试；
  • 检查错误日志；
  • 比较 Git diff。

这时你需要的已经不是“一个知道怎么写 JavaScript 的聊天机器人”，而是一个进入实际软件工作环境的 agent。这才是理解 Codex 的关键。

API / Platform：把能力做进你自己的产品

还有第四层：OpenAI API 和 Platform。如果你不是想“让 ChatGPT 帮我工作”，而是希望你做出来的游戏、网站或服务本身调用模型，就进入了 API 层。例如，你以后希望小游戏里的 NPC 能调用模型生成对话，那么你需要考虑 API、模型调用、鉴权、成本、服务器逻辑和用户数据，而不是简单打开 Codex。API 的 agent 体系甚至可以直接使用 OpenAI 管理的 Codex harness：由 OpenAI 管理 session、工具循环、上下文压缩和恢复，再连接你选择的执行环境。因此第一张地图可以先这样看：

想问题、研究、讨论

ChatGPT

推进较长、多步骤的知识工作

ChatGPT Work

进入代码、命令、测试和工程环境

Codex

把模型和 agent 能力接进自己的产品

OpenAI API / Platform

它们之间会重叠，但重叠不代表它们是同一个层级。而图片、语音、浏览器操作、Computer Use，以及通过插件连接的外部系统，又是叠加在这些入口上的不同能力。所以以后遇到一个功能，先别问：“这是不是 Codex？”先问：它是在负责理解，负责执行，负责连接，还是负责生成某一种具体产物？

02

Codex 在哪里？先区分“控制入口”和“执行地点”

另一个最常见的混乱是：Desktop、CLI、IDE、Cloud、Remote 到底是什么关系？这里有一个非常重要的判断方法：我在哪里告诉 Codex 做事，和 Codex 实际在哪里执行工作，是两个问题。

Desktop：图形化控制台

现在的 ChatGPT 桌面 App 同时包含 ChatGPT 与 Codex 相关工作流。2026 年的桌面产品整合后，Codex 仍保留独立视图和自己的开发工作流，而 ChatGPT 一侧则可以在 Chat 与 Work 之间切换。桌面 App 的价值不只是“另一个聊天窗口”。对于开发任务，它可以成为一个控制台：你可以看到任务、diff、文件、终端、浏览器、审批请求、工作环境以及多个正在推进的聊天。

CLI：站在项目目录里面工作

CLI 是终端入口。如果你在：cd my-gamecodex启动 Codex，那么当前目录本身就是非常重要的工作边界。官方文档明确说明，Codex CLI 会把启动时所在目录视为当前聊天的项目目录，也可以通过 --cd 指定目录。这特别适合已经习惯：

  • shell；
  • Git；
  • npm、pnpm；
  • Python；
  • 构建脚本；
  • 测试命令

的人。但它不是“能力更高级的 Codex”。它只是另一种控制入口。

IDE：在代码旁边协作

IDE 扩展则更适合一种非常具体的场景：你已经打开代码，而且正在阅读。这时你希望直接选中一个函数，说：这里为什么会出现状态不同步？或者：保留这个接口，只修改下面的渲染逻辑。IDE 可以把当前 workspace、打开的文件或者选择的代码直接变成上下文。官方文档也把 IDE 当前打开的 folder/workspace 视为本地项目范围。

Cloud：换一台真正执行工作的电脑

Cloud 的本质就不同了。Local 和 Worktree 都在你的电脑上运行；Cloud 则让任务进入一个已发布的远程环境。官方目前把三种模式直接区分为：

  • Local：直接使用当前项目目录；
  • Worktree：在 Git worktree 中隔离修改；
  • Cloud：在可复用的远程环境中开始任务。

一个 Cloud environment 可以提前准备：

  • repository；
  • dependencies；
  • tools；
  • network access；
  • secrets；
  • setup scripts。

然后每一个 Cloud task 拥有自己的工作文件。最直观的区别是：Cloud task 可以在你的电脑睡眠以后继续执行。所以“把电脑合上还能继续”不是因为 Codex 神奇地控制着一台已经睡眠的 Mac。而是因为真正执行任务的机器已经不是你的 Mac。

Remote：换了遥控器，但没有换机器

Remote 恰好相反。例如你出门以后，用手机打开 Codex Remote。你可以：

  • 发起任务；
  • 查看任务；
  • 发送新的指导；
  • 批准操作；
  • 查看 diff 和测试结果。

但真正工作的仍然是与你连接的电脑。官方目前的描述非常直接：手机负责 start、guide 和 review，任务运行在 connected computer 上；如果走的是这种 Remote 本地执行路径，电脑需要保持在线和唤醒。所以，Remote 和 Cloud 可以这样区分：

想清楚

01手机 / Web / Desktop / CLI / IDE

你的电脑或开发机

留下的结果：Remote 控制本地任务；电脑需要在线并保持可用

02手机 / Web / Desktop

OpenAI 管理的 Cloud 环境

留下的结果：Cloud 任务在远程环境继续运行，本地电脑可以休眠

在执行地点内部，还要继续区分：

  • Local：直接使用当前项目目录；
  • Worktree：在 Git 隔离副本中修改；
  • Cloud task workspace：在云端任务自己的工作副本中修改。

只要把入口和执行环境分开，大量产品名立刻就不混乱了。

03

Workspace、Project、Repository 和 Worktree：不要把四层东西塞进一个词

接下来会遇到另一个危险词：Workspace。它尤其容易让新手混乱，因为今天的 OpenAI 工具里，workspace 至少可能表达两种不同东西。

第一种 Workspace：你属于哪个 ChatGPT 工作环境

在 ChatGPT 的组织层，workspace 是你的个人或组织环境。它关系到：

  • 谁是成员；
  • 有什么权限；
  • 哪些产品能力可用；
  • 哪些插件可以安装；
  • 哪些管理员策略生效。

OpenAI 的企业文档也明确把 workspace access、Codex local runtime、Codex Cloud、Platform API、plugins 和外部系统权限视为彼此不同的控制边界。因此：加入一个 workspace，不代表你自动拥有所有代码仓库、云环境、账号和外部系统权限。

第二种 workspace：IDE 里的工作目录

到了 VS Code 或其他编辑器里，workspace 又常常只是：我现在打开的这个 folder / workspace。这是文件系统意义上的工作现场。所以写长期项目文档时，最好少说一句模糊的：“把项目放进 workspace。”而改成：“把它加入 ChatGPT Project。”或者：“在 IDE 中打开这个本地 workspace。”否则同一个词可能指完全不同的东西。

Project：把长期工作的上下文放在一起

Project 更接近普通用户理解的“项目”。当前 ChatGPT Projects 可以把相关的：

  • chats；
  • files；
  • instructions；
  • connected sources

组织在一起。一个项目可以同时包含 Chat 和 ChatGPT Work 的聊天。桌面 App 还存在 local project：它可以连接一个或多个本地文件夹。所以我们做小游戏时，可以建立：Project: Mobile Game里面放：产品讨论技术路线UI 研究角色设定第一次开发Bug 修复发布准备它们属于同一件长期工作，但不应该强迫所有内容挤在同一个聊天里。

Repository / Folder：东西真正放在哪里

项目概念解决的是“这些事情属于谁”。Repository 和 Folder 解决的是：文件到底在哪里？例如：~/Projects/my-game里面才真正存在：src/assets/package.json.git/Codex 修改代码，本质上最终还是修改这些文件。

Worktree：同一个仓库，多开一个隔离工作现场

现在假设游戏已经能运行。你正在主目录修改菜单系统，但又希望 Codex 同时实验一个新的关卡。如果两边直接改同一批文件，就容易互相覆盖。这就是 Git worktree 有用的地方。Codex 可以为一个聊天创建独立 worktree。官方当前实现会从所选择分支的 HEAD 开始建立工作副本；如果你明确选择带本地修改的分支，也可以把这些未提交修改应用到新 worktree。多个 worktree 因此可以围绕同一 repository 同时开展不同工作。于是，同一个 Repository 可以对应多份工作副本：

Local checkout

修改主菜单

Worktree A

实验新关卡

Worktree B

修复音频 Bug

代码来源可以相同，工作副本彼此隔离。

Chat、Task 和 Thread 也不是一个东西

这里再清理三个词。Chat 是你与 ChatGPT 或 Codex 的一段持续对话和工作记录。Task 更偏向“需要完成的结果”：修复启动崩溃。这是一项 task。而 Thread 在当前 Codex app-server / SDK 文档中更偏技术对象：它保存 turns 和 conversation history。普通用户不需要把所有聊天都刻意称为 thread。为了避免概念污染，这一系列后面会尽量使用：Project：长期工作容器Chat：一次相对独立的协作Task：这次要完成的结果Repository / Folder：实际文件Worktree：隔离的 Git 工作副本至于 Artifact，本文把它当作普通意义上的“工作产物”，而不是强行当成某个统一的 OpenAI 产品对象。例如：

  • 一份设计文档；
  • 一个代码 diff；
  • 一张图片；
  • 一个 APK；
  • 一个 URL；

都可以成为需要验收的 artifact。

于是完整关系可以压缩成五层：

ChatGPT Workspace

账号、成员、政策和能力边界

Project

长期工作的聊天、文件、说明和来源

Chat / Task

一次相对独立的协作和要完成的结果

Repository / Folder / Worktree

实际文件与隔离的 Git 工作副本

修改、测试、构建 → Artifact

可以检查、预览或交付的结果

这里有两个特别常见的错误。第一个：“我已经把项目放进 Project 了，所以所有聊天应该都自动看到我电脑上的最新代码。”不一定。ChatGPT Project 的共享文件和来源，与电脑文件夹的实时状态不是同一个概念；官方也特别区分 conversation sync 与 local project-file access。第二个：“我创建了一个 worktree，所以相当于又创建了一个项目。”也不是。worktree 只是同一个 Git repository 的另一份工作副本。

04

Prompt、Plan、Goal、Queue、Steer、Side Chat、Compact：它们控制的是不同时间尺度

现在终于可以真正开始做小游戏了。假设今天的任务是：做出第一个可玩的关卡。很多人会把所有控制方法都理解成“不同形式的 Prompt”。其实它们解决的是不同时间尺度上的协作问题。

Prompt：现在做什么

Prompt 是最普通的一次请求。例如：阅读当前代码，告诉我为什么角色碰到墙以后会穿过去。先不要修改。它控制的是：下一步。

Plan：先决定怎么走

任务一复杂，就不要急着改。例如：先检查当前输入系统、碰撞系统和场景结构，提出最小修改方案，不要写代码。Plan Mode 当前就是用来处理这种多步骤规划的。它回答的是：我们准备怎么做？特别适合：

  • 影响范围未知；
  • 会修改多个系统；
  • 有数据迁移；
  • 有发布风险；
  • 你还没决定采用哪条路线。

Goal：什么状态才算结束

Goal 和 Plan 最大的区别，是 Goal 不只是“列计划”。它定义一个可以持续追踪的终点。官方当前把 Goal 描述为一个 persistent objective：ChatGPT 会朝它持续工作，直到完成、暂停或者需要更多输入。例如：做出一个可以从开始界面进入第一关、移动角色、碰撞正常、失败后重新开始的可玩版本。现有测试不能退化，新增行为必须有验证；如果无法继续，说明阻塞原因并停止。Plan 回答：怎么做？Goal 回答：什么时候才能说做完？

Queue：做完现在这件，再做这个Codex 正在修碰撞。你突然想到：修完以后顺便检查一下重新开始按钮。这不应该打断现在的工作。把它 Queue。Queue 会把消息留给下一次运行。

Steer：方向错了，现在就纠正

另一种情况：Codex 原本只需要修碰撞，却开始重构整个物理系统。这时候你说：不要重构引擎。保持当前结构，只做最小修复。这应该 Steer。Steer 会进入当前正在进行的运行，让 agent 改变方向。一句话记：Queue = 等这一轮结束Steer = 现在就转向

Side chat：我有个问题，但别打断主线

Codex 正在工作。你看到日志里出现：requestAnimationFrame你只是想问：这个东西到底是什么？没必要为了这个问题破坏主任务上下文。Side chat 就是这种“思维旁支”。当前 /side 会开启一个临时的旁支对话，而不打断主聊天。主聊天负责：把游戏做完。Side chat 负责：帮我理解正在发生什么。这个区别对长期项目非常重要。

Compact：不是删除历史，而是压缩工作记忆

一段协作可能持续很多天。如果把所有历史逐字保留，上下文最终会越来越庞大。Compact 的目的，是压缩已有上下文，同时尽量保留后续继续工作需要的状态。当前 Codex 提供 /compact，API 体系也存在对应的 compaction 机制。它更接近：把厚厚的工作记录整理成可以继续工作的状态。而不是：忘掉以前发生过什么。

于是一个实际开发日可能变成：09:00Prompt“检查当前项目状态。”

09:10Plan“先规划第一关实现，不修改代码。”

09:30Goal“完成第一个真正可玩的版本，并通过指定测试。”

11:00Steer“不要重写物理系统，只修当前碰撞问题。”

11:05Side chat“为什么这里会发生 frame drop？”

12:00Queue“当前修复完成后检查 restart flow。”

几天以后Compact压缩越来越长的工作上下文。它们不是七种“高级 Prompt”。它们是在控制协作过程本身。

05

让 AI “看见”不等于让它“操作”：文件、图片、屏幕、浏览器和 Computer Use

到这里，还需要拆开另一个经常被混为一谈的问题：AI 到底能不能看我的电脑？这个问题太大。更准确的问法至少应该拆成四个动作：看见理解操作复现

文件：给它真正的项目材料

代码、配置、日志、PDF、文档、数据，本质上都属于文件上下文。如果你只是描述：游戏打开以后画面不对。Codex 只能根据描述判断。如果它能读取项目文件，就可以检查真正的实现。

图片：告诉它“现在看起来是什么样”

UI Bug 很适合图片。例如：iPhone 上开始按钮跑出屏幕了。一张截图经常比三百字描述更准确。当前 ChatGPT/Codex 文档也把 image inputs 作为独立输入能力。

语音：降低描述成本

语音适合你脑子里已经有很多想法，但不值得慢慢打字的时候。比如边看游戏边说：这里移动太快了，然后这个弹窗出现的时候我希望背景慢一点暗下去……它首先解决的是输入效率。

屏幕上下文：让系统看到当前软件状态

如果任务发生在 GUI 软件里，屏幕内容本身就是上下文。在 macOS 上，Computer Use 需要相应的 Screen Recording 和 Accessibility 权限，才能看到目标应用并与之交互。但：能看到屏幕，不等于已经获得所有操作权限。

Browser：给网页工作一个共享现场

ChatGPT 桌面 App 当前提供内置浏览器。它可以让你和 ChatGPT 在同一个页面状态上工作，例如：

  • 打开本地网页；
  • 查看真实渲染效果；
  • 标记一个 UI 问题；
  • 检查网页状态。

内置 Browser 使用自己的 browser profile，并不会自动继承你普通浏览器里的 tab 和登录状态。

Computer Use：从“看”进入“操作”

Computer Use 再向前一步。它可以与软件 UI 进行交互。官方当前文档描述的能力包括查看屏幕、截图，以及与窗口、菜单、键盘输入和剪贴板状态交互；在浏览器里，它还可以打开页面、点击、输入并检查最终页面状态。例如测试小游戏：打开游戏→ 点击 Start→ 移动角色→ 撞墙→ 点击 Restart→ 检查状态是否重置过去你可能需要自己做完整流程。现在 agent 可以在受控环境中执行其中一部分。但这是操作能力，不是“模型变聪明了”。

Record & Replay：把“我示范一次”变成可复用流程

Record & Replay 又是另一层。它不是普通录屏。也不是：录一个视频，以后再播放视频。它当前的设计是：你演示一次电脑操作流程，ChatGPT 或 Codex 把它转换成可以检查和修改的 reusable Skill。例如你每次测试游戏都要：启动模拟器→ 打开测试账号→ 进入关卡→ 执行一组固定动作→ 检查结果有些步骤很难通过 Prompt 精确描述。这时候直接“做一次给它看”可能比写一页说明书更自然。需要注意的是，截至本文核验日期，Record & Replay 仍要求 macOS 和 Computer Use；OpenAI 当前的可用性说明仍注明初始开放范围不包括欧盟、英国和瑞士等地区。所以这七类能力最好不要混起来：文件 → 给材料图片 → 给视觉状态语音 → 给自然语言输入屏幕 → 给当前界面状态Browser → 给网页工作现场Computer Use → 进行界面操作Record & Replay → 把示范沉淀为可复用流程

06

模型、工具、Skill、MCP、Plugin、Harness：能力究竟从哪里来？

现在我们来到最容易被各种 AI 术语淹没的一层。你可能已经见过：ModelToolSkillMCPPluginHarness它们并不是六种 agent。可以把它们看成一套系统里的不同零件。

Model：负责理解和推理

模型首先负责：

  • 理解你的输入；
  • 判断问题；
  • 推理；
  • 生成文字或代码；
  • 决定下一步需要什么能力。

但模型自己并不等于电脑。它“知道应该运行测试”，和它“真的拥有一个终端并运行了测试”，不是一件事。

Tool：真正能做动作的手

工具让模型可以做模型本身做不了的事情。比如：读文件运行 shell搜索网页调用数据库操作浏览器生成图片因此可以把 Tool 理解成：一个可以被模型调用的具体动作接口。

Skill：教它一类事情应该怎么做

有工具仍然不代表会做对。假设你给一个 agent：读取文件工具搜索工具邮件工具然后说：做一次客户周报。它仍然需要知道：

  • 先找哪些材料；
  • 哪些数据可信；
  • 输出什么结构；
  • 缺信息怎么办；
  • 最后检查什么。

Skill 就解决这一层问题。OpenAI 当前把 Skill 描述为一组可复用的 instructions 和 resources，用来教 ChatGPT/Codex 完成特定工作流；一个 Skill 可以包含 SKILL.md、参考资料、模板、脚本等。所以：Tool = 我能做什么Skill = 这类事情应该怎么做这两个概念非常值得记住。

MCP：把外部世界接进来

如果工具不在 OpenAI 自己的环境里呢？例如：

  • 公司内部数据库；
  • 一个私人服务；
  • 自己开发的部署系统；
  • 项目管理系统。

MCP，也就是 Model Context Protocol，可以把外部工具和数据暴露给 AI 客户端。MCP server 可以提供 tools、resources、prompts 和相关 instructions；对于 Plugin 工作流，最重要的通常是它提供的工具与外部系统访问。所以：MCP = 一种连接协议和接口边界而不是一个“更高级的 Prompt”。

Plugin：把能力包装起来

Plugin 再向上一层。当前 OpenAI 的 Plugin 可以包含：

  • Skills；
  • MCP server；
  • 外部应用连接；
  • 以及部分可选扩展资源。

可以把 Plugin 理解成一个能力包：

Skills

可复用的工作流程

MCP server

外部系统和工具的连接

Tools

具体可调用的动作

Optional UI

给人使用的界面组件

因此：MCP 和 Plugin 不是竞争关系。MCP 负责把外部能力接进来。Skill 负责告诉 agent 如何完成工作。Plugin 可以把这些东西包装成一个可安装、可分发的能力单位。

Harness：让这一切真的跑起来

最后是 Harness。它很容易被忽略，却可能是理解 agent 最重要的词之一。Harness 不是一个模型。它是围绕模型构建的执行框架。在当前 OpenAI Agents API 的定义中，Codex harness 会管理模型与工具之间的循环，以及 agent session；环境则负责真正执行代码和处理文件。可以把它理解成一条执行链：

User Goal

说明要达到的结果

Harness

组织上下文、工具调用、循环和停止条件

Model

理解、推理并决定下一步

Tools

读取文件、运行命令、浏览或操作界面

Skills

提供可复用的流程知识

MCP / Plugins

连接和包装外部能力

Execution Environment

真正提供文件、程序和计算机

模型负责思考。工具负责动作。Skill 负责流程知识。MCP 负责外部连接。Plugin 负责包装和分发。Environment 提供真正的文件和计算机。Harness 则负责：让这些东西组成一次可以持续运行、调用工具、检查结果并继续下一步的工作循环。所以，“换模型”并不一定意味着整个 agent 系统都换了。同样，“安装了一个工具”也不意味着 agent 自动知道正确使用方法。更重要的一句话是：有 Tool，不代表流程正确；有 Skill，不代表事实正确；有 Agent，不代表结果已经验证。

07

代码、图片、视频、网站和 App，不是同一种“生成”

回到小游戏。最后你可能得到：游戏规则说明.md代码仓库角色.png宣传片.mp4网页试玩地址iPhone App它们看起来都是“AI 帮我做出来的”。但从工程角度，它们完全不是同一种输出。

一份代码，不等于一个程序

模型生成：function startGame() { ...}只是代码文本。只有真正进入项目：保存文件→ 安装依赖→ 编译→ 运行→ 测试以后，它才开始接近“可工作的软件”。

HTML 不等于网站

你让 AI 写出：index.htmlstyle.cssapp.js你拥有的是网页文件。如果它运行在：http://localhost:3000你拥有的是本地预览。如果以后部署到：https://example.com才拥有一个其他人可以访问的互联网地址。所以：HTML ≠ 网站localhost ≠ 公网 URL源码 ≠ 部署产物

API 地址也不是网页地址

另一个常见误区：https://api.example.com/game可能只是程序调用的 API endpoint。浏览器打开它，看见一段 JSON，并不代表“网站坏了”。URL 只是地址。地址背后是什么服务，需要另外判断。

每种交付物都有自己的完成证据

小游戏最后应该分别验收：

想清楚

01想清楚

ChatGPT / Work

留下的结果：目标、未知问题、方案比较

02做出来

Codex、Local、Worktree、Cloud

留下的结果：代码、diff、测试和构建结果

03操作与验证

Browser、Computer Use、Remote、Record & Replay

留下的结果：页面状态、操作记录和复现结果

做出来

04交付

网站、URL、API、安装包

留下的结果：可访问地址、构建产物和验收记录

这也是为什么：“Codex 已经写完代码了。”和：“产品已经完成。”之间，可能还隔着很长一段路。

08

权限、凭证、事实和责任：Agent 的边界不是“能不能想到”

随着能力越来越强，我们必须建立另一张地图。不是能力地图。而是权限地图。

能做到，不代表被授权做到

一个 agent 可能理论上会：修改文件访问互联网打开 GitHub发送消息修改线上配置发布网站但真正运行时，它应该受到：

  • sandbox；
  • filesystem permissions；
  • network policy；
  • workspace permissions；
  • external account permissions；
  • approval policy

等多层限制。官方当前也明确区分 ChatGPT workspace 权限、本地 runtime、Codex Cloud、Platform API 和 connected systems 的访问边界。不要把：“我登录了 ChatGPT。”理解成：“Agent 已经拥有我所有账号的权限。”

凭证是另一层东西

API key、GitHub token、SSH key、服务器密码、数据库凭证都不是普通文本材料。长期项目一个很重要的习惯是：尽量给完成任务所需的最小权限，而不是把所有钥匙都交出去。

“AI 说做完了”不是完成证据

如果 Codex 说：测试应该可以通过。它没有运行测试。那它只是在判断。如果它说：我运行了 npm test，42 个测试全部通过。你就有了更强的证据。如果这是一款手机游戏，最终可能还需要：我在目标设备安装了构建产物，并完成了 Start → Play → Fail → Restart 的测试流程。证据又更强了一层。长期项目最重要的变化之一，就是把问题从：AI 回答得像不像真的？改成：它留下了什么可以检查的证据？

当前产品事实也需要重新查询

这一点对学习 Codex 本身尤其重要。模型名称、套餐、价格、地区、功能入口、实验功能和限制都可能变化。例如，2026 年的 ChatGPT 桌面 App 与几个月前的 Codex 产品关系已经发生明显变化。所以遇到：“现在 Plus 能不能用这个？”“当前模型叫什么？”“这个功能在瑞士开放了吗？”正确做法不是从一篇半年以前的教程里猜。而是查看当前官方资料。

最后还有一层不能外包：责任

Codex 可以：

  • 给你方案；
  • 帮你研究；
  • 写代码；
  • 改代码；
  • 运行测试；
  • 操作工具；
  • 找到可能的问题。

但它不能替你承担：

  • 产品方向；
  • 用户体验；
  • 商业决定；
  • 隐私义务；
  • 版权判断；
  • 安全责任；
  • 上线责任。

Agent 可以帮助形成判断。但判断最终属于人。

09

现在重新做一次小游戏：整张地图终于可以用了

最开始，我们只有一句：帮我做一款最终可以放在手机 App 里的小游戏。现在，我们终于可以把它拆成一个真正的工作系统。

想清楚

01想清楚做什么

ChatGPT / Work

留下的结果：需求、范围、风险和下一步

02进入软件现场

Codex + Local / Worktree / Cloud

留下的结果：文件变更、命令输出和测试

03把结果交给别人

Browser / Remote / 构建与部署

留下的结果：预览、URL、安装包或发布记录

这才是一张“能拿来工作”的地图。不是：哪个产品功能最多？而是：我现在处在哪个问题层级？下一步应该把哪种能力接进来？它在哪里执行？最后拿什么证明它完成了？

10

第一次真正有用的输入，不是“帮我写代码”

如果你准备开始一个可能持续几周甚至几个月的项目，第一条信息可以先不要求 Codex 写任何代码。比如：目标我想从零完成一款最终可以在手机上运行的小型单人游戏。第一阶段目标不是发布，而是做出一个可以在目标设备上实际试玩的最小版本。我的现状我没有正式的软件开发经验，因此遇到技术选择时需要解释关键概念，但不要把整个任务降级成教程；仍然以真正做出产品为目标。已有材料目前只有游戏概念和几张视觉参考，没有代码仓库。先检查我提供的材料，并列出缺失信息。工作环境在真正创建代码前，先建议适合这个项目的开发环境、项目结构和运行方式，并说明哪些东西会保存在本地、Git 仓库和云环境中。权限第一阶段可以读取我主动提供的文件和公开网页。不要创建线上账号、购买服务、提交商店、公开发布或使用需要付费的外部服务，除非我明确批准。当前阶段现在处于项目定义阶段。先不要写完整游戏。完成证据这一阶段完成时，我希望看到：明确的第一版范围、技术路线、主要风险、需要安装的工具、项目目录建议，以及下一阶段的可执行任务。停止条件如果某个关键决定必须由我选择，或者需要新增付费、账号、密钥、隐私权限或发布权限，请停止在那个决定点，并解释选项，不要自行假定。这段话真正重要的地方不在于它“写得像 Prompt 工程”。而在于它给出了一个工作系统真正需要的八样东西：目标现状材料环境权限阶段完成证据停止条件有了这些以后，Codex 才不只是得到一句：“帮我做游戏。”它得到的是一个可以开始工作的边界。

写在最后：不要先学会指挥 AI，先学会定义工作

第一次使用 Codex，很容易把注意力全部放在模型能力上。它会不会写 Swift？会不会 React？能不能自己修 Bug？能不能一次做完整个 App？这些当然重要。但当一项工作从十分钟变成十天、十周甚至更久以后，真正决定结果的，越来越不是“这一轮回答够不够聪明”。而是：任务放在哪里？文件到底是哪一份？谁拥有修改权？这一轮在本地还是云端执行？什么时候应该规划？什么时候应该纠偏？哪些上下文应该长期保存？哪些操作需要批准？怎样证明它真的完成了？这也是从“聊天”走向“协作”，再从“协作”走向“交付”的分界线。Codex 最值得理解的地方，不是它能写多少代码，而是它第一次让模型真正进入软件工作的现场。但进入现场以后，文件、环境、权限、验证和人的判断仍然存在。它们没有因为 AI 变强而消失。相反，AI 能做的事情越多，我们越需要看清这些边界。第一张地图到这里就完成了。下一篇，我们会真正进入一次长期协作的内部：如何把一个模糊目标拆成 Prompt、上下文、任务、验收条件、反馈和交接，让“帮我做完”逐渐变成一个 AI 和人都知道该怎么推进的工作流。
