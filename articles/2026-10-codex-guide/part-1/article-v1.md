# Codex 到底是什么：小白开始长期工作的第一张地图

> **内容提要**
>
> Codex 不是一个输入愿望就自动交付成品的窗口。它需要一个可以访问的工作环境、一段连续的任务上下文、明确的完成证据，以及用户在关键节点做出的判断。
>
> 本文从一个“想做一款可以放进手机 App 的小游戏”的模糊想法出发，解释 Codex 的工作区、项目、任务、对话、仓库、本地、终端、Cloud、Remote、Plan 和 Goal 分别解决什么问题。读完后，第一次打开 Codex 的人应该知道先选哪里、先说什么、哪些权限可以给、哪些事情不能直接交出去。
>
> 本文只建立基础地图。提示词的详细写法、GitHub 和 Skills 的配置、云端部署与网站上线，分别放在后续篇目。

## 一句“做个游戏”，为什么还不能开始

“我想做一个可以在手机上玩的游戏”是一个方向，不是一项可以直接执行的任务。

它至少缺少几个决定性条件：游戏给谁玩，核心玩法是什么，先支持网页还是手机，使用触摸还是键盘，第一版做到什么程度，哪些功能暂时不做，怎样算完成，代码和素材放在哪里，最后由谁在什么设备上测试。

如果这些条件没有确定，Codex 可能仍然会生成代码，但生成的内容很难判断是否正确。它也可能选择一个不适合初学者的技术路线，或者在还没有验证最小玩法之前，先做菜单、动画和复杂的账号系统。

所以，长期工作的第一步通常不是“开始写”，而是先确定三个东西：**工作发生在哪里，当前要完成哪一小段，以及用什么证据判断它完成了。**

这也是理解 Codex 的入口。

## Codex 在整个工作系统中的位置

Codex 的核心工作是软件开发和技术工作。它可以阅读代码和项目文件，修改文件，运行命令和测试，检查改动，解释错误，并在连续的任务中继续推进。

这和普通聊天的关系，类似于“讨论问题”和“进入工作台”的区别。普通聊天适合问概念、比较方案、整理思路；Codex 的价值在于，它可以在获得授权后接触代码、终端、仓库和开发工具，把讨论变成可检查的改动。

ChatGPT Work 解决的是更广的长期工作，例如研究资料、文档、表格、报告或其他交付物。它和 Codex 可以协作，但不应把两者当成完全相同的工作表面。一个创业者可能先在 Work 中整理用户需求，再在 Codex 中建立产品原型；一个内容团队可能用 Work 整理资料，用 Codex 做网站或内部工具。

代码编辑器和终端也不是 Codex 的同义词。编辑器是查看和修改文件的地方，终端是执行命令的地方，Codex 是在这些环境中帮助完成软件任务的代理。它可以通过桌面应用、命令行或编辑器集成进入同一个开发过程，但不同入口的文件权限、界面和可用工具可能不同。

因此，“我在用 Codex”还不够具体。真正需要问的是：**我通过哪个入口，让它在什么环境里，处理哪一份工作？**

## 先分清你正在创建的是什么

第一次使用时，最容易混淆的是“项目”“任务”和“代码所在位置”。它们经常同时出现，却承担不同作用。

可以把它们想成一间工作室里的不同区域。

**工作区或运行环境**决定 Codex 能接触哪里。它可能是当前电脑上的一个文件夹，也可能是一个云端环境。它决定文件是否存在、命令在哪里运行、是否能访问网络，以及是否连接了模拟器、数据库或其他工具。

**项目**用于聚拢长期相关的背景、文件、说明和讨论。它更像一个主题范围，帮助不同任务共享必要的上下文。项目并不自动等于代码仓库，也不意味着其中的每个文件都应该被读取或修改。

**任务、对话或线程**承载一段具体协作。比如“建立游戏骨架”“修复碰撞错误”“检查发布包”可以是不同任务。它们各自有自己的对话过程、改动记录和完成条件。一个长期项目不一定要把所有事情塞进同一个对话；当问题有独立目标、不同权限或不同验证方式时，拆开反而更清楚。

**仓库、文件夹和 worktree**是代码实际存在或被隔离出来的载体。仓库保存版本历史；文件夹是本地或环境中的目录；worktree 可以让不同任务在相互隔离的工作目录中进行，减少同时改动同一份代码的冲突。

回到游戏例子：项目可以保存游戏的目标和资料；主任务负责搭建可玩的第一版；另一个任务专门排查触摸操作；代码仓库保存文件和历史；一个隔离的 worktree 用来尝试新的界面。它们相互关联，但不是同一个对象。

这一区分很重要，因为“把资料放进项目”不等于“让所有任务自动拥有全部操作权限”。

## 本地、终端、Cloud 和 Remote，不是同一件事

Codex 可以在不同位置工作，而“远程”这个词容易把几种情况混在一起。

**本地工作**发生在当前电脑上。Codex 可能读取本地文件、运行终端命令、使用本机安装的依赖，并连接本地模拟器或设备。它的优点是离真实开发环境近；限制是电脑必须开着，文件和权限也受这台电脑控制。

**CLI 或终端工作**是通过命令行进入 Codex。它适合已经习惯终端、需要脚本化操作，或希望把任务放进现有开发目录的人。终端不是“能力更强的聊天框”，而是另一种工作入口；命令、当前目录、环境变量和批准方式都会影响结果。

**Codex Cloud**是在 OpenAI 管理的计算机或云环境中运行任务。它适合让任务在本地电脑休眠时继续，但云端是否能访问某个仓库、依赖、网络或凭证，要看环境配置和工作区权限。云端能运行代码，不代表它能看到本地电脑上没有上传或连接的文件。

**Remote**通常是从另一台设备访问正在运行的桌面任务。它解决的是“人不在电脑旁边时如何查看进度、追加要求或审阅结果”，不等于把本地电脑变成云服务器，也不等于手机自动拥有本地模拟器、文件和凭证。

例如，游戏项目可能在有模拟器的 Mac 上本地运行；晚上用 Cloud 执行不依赖本地设备的测试；手机通过 Remote 查看任务和审阅改动。三者的文件、设备、权限和失败原因都可能不同，不能因为都叫“远程”就把它们当成同一种工作方式。

开始任务前，先确认四个问题通常比马上输入提示词更有用：

- 代码和资料在哪个环境？
- 任务需要哪台设备或哪种系统？
- 它是否需要网络、第三方账号或本地凭证？
- 如果环境不可用，任务应该暂停、换环境，还是只做分析？

## Plan、普通提示和 Goal：路径、下一步与终点

长期工作中，三个概念很容易被混用：普通提示、Plan 和 Goal。

**普通提示**要求 Codex 做下一步明确动作。例如：“读取项目结构，列出启动游戏还缺少的文件，不要修改代码。”这类请求适合范围已经清楚、只需要推进一个动作的情况。

**Plan**用于先讨论路径。它适合目标不清、会影响多个文件、需要选择技术方案，或一旦做错就会产生较大返工的任务。计划应该说明准备怎么做、依赖什么、有哪些风险、怎样验证。Plan 回答的是：“我们准备怎样接近这个问题？”

**Goal**用于持续追踪结果。它适合路径可能随着调查而变化，但终点可以说清楚的任务。例如：“完成一个能在指定模拟器启动、能完成一局游戏并通过验收清单的最小版本。”Goal 回答的是：“做到什么才算完成？”

一个适合长期项目的顺序可以是：先用普通提示描述愿望，让 Codex 帮忙发现缺口；再用 Plan 讨论路径；确认边界后，设定带验证条件的 Goal；执行过程中用普通提示推进具体步骤，用 Queue 等待当前工作结束，用 Steer 修正正在偏离的方向。

Side chat 也有自己的位置。主任务负责推进，旁支对话可以解释某个错误、追问某个选择，或帮助理解一段结果。这样既能保留主线，又不会让每一个临时问题都改变项目目标。

这些模式不会替用户决定游戏到底应该做成什么，也不会替用户验证所有设备。它们只是在不同阶段提供不同的协作结构。

## 输入方式和权限，决定 Codex 能做什么

Codex 不只接收文字。文件、图片、语音、终端输出、网页状态、屏幕内容和电脑操作都可能成为工作上下文，但它们的含义和风险不同。

文件适合提供代码、需求、日志和参考资料；图片可以说明界面问题、错误提示或视觉方向；语音适合快速描述想法和现场问题；终端输出提供命令真实执行后的结果；浏览器和电脑上下文让 Codex 能观察或操作界面。Record & Replay 则是把一次可重复的电脑操作记录成可复用的流程能力，它和普通录屏、会议录音、游戏宣传视频不是同一个功能。

每增加一种输入或操作能力，也会增加新的权限问题。读取一个项目目录，和修改整个磁盘，风险不同；运行测试命令，和执行删除、部署或发送请求的命令，风险不同；查看网页，和使用已登录账号提交表单，责任也不同。

因此，权限不应被理解成“开得越多越方便”。更稳妥的做法是让权限跟当前阶段匹配：分析阶段先给读取权限；修改阶段限定文件和目录；部署阶段使用专门的环境和凭证；发布或涉及真实用户数据时，保留人工审批。

密钥、云账号密码、SSH 私钥、支付凭证和客户资料不应该直接写进提示词、公开仓库、录制过程或截图。一个能执行命令的代理，必须同时配合清晰的授权范围、日志和回退方式。

## 第一次工作的最小设置

如果目标是让 Codex 帮忙启动一个游戏项目，第一条请求不需要要求它生成完整产品。更合适的首轮工作是建立共同理解。

可以这样写：

> 我想做一款最终运行在手机上的简单 2D 游戏，目前没有编程经验，也没有确定技术栈。
>
> 这一轮先不要写代码，也不要创建项目。请先完成四件事：
>
> 1. 列出这个目标缺少的关键信息，最多提出 8 个必须回答的问题；
> 2. 给出三条从最小原型到手机运行的可行路径，比较学习成本、工具、风险和后续发布难度；
> 3. 为每条路径定义第一个可以在一天内验证的成果；
> 4. 推荐一条路径，并说明推荐依据和仍需要我决定的事项。
>
> 输出使用：已知条件、未知问题、方案比较、推荐方案、待我决定。不要把假设写成已经确认的事实。

这条请求有几个作用：它把“做游戏”变成了一个分析任务；让 Codex 暂时不改代码；要求它把未知和假设分开；还要求给出可验证的第一步。

等路线确定后，下一轮才适合进入项目初始化，例如确认代码目录、运行环境、第一版范围和验收方式。整个过程不需要用户一开始就懂所有术语，但需要保留三个判断：哪些建议接受，哪些范围暂时删掉，什么证据可以证明这一阶段完成。

## Codex 的边界，不只是一句“请核实”

理解边界，可以分成五类。

**判断边界**：玩法是否值得做、目标用户是谁、哪些功能应该删掉，属于产品判断。Codex 可以比较方案，但不能自动知道用户真正愿意承担什么成本。

**事实边界**：平台规则、模型状态、云服务价格、第三方 API、设备兼容性和素材授权需要查一手资料。生成得很流畅，不代表事实已经核实。

**验证边界**：没有运行过的代码、没有覆盖的设备、没有复现的错误、没有检查的部署配置，都不能仅凭一句“看起来没问题”视为完成。

**权限边界**：能访问文件、网络和账号，不代表应该执行所有操作。真实数据、支付、发布、删除和大范围修改都需要更严格的审批和回滚方案。

**责任边界**：Codex 可以帮助写代码、整理清单、解释日志和提出下一步，但最终的产品取舍、版权确认、账号责任、生产风险和对用户的承诺，仍需要人承担。

这并不意味着小白必须先变成专业开发者。更实际的做法是：让 Codex 把专业流程解释出来，把每一轮工作缩小到可以观察和判断的范围，再用证据决定是否继续。

下一篇将继续回答一个更具体的问题：当目标还没有想清楚时，怎样写第一条提示词，让 AI 先帮助建立工作流，而不是直接猜着执行。
