# Codex 到底是什么：从聊天到交付的完整工作地图

第一次打开 Codex，很多人会把它理解成“一个更会写代码的 ChatGPT”。

于是第一句话往往是：

> 帮我做一个可以放进手机 App 的小游戏。

这句话可以作为起点，却不能直接作为完整任务。

因为一个真正能交付的小游戏，至少会涉及：玩法、界面、代码、图片和音效、开发环境、测试设备、版本记录、预览地址，最后还可能有安装包、网站和发布账号。

如果这些东西只散落在不同对话里，项目很快会出现问题：文件找不到，修改互相覆盖，本地能运行但换一台设备就失败，Codex 说“完成”却没有测试证据。

所以，使用 Codex 的第一步不是记住某个按钮，而是先看懂自己正在使用的整套工作系统。

这篇文章不讲完整的游戏开发教程，而是回答一个更基础的问题：当一项工作会持续几天、几周甚至几个月时，ChatGPT、Work、Codex、Cloud、Remote、工作空间、worktree、工具和模型分别放在哪里？它们怎样一起工作？

## 一、先分清：ChatGPT、Work、Codex 和 API/Platform

这些名称经常出现在同一个产品界面里，但承担的工作不同。

**ChatGPT**更像一个通用工作入口。它可以用于对话、研究、文件分析、文字整理，也可以调用可用的工具和连接。

**Work**适合把一项持续工作组织起来。项目可以集中放置相关对话、文件和指令，也可以配合连接的工具、语音或计划任务。它解决的是“怎样围绕一个主题持续协作”。

**Codex**的中心是软件开发和技术执行。它可以在得到授权的工作环境中读取代码和项目文件，运行命令，修改文件，检查测试结果，并根据结果继续推进。

**API/Platform**则是另一层：开发者把模型、工具和智能体能力接入自己的程序或服务，让自己的应用调用这些能力。

可以先用一句话区分：

> ChatGPT 负责更广泛的对话和内容工作，Work 负责组织持续协作，Codex 负责进入软件项目现场，API/Platform 负责把能力接进自己的产品。

这并不意味着它们完全隔离。一个游戏项目可能先在 ChatGPT 或 Work 中整理想法，再交给 Codex 建立代码项目；如果最后要做一个自动化服务，还可能通过 API/Platform 把模型能力接入产品。

但不能把所有 OpenAI 能力都叫作 Codex。图片、视频、语音、浏览器、电脑操作和第三方服务，可能由不同的模型、产品或连接提供。第一步不是背下产品名称，而是知道当前这项工作到底由谁负责。

## 二、Codex 有哪些入口

同一个 Codex 任务，可以从不同入口开始或继续，但入口会改变你能看到的控制方式。

### 桌面 App

桌面 App 适合管理本地项目、查看任务、选择工作环境、审阅修改和处理需要电脑权限的操作。它更接近一个工作台。

### CLI 和终端

CLI 是命令行入口。你可以在项目目录中运行 Codex，执行测试、构建、脚本和版本控制命令。

终端不是“更高级的聊天框”。当前目录、环境变量、已经安装的依赖、命令执行权限，都会影响 Codex 能否真正完成任务。

### IDE 扩展

IDE 扩展把 Codex 放进代码编辑器里，适合边看代码边提问、修改和审阅。它仍然依赖项目文件和当前开发环境，而不是只依赖聊天记录。

### Cloud

Codex Cloud 在 OpenAI 管理的计算机上运行任务。你需要先准备一个环境，把仓库、工具、依赖和访问设置配置好；之后可以让任务在本地电脑休眠时继续运行。

Cloud 任务通常有自己的隔离工作空间。开始一个新任务，不会自动恢复另一个任务里尚未提交的修改，因此重要改动仍要通过版本控制保存。[OpenAI 对 Codex Cloud 的说明](https://help.openai.com/en/articles/20001545-using-codex-cloud)

### Remote

Remote 解决的是“人不在开发电脑旁边时，怎样继续控制正在运行的任务”。手机或另一台设备是控制入口，代码仍然运行在原来的电脑、开发机或连接的主机上。

它和 Cloud 不是一回事：Cloud 换了执行机器；Remote 主要换了控制入口。OpenAI 官方也把两者明确区分开来。[OpenAI 对 ChatGPT Work、Codex 与 Remote 的说明](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)

做小游戏时，可以在连接模拟器的电脑上本地调试，把不依赖本地设备的测试交给 Cloud，离开电脑后用 Remote 查看任务进度和审阅结果。

开始任务前，先问清楚两件事：

1. 我从哪里控制这项工作？
2. 代码和工具实际在哪台机器上执行？

## 三、工作空间和 worktree 不是一回事

这是初学者最容易混淆的一组概念。

**工作空间（Workspace）**是更大的工作边界。它可能涉及项目、成员、环境、连接、权限和可用资源。它回答的是：这项工作属于哪个工作系统，谁可以参与，Codex 能获得哪些条件。

**仓库（Repository）**是代码和版本历史的载体。

**文件夹（Folder）**是某个环境中的实际目录。仓库可以被放在文件夹里，但“能不能访问这个文件夹”还要看当前环境和权限。

**worktree**则是同一个 Git 仓库的一份隔离工作副本。它适合把不同任务分开：一份 worktree 做新功能，一份 worktree 修 bug，另一份 worktree 做实验。这样不同任务不会直接改同一份工作目录。

可以这样记：

> 工作空间决定“在哪个工作系统里做”；仓库决定“改哪套代码”；worktree 决定“这次修改使用哪一份隔离副本”。

它们不能互相替代。

一个小游戏项目可以属于某个工作空间，代码保存在 GitHub 仓库中；“实现触摸控制”使用一个 worktree，“尝试新界面”使用另一个 worktree。两个任务都属于同一个项目，却不必在同一份未提交代码上互相覆盖。

**任务或 Thread**是在某个工作空间和工作副本里推进的一段具体工作。**对话**是这段协作的交流记录。**Artifact**则是可以预览、审阅或交付的结果，例如构建包、报告、图片、网页或其他生成文件。

因此，聊天记录不是项目本身。长期有效的规则、当前进度、重要决定和验收条件，应该写入项目文件或其他稳定位置。

## 四、一次协作怎样推进

复杂项目里，几个看起来相似的控制方式，其实解决不同问题。

### Prompt：要求下一步动作

例如：

> 请读取项目结构，列出当前缺少的依赖，不要修改文件。

它适合有明确边界的一次行动。

### Plan：先讨论路径

当需求不清楚、会修改很多文件，或技术路线选错会造成返工时，先让 Codex 进入 Plan 模式，要求它调查现状、比较方案、说明风险，再决定是否修改。

Plan 回答的是：**准备怎么走。**

### Goal：持续追踪终点

Goal 适合“路径会变化，但终点可以定义”的工作。例如：

> 完成一个能在指定模拟器启动、能完整玩完一局，并通过验收清单的最小版本。

一个好的 Goal 应该说明目标、完成证据、约束、允许使用的范围，以及遇到阻塞时何时停下。Goal 不是让 Codex 无限制地自己工作，而是把完成条件挂在当前任务上。[OpenAI 对 Codex Goals 的说明](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

### Queue 和 Steer：等待还是改变方向

如果 Codex 正在处理一项任务，下一条指令可以排队等待，也可以立即改变当前方向。

- **Queue**：让当前动作先完成，再处理下一条；
- **Steer**：任务进行中就改变方向。

修正明显错误时可以 Steer；只是想补充下一步时，通常 Queue 更稳妥。

### Side chat：把旁支问题分出去

主任务负责推进项目，旁支问题负责解释和调查。例如主任务正在修改游戏逻辑，你可以用 side chat 问“为什么选择这个架构”“这个错误是什么意思”，避免把主线变成一串互不相关的问题。

### Compact：压缩过长的上下文

长期对话会变长。Compact 的作用是把已经完成、仍然重要和下一步需要的信息压缩成较短的工作上下文。它不是删除项目文件，也不是把所有历史变成永久记忆。

可以把这几种方式理解成一套控制杆：Prompt 推动下一步，Plan 讨论路径，Goal 固定终点，Queue 和 Steer 管理节奏，Side chat 分离思路，Compact 保持上下文可用。

## 五、输入不只有文字

当 Codex 参与真实项目时，输入可能来自很多地方。

**文件**提供代码、需求、日志和配置；**图片**可以说明界面问题、错误提示或视觉参考；**语音**适合快速描述想法或讨论下一步；**终端输出**提供命令真实执行后的结果；**浏览器和屏幕上下文**让 Codex 观察网页或桌面状态。

这些输入的价值不同：文字主要表达意图，文件提供材料，日志提供证据，屏幕和浏览器提供当前状态。

### Computer Use：让模型操作界面

Computer Use 是一种界面操作能力。模型可以根据截图和工具结果，在受控的浏览器或桌面环境中执行鼠标、键盘等操作，用于填写表单、测试用户流程或操作应用。[Computer Use 官方说明](https://developers.openai.com/api/docs/guides/tools-computer-use)

它和“看见屏幕”不是一回事：

- 看见屏幕，是获得观察信息；
- Computer Use，是根据观察执行界面动作；
- 浏览器工具，是在特定网页环境中访问、检查或操作；
- 代码执行，是通过脚本调用 Playwright、PyAutoGUI 等工具完成动作。

操作真实账号、订单和数据时，权限和审批比“能不能点到按钮”更重要。

### Record & Replay：把操作示范变成可复用流程

Record & Replay 也不是普通录屏，更不是视频生成。

在符合条件的 Codex 桌面环境中，用户可以示范一次稳定、重复的电脑操作，让 Codex 把它转成可复用的 Skill。它适合“每周都要按同样步骤完成”的流程，例如打开系统、检查页面、导出数据或运行一套固定操作。

录制时，Codex 会观察完成流程所需要的操作和窗口内容。因此不要在录制中输入密码、私钥、支付信息或其他敏感数据；也不要把无关的桌面内容混进流程。当前可用性受系统、账户、地区和 Computer Use 条件限制，发布前需要再次查看官方说明。[Record & Replay 官方说明](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)

它和视频生成的区别很明确：

> 视频生成是在创造一段影像；Record & Replay 是在学习一套可以再次执行的电脑操作。

## 六、模型、工具、Skill、MCP、Plugin 和 Harness

这些词经常被放在一起，但它们不在同一层。

**模型**负责理解、推理和生成。不同模型可能在速度、长上下文、代码修改、视觉理解或复杂推理上有不同侧重，具体能力和可用范围需要按当前官方资料核对。

**工具**让模型接触外部世界，例如读取文件、运行终端、浏览网页、查看屏幕或调用 API。

**Skill**是一套可复用的工作方法。它把任务步骤、判断条件、输出要求和示例写下来，让模型在类似任务中按照稳定流程工作。一个 Skill 可以独立存在，也可以配合 MCP 工具。[OpenAI 对 Skills 的说明](https://developers.openai.com/plugins/build/skills)

**MCP**是一种连接外部数据和工具的方式。它可以让模型使用某个服务提供的查询或操作，但服务的权限、认证和数据边界仍由连接方控制。

**Plugin**可以把 Skill、MCP 服务器和其他资源打包，供 ChatGPT 或 Codex 使用。它是分发和组织能力的容器，不是一个更聪明的模型。

**Harness**可以理解为围绕模型搭建的执行框架：它负责组织上下文、工具、权限、循环、检查和停止条件。Codex 本身就是一种面向软件工作的 agent harness；用户也可以在自己的应用里搭建类似结构。

用小游戏举例：模型可以理解玩法，工具可以读写代码和运行测试，Skill 可以规定“怎样做一次移动端兼容检查”，MCP 可以连接任务管理或素材库，Plugin 可以把这些能力打包，Harness 则负责让它们按顺序协作。

但有工具不等于模型知道正确流程，有 Skill 也不等于资料已经核验。流程说明、实时数据和权限控制仍然是不同问题。

## 七、文字、代码、图片、视频和网站不是同一种交付物

同一个游戏项目，可能同时产生很多结果：

- 需求说明是文字；
- 游戏逻辑是代码；
- 角色和背景是图片；
- 宣传片是视频；
- 可预览的页面是 HTML 或网站；
- 可访问的地址是 URL；
- 后端服务的入口是 API 地址；
- 可以安装或提交的文件是构建产物。

它们不能使用同一套验收标准。

代码要看测试、构建和运行结果；图片要看尺寸、透明度、风格和授权；视频要看时长、画面、声音和编码；网站要看页面、交互、域名和访问权限；API 要看请求、响应、认证和错误处理。

Codex 可以负责组织这些文件、调用工具、编写代码和安排验证，但图片和视频往往由专门的生成模型或连接的工具完成。不要把“Codex 能协调一项工作”误解成“所有媒体都由 Codex 自己生成”。

同样要分清几个常见词：

- **网页**是一页可以在浏览器中打开的内容；
- **网站**是由多页、功能和资源组成的整体；
- **URL**是访问某个网页、文件或接口的地址；
- **API 地址**是程序与服务通信的入口；
- **预览链接**通常指测试环境中的访问地址；
- **部署产物**是构建后可以交付、上传或运行的文件。

如果要把小游戏交给别人试玩，提供一个本地预览地址，不等于已经部署成公开网站；生成一个网页，也不等于已经生成手机安装包。

## 八、权限和边界

Codex 能看到什么、能改什么、能不能访问网络，取决于当前工作空间、执行环境和授权。

最少要把以下权限分开考虑：

- 项目文件的读取和修改；
- 终端命令的运行；
- 网络和第三方服务访问；
- 浏览器中的登录状态；
- 云服务、数据库和对象存储；
- GitHub 或其他代码托管平台；
- 发布、支付和真实用户数据。

读取项目目录和删除整个磁盘不是一个级别；运行测试和执行线上迁移也不是一个级别。

密钥、SSH 私钥、支付凭证、客户资料和生产数据库，不应该直接写进提示词、公开仓库、录制过程或截图。对真实账号和线上环境的操作，应当保留人工审批、日志和回滚办法。

还要区分三种边界：

**事实边界**：当前模型、功能、价格、套餐、地区和权限，需要查官方资料，不能凭旧记忆判断。

**验证边界**：没有运行过、测试过或复现过的结果，不能只因为 Codex 说“完成”就视为完成。

**责任边界**：Codex 可以写代码、整理证据、提出方案，但产品取舍、版权确认、安全风险、账号责任和发布承诺仍由人承担。

## 九、把这张地图放回小游戏项目

现在可以把整个系统放回最初的例子：

| 当前问题 | 可以使用的入口或能力 | 应留下的结果 |
| --- | --- | --- |
| 先把模糊想法说清楚 | ChatGPT / Work | 目标、未知问题、初步方案 |
| 选择技术路线 | Codex Plan | 方案比较、风险和推荐路径 |
| 修改和运行代码 | 桌面 App / CLI / IDE / 本地工作区 | 文件变更、日志、测试结果 |
| 把不同实验隔离开 | Git 仓库 / worktree | 独立修改和可回滚版本 |
| 让工作持续推进 | Goal / Queue / Side chat / Compact | 当前状态、下一步和阻塞点 |
| 查看远程进度 | Cloud / Remote | 任务状态、审阅结果和批准记录 |
| 操作网页或桌面 | Browser / Computer Use | 截图、操作结果和复现记录 |
| 把重复操作变成流程 | Record & Replay / Skill | 可复用的工作步骤 |
| 交付给用户 | 构建、预览、网站或安装包 | URL、构建产物和验收记录 |

这样看，Codex 不是一个孤立的“代码生成器”。它更像一套围绕工作环境运行的协作系统：模型负责理解和推理，工具负责接触现场，工作空间和权限规定边界，任务和 Goal 维持方向，测试和产物提供证据。

## 十、第一条系统级输入

如果现在真的要开始这个游戏项目，第一条消息可以这样写：

> 我想做一款最终可以在手机上运行的简单 2D 游戏，目前没有编程经验，也没有确定技术栈。
>
> 这一轮先不要写代码，也不要创建项目。请先帮我建立工作地图：
>
> 1. 说明这个目标需要哪些阶段，从想法、原型、可玩版本到手机运行分别要得到什么结果；
> 2. 列出我需要准备的材料、设备、账号和权限；
> 3. 比较本地、Cloud 和 Remote 在这个项目中的适用范围；
> 4. 说明哪些工作适合普通提示，哪些适合 Plan，哪些适合 Goal；
> 5. 列出代码、图片、视频、网页和安装包各自的验收证据；
> 6. 标出哪些能力属于 Codex，哪些需要 ChatGPT、专门的生成模型、插件或外部服务；
> 7. 如果信息不足，最多提出 8 个必须由我决定的问题。
>
> 输出分为：工作地图、已知条件、未知问题、方案比较、推荐路径、权限与风险、下一步。不要把假设写成已经确认的事实。

这条输入的作用不是让 Codex 立即写出一款游戏，而是让它先把系统、路径和缺口摆到桌面上。

复杂工作真正开始的标志，也不是生成了第一段代码，而是已经知道：目标是什么，材料在哪里，谁在什么环境中执行，哪些动作需要授权，什么证据可以证明完成，遇到什么情况必须停下来问人。

下一篇再进入提示词本身：怎样让 AI 先帮你澄清问题、发现工作流、拆分任务，并把一条模糊想法变成可以执行和验收的协作协议。
