# 六篇顺序审计

日期：2026-10-03

## 旧问题

v2 按“产品地图、提示词、可复用工作流、身份、基础设施、案例”排列。这样会让 GitHub、网站、云服务和提示词在多篇重复出现；第六篇又重新讲一次前五篇，像第二套教程。

## 新顺序

1. **认识系统**：先知道 Codex 在哪里工作，以及有哪些边界。
2. **提出任务**：在不知道流程时，先让 AI 帮忙澄清和计划。
3. **建立项目**：把代码、规则、计划、版本和工具放进稳定上下文。
4. **推进项目**：用循环完成代码、多媒体、工具调用、测试和审阅。
5. **交付产品**：把成果构建、部署、接入数据与网络，让用户能够访问。
6. **长期运营**：处理反馈、监控、评估、成本、自动化、治理和复盘。

## 避免重复的规则

- GitHub 在第三篇完整解释；第四篇只使用它；第五篇只讲它如何接入构建发布；第六篇只讲维护和版本运营。
- 网站、云服务、域名和 URL 在第五篇完整解释；第四篇只准备前端/原型；第六篇只处理上线后的观测和迭代。
- 提示词在第二篇完整解释；第三篇只讲如何把稳定提示词沉淀成规则文件或 Skill；第四篇只展示阶段提示；第五篇只讲部署任务提示；第六篇只讲维护和复盘提示。
- 游戏案例从第一篇开始，每篇只推进一个阶段；第六篇不重新教学，而是回顾决策、证据和交接。
- Skills、MCP、Harness 在第三篇完整解释；第四篇使用它们；第六篇讨论版本、评估和治理。
