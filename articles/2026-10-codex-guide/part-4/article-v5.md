# 你发出一句话后，Codex 背后发生了什么？

> 标题候选｜第四篇完整纯文字稿 v5｜2026-10-22｜待审阅

让 Codex 做一份报告，最后收到十页文字，和收到一个可以看图、比较、筛选的页面，是两种很不一样的体验。

前者把资料交给了你，后者还帮你把资料之间的关系摆了出来。如果下一步是选产品、定方案，后一种形式往往更有用。但如果报告还在反复修改观点，简单的文字底稿可能更省事。

选哪一种，影响的不只是外观，还有这项工作要来回多少次、你还要接手多少事。

与 Codex 合作，也有类似的选择：哪些信息应该交给它，哪些方法应该由它寻找；哪些事情适合用程序处理，哪些结果需要人来判断；最后交付什么，才能让接下来的工作更容易。

理解它背后怎么工作，目的就是把这些选择做得更好。人的已有认识要交接，寻找办法和实际执行的工作要让它承担，成果则要做成人容易理解和使用的样子。

## 一、把你知道的交给它，让它补上你不知道的

你掌握的背景、经验和资源，值得告诉 Codex；你不懂的专业方法，应当由它调查和推荐。

比如，一家小公司准备做骑车通勤用的雨衣，想请 Codex 调研竞品。下面用这个假设场景，看看信息怎样影响它的工作。

只说“做一份雨衣市场调研”，它可能从市场规模、品牌和价格讲起。这些内容未必错，却可能离眼前的决策很远。

负责人实际上已经知道：目标顾客每天骑车上下班；收到的反馈集中在背包淋湿、穿着闷热、收纳不便；这次调研是为了决定第一款产品先解决哪个问题。过去的报告罗列过许多品牌，却没有把这些差异比较清楚。

这些信息一旦交接，调查就有了重点。它需要看的不只是售价，还包括背包覆盖方式、透气设计、收纳体积，以及用户对这些设计的实际评价。

原因很直接：Codex 根据当前能看到的信息判断请求的意思。它可以推测通常的市场调研包括什么，却无法凭空知道这家公司收到过哪些反馈、已经试过什么、正准备做哪个决定。缺少这些事实时，它可能用一个看似合理的通用答案填补空白。

这里需要的不是把所有资料一股脑塞进去，而是把会改变判断的资料交给它。反馈记录比一句“要深入”更具体，过去报告及其不足也比一句“不要泛泛而谈”更有帮助。

再往前一步，负责人可能找到一个 GitHub 项目，据说能整理电商评价。把这个线索交给 Codex，它就多了一条值得调查的路。

但接下来应由它判断：这个项目是负责取得评价，还是只处理已经下载好的文件？适用于哪些网站？能否保留原始出处？整理出的分类，能不能回答这次的问题？一个项目名称并不能代替这些检查。

这也是“知道有工具”和“用好工具”的区别。它需要阅读说明，判断用途，再决定是否采用。现成的工作指引和处理脚本，也是在这些步骤中发挥作用，而不是提到名字就自动生效。

如果负责人根本不知道这个项目，也不应该先去学会整套数据处理方法，才有资格交办调研。Codex 应当主动检查可以怎样获得资料、怎样整理，哪些办法值得用。如果没有足够可靠的评价来源，就说明缺口，而不是把零散印象写成消费者结论。

因此，信息交接和方法探索可以这样分工：人把独有的事实、经验和资源带进来；AI 负责把未知部分查清，并提出可行的做法。遇到业务取舍再找人判断，不必让人逐个提醒它“现在去查资料”“接着做计算”。

## 二、它先做一个动作，再根据结果决定下一步

Codex 真正做事时，会在“判断下一步”和“执行这一步”之间来回切换。

假设你交给它几个月的订单文件，让它找出哪些商品拖累了销售。它不能只凭文件名写分析，需要先读取里面的数据。

开始时，它可能先查看各个文件有哪些列，以及几行样本。工具把读取结果返回后，它才知道：这里有订单金额、商品名称、订单状态和退款金额，而且不同月份的列名还不完全相同。

接下来，它可以写一段程序，把对应的列统一起来，按商品计算销售额，再比较月份之间的变化。

这时可能出现一个意外：合并后，同一笔订单出现了多次。

如果直接把重复记录删掉，也可能删错。同一订单里买了两种商品，分成两行是正常的；同一订单在相邻两个月的导出文件里各出现一次，则可能真的被重复计算了。

它需要回头查看订单编号、商品明细和文件的来源说明，确认每一行究竟代表什么，再调整计算方式。如果资料里没有解释清楚，就需要向人确认，而不是擅自决定。

调整之后再运行，得到的结果才有继续核查的价值。它还应检查：汇总金额能否与原始记录对应？退款是否重复扣除了？被判断为“销售下降”的商品，是销量减少，还是退款增加？

这段过程里，模型和工具各做了一部分工作。模型判断要读什么、怎样处理、哪里可能有问题；工具实际读取文件、运行程序，并把数据或错误返回。Codex 的运行系统把这些步骤连接起来，一次请求就可以继续推进许多动作。[OpenAI 对 Codex 执行机制的说明](https://developers.openai.com/blog/codex-as-a-platform)介绍了这种连接模型、工具和执行结果的工作方式。

所以，它并不一定在收到请求的那一刻，就已经想好了全部步骤。读到新资料、遇到错误、发现异常之后，后面的做法可能需要改变。

这也解释了一个容易误判的地方：一份分析写得流畅，不代表它已经读过文件；出现了精确数字，也不代表计算一定正确。判断工作是否完成，要看实际做过什么，以及结果能否对照。

程序能帮助检查，却也可能把错误的规则执行得很整齐。比如，公司把“销售额”定义为扣除退款后的实收金额，如果 Codex 按下单金额统计，程序运行成功也没有解决业务问题。

人需要补充的是这些业务含义。读取、计算、发现异常后的追查，以及必要的核对，则应由它主动承担。合作效率提高，来自这种分工，而不是把每一个动作重新口述给它。

## 三、适合批量处理的事，让它用机器的办法做

Codex 可以操作界面，也可以直接调用工具、运行程序。对于规则明确、需要重复处理的工作，通常应优先考虑后面这条路。

继续看订单整理。人工处理时，可能需要逐个打开表格，复制到总表，统一商品名称，再计算退款后的金额。

如果照着这套动作让 AI 操作，它也得在多个窗口和表格之间切换。但同一件事可以换一种做法：写一个处理程序，一次读入这些文件，按照规则整理，再输出新的工作簿。

程序还可以把需要人确认的记录单独列出来。例如，“城市通勤雨衣”和“通勤雨衣标准款”是否属于同一商品，不能只看名称相似就合并。确认一次后，这条对应关系就可以用于下一批数据。

这里，代码是一件临时工作工具。最终交付仍然可以是表格和分析，用户不需要阅读代码。下个月收到新文件时，还可以沿用已经检查过的处理办法，减少重复劳动。

终端在这种工作里经常出现。可以把它理解为一个用文字发出操作指令、接收结果的入口。Codex 通过它启动程序，看到处理了多少条数据、生成了哪些文件，或者具体在哪里出错，再继续处理。

它适合的，是能清楚说出输入、操作和输出的工作。不需要先把每一步变成人看得见的按钮和窗口，机器也能执行并获得反馈。

Codex 使用者 Peter Steinberger 在一篇[实践文章](https://steipete.me/posts/2025/shipping-at-inference-speed)中，也采用了先建立可直接调用的命令行核心、再扩展其他形式的做法，让 AI 能直接使用和核查它。

有现成的专用工具时，也没有必要凡事重写程序。需要观察真实网页的显示效果，或者某项操作只能在界面里完成时，浏览器和界面操作就有价值。

判断标准是这条路能否把事做清楚、做完整，并便于检查。交办时说清输入、结果和关键业务规则，具体采用哪种处理方式，应当让 Codex 调查和选择。这样才用到了它与机器直接协作的能力。

## 四、交付物不只是一份文档，也可以是一种新的工作方式

先想成果拿来做什么，再决定交付什么。读结论、改内容、算数据、观察空间，适合的表达并不一样。

这也意味着，可以让 Codex 帮你试一试过去没有做过的东西。没有三维建模经验，也可以从一个简单的桌面收纳架开始：先看立体形状，换几个角度，再调整抽屉的位置和大小。有了对应的建模工具，还可以继续保留模型和尺寸图。原来只能用文字描述的想法，就有了可以观察和修改的对象。

第一次尝试的意义，不一定是马上做出专业作品，而是发现一种以前没有用过的思考办法。有些问题摆成表格才容易比较，有些变化做成动画才容易理解，有些空间关系需要转动模型才能看清。

Codex 可以帮助连接这些不同形式。它可以先把资料整理成数据，再通过程序或制作工具生成图表、页面、文档和模型。中间方便处理的形式，与最后方便人使用的形式，不必相同。

比如，一份竞品研究可以先用 CSV 保存产品记录；一个产品对应多条评价、多个来源时，也可以用 JSON 保存这些关系。数据整理好之后，再按用途制作成果：需要测算价格，就做工作簿；需要开会讲结论，就做演示稿；需要自己筛选和比较，就做交互页面。

其中，HTML 是值得主动尝试的一种选择。假设二十款雨衣已经整理完毕，下一步要选出值得深入研究的五款。长文需要读者来回翻找、记住差异；页面可以把图片与参数并排摆出，按背包覆盖、收纳体积等条件筛选，再勾选保留项。它减少的是比较和反馈的工作量。

HTML 用文本描述页面的结构和样式，浏览器把它显示出来，需要时再加入交互。Codex 可以修改代码、预览页面，再调整布局和功能。页面还可以把勾选结果导出成文件，交回 AI 继续处理；普通页面里的点击不会自动被 AI 知道，需要实际保存或回传。

Thariq Shihipar 的[实践文章](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html)展示了用这类界面呈现信息、收集人的选择的做法。对于需要看图、比较和筛选的任务，这比默认交一篇长文更值得考虑。如果目的是反复修改论述，简单文字底稿更方便；需要持续计算，就保留工作簿的公式；需要别人继续编辑演示材料，就交可编辑的演示稿。

下面这张表可以当作一份尝试清单。遇到熟悉的工作，也可以看看：换一种交付形式，会不会更容易理解、更方便使用？具体制作仍需要相应的软件、工具和检查。

| 既有系统中的修改 | 改好原有文档、更新表格、修复应用、整理资料库 | 已保存的修改、代码差异、PR、系统内更新 |

这里的“自动化流程”，可以用一个简单例子理解：这次让 Codex 整理订单，拿到的是一份整理后的表格；也可以让它留下一个处理程序，以后把新订单放进去，再运行一次，就能按同样的规则生成结果。这是批处理。如果还配置了定时运行，就可以每周五生成一份周报；如果配置成发现新文件就开始，则是按事件触发。程序负责具体处理，触发机制决定什么时候开始，不是 AI 凭空记住了下周还要做事。

因此，“交付一个程序”和“已经配置好自动运行”是不同的完成状态。完整的自动化交付，需要说明从哪里取输入、何时运行、结果存到哪里，以及失败时怎样发现。这里只认识这种交付形式，持续运行和维护留到后面讨论。

另一个需要分清的关系是：Blender 是制作工具，三维是表达方式。通过 Blender 可以交付可编辑工程，也可以输出模型、渲染图或动画。同一个成果，交给人看、交给人操作、交给人继续修改，需要的文件可能不同。

所以，尝试一种新形式时，也可以继续问：能否转动它、修改它、换一组数据再生成？最终交付可以是一组成品、数据和源文件，但应按下一步用途选择，而不是每次生成所有版本。

评价这些选择，要把制作、检查、阅读和修改一起计算。精美页面未必比简单文字生成得快，但如果它让比较更清楚、反馈更省力，整项工作仍可能更顺畅。

理解 Codex 的工作方式，最后会改变交办工作的方式：把会影响判断的信息带给它，让它选择合适的方法去执行，用实际结果推动下一步，再把成果做成人能够判断和使用的形式。

更好的合作，应当让你少接手一些查找、搬运、计算和转换的工作，也让你更容易看清结果，然后作出决定。
