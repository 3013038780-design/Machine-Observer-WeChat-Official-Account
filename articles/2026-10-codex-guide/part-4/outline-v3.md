# 第四篇写作逻辑与具体大纲 v3

日期：2026-10-22。状态：完成范围研究后的候选大纲，待用户审核；不扩写正文，不制作 HTML 或配图。研究见 research/mechanisms-and-capabilities-v3.md。

## 文章命题

Codex 怎样把人的请求转化为实际成果，理解这个过程后，怎样把工作交给它，减少逐步提醒与返工。

读者收益：能判断该提供哪些材料、方法与工具选择该由谁承担、什么路径适合所需成果，以及交付是否经过必要检查。评价效率包含人的时间，不只看回答速度。

核心判断：一次交付经过信息获取、任务判断、能力选择、工具执行和结果检查；任何环节断开都会影响成果。人说明目的、用途和重要取舍，AI 主动补专业方法、选择路径并执行；在决定方向或关键样本处进行必要对齐，避免由人逐条编排动作。

## 系列分工

第一篇认识产品与功能；第二篇共同判断与沟通；第三篇保存项目、规则与可复用能力；第四篇解释系统怎样利用这些信息与能力实际工作；第五篇对外发布与使用；第六篇长期运营与改进。

本篇不重新教提示词模板、GitHub、Skill 目录与安装，不恢复“完成一轮开发”的操作手册，不单列长期状态和泛泛反馈章节。

## 标题候选

推荐入口：《你发出一句话后，Codex 背后发生了什么？》

描述候选：它怎样理解任务、选择工具、制作成果；看懂这个过程，减少逐步提醒和反复修改。

“黑箱”可作为引入，不将文章承诺写成披露模型完整内部思维。正文使用客观中文，不写作者第一人称经验。

## 正文组织

按一项委托从进入系统到形成可用成果的因果过程展开，四节足够。每节解释机制、它导致的行为和可据此采取的合作办法；这些内容写成连贯过程，不机械分成三列卡片。

开头：从“一个任务为什么有时能一口气交付，有时却要逐项提醒”进入。指出需要观察的不仅是对话措辞，还有材料、任务判断、工具条件与成果制作方式。既不默认所有失败是用户表达问题，也不先把责任推给权限。

开头用短段建立整体关系：请求与材料进入上下文 → 模型决定下一步 → 工具执行并返回 → 判断与修正 → 产生成果并核查。模型、运行系统、工具和环境只在图/段落中定位，不重讲第一、三篇产品词典。

## 01 收到请求时，它到底知道什么

本节问题：人的完整意图、当前可见材料和模型已有知识，怎样共同影响任务理解？

展开顺序：

1. 人的一句话只表达了部分意图。背景、对话、适用规则、已读取材料和工具结果帮助解释，但系统不能自动获得人的全部经验与期待。
2. 把“文件就在电脑里”拆开：当前环境能不能访问，是否找到正确版本，内容是否实际进入工作。云端与本地资料也有边界。
3. 解释信息呈现：抽出的文字、表格原始数据、页面图像各自保留不同信息。既需要内容，也可能需要视觉与结构，不能笼统建议全改成文本。
4. 把长对话放在此处简短解释：上下文有容量，系统会做整理/压缩；跨会话记忆有条件。必要决定需能从有效材料恢复，但不重新教第三篇的状态文件。

合作落点：人提供成果用途、重要约束及有效材料入口；AI 主动查找、核对、提取和补充信息。资料少时先调查，不逼用户列全专业流程；资料多时先定位，不全量贴进对话。

必要例子：分析销量时，数据文件、统计口径和展示截图各自能帮助判断什么；不能仅凭一张图推定掌握全部明细。教学示例不写成实测。

与下一节关系：获得信息仍不足以完成任务，还需要选择怎样做。

## 02 它怎样决定下一步，为什么有些能力没有被用上

本节问题：模型怎样从目的形成任务与方法，当前能力怎样被发现和选中？

展开顺序：

1. 由用途决定工作深度：回答知识问题、调查并推荐、执行制作，需要不同工作；人的模糊要求会引入假设，关键假设需要验证。
2. 解释方法选择：先确定支撑判断所需证据，再决定找什么资料、是否需要计算、批量采集或额外服务。专业方法应由 AI 主动调查推荐。
3. 引入可观察的能力发现：Skill 通常先见名称与用途，再按需读取完整流程；工具也有定义、适用条件，部分集成会动态加载。已安装不代表本轮已调用。第三篇概念仅作引用。
4. 具体诊断能力未用上的情况：方法没选到、能力没发现、环境或登录条件不具备、有明确触发/授权要求、执行失败。不把这些全部称为“必须让用户提醒”。
5. 用子代理作一个有明确证据的例子：当前本地 Codex 文档有直接请求或项目/技能指令触发的约定；这不意味着每种工具都要点名。独立任务可分工，依赖很强的任务不必拆给多个代理。

合作落点：把目的、范围与决定权交代清楚，让 AI 主动补方法、比较路径并执行。对反复漏用的固定工作，核查能力描述与触发安排；普通调查和工具选择不能逐项退回给人。需要澄清时聚焦会改变方案的选择，其他专业细节由 AI 研究后推荐。

必要例子：市场进入调研，先判断官方数据、接口或公开网页是否足够，才决定抓取；不是先下载工具再寻找用途。特定未确认产品名不进入事实陈述。

与下一节关系：选中了方法和工具，动作究竟怎样发生，结果怎样影响后续工作？

## 03 它真正动手时，模型、代码和工具怎样接力

本节问题：为什么写代码和使用终端能用于非编程任务？系统又怎样通过结果发现失败？

展开顺序：

1. 展开一次调用：模型提出动作与参数，运行系统按条件执行，工具返回数据/错误/状态，模型据此继续或换路径。一次用户请求可包含多次调用，不是先在脑中算好全部过程再打印结果。
2. 解释临时工作代码：程序处理查找、去重、汇总、生成与校验，模型负责理解目标和组织工作；计算结果要从执行获得，不能把语言生成当精确计算引擎。
3. 比较操作路径：直接工具/API 提供明确对象与结果；命令与脚本便于组合、批量和重复；浏览器/Computer Use 处理界面和实际视觉。终端是重要途径，但不存在通用的“最舒服所以永远最快”。
4. 数据多时可以先通过程序筛选、合并、校验，返回必要结果；独立操作可并行，顺序依赖则不能强行并行。不要把 API 具体配置写成所有客户端同一实现。
5. 把纠错放进循环：工具成功与业务正确不同，错误需要真实返回、保留并处理。检查是获取新证据；钩子仅作为可触发已有检查的机制，配置留后续。
6. 说明速度由哪些环节影响：模型推理、工具轮次、外部等待、串行依赖和重试；换快模式不自动解决错误方法或缺失数据。不展开型号、价格和倍率。

合作落点：让 AI 自己选择并说明关键执行路径，完成合理范围内的调查、运行和检查；人无需规定每条命令。给它可执行与可观察的工作条件；只有真正涉及人的取舍、权限或外部后果时才停下来决定。

必要例子：一批数据从读取、程序去重汇总，到发现口径异常并修正；计算不是靠措辞更严谨完成。与 UI 操作作简短对照，不做工具安装教程。

与下一节关系：执行能力只是手段，最终应按人的使用方式组织成果。

## 04 从“能生成”到“能使用”，一份成果怎样做出来

本节问题：Codex 可以通过哪些路径交付成果，这些路径怎样影响速度、质量、可编辑性和下一次修改？

展开顺序：

1. 先按制作路径解释能力，而不是按扩展名排名：直接生成文字/结构化内容；用程序计算和制作文件；调用专用媒体工具；编辑已有应用/在线对象；构建可执行或交互成果。这是编辑归纳，允许交叉。
2. 对应覆盖文章与研究报告、结构化数据与数据库脚本、统计图与矢量图、文档/表格/演示/PDF、网页/应用项目与交互工具。媒体要看具体接入，不把缺少实测的视频/配音作为默认能力。
3. 区分模型便于处理的中间表示与人的最终交付物。MD/HTML/JSON/代码可用于组织和制作，但不赋予它们普遍质量优势；Office 文件也可以直接通过相应对象模型编辑，不必先转成网页。
4. 说明源数据、制作脚本、可编辑文件与发布/展示版本之间的关系。内容一改，哪些可以从源头更新并重生成，哪些在原文件中修改更合适；不得承诺格式转换无损。
5. 以两种制作过程说明检查：表格需要核对数据与公式并重算；文档/演示需要查看实际渲染，原生编辑与兼容要求需要对应环境检查。网页版面也需要浏览器检查。生成文件成功不足以证明最终可用。
6. 比较静态交付与交互成果：一份需要持续筛选的数据，也许需要可筛选表格或交互工具；需要汇报和后续编辑时，演示文件可能更适合。AI 应提出用途导向的推荐，并遵守明确指定格式。

合作落点：说明受众、使用场合、最终格式与目的地、可编辑/更新要求和重要模板；AI 选制作工具并负责检查。关键结构或代表性样本先验证，再批量制作，不把每一页都变成人工审批。最终按请求交付，不用一堆中间文件让人自行拼装。

必要例子：同一份销售分析的原始数据、计算过程、工作簿图表与汇报材料如何衔接；用于解释，不将所有成果写成每项任务都必需。公众号 MD/HTML 只作为短补例，不再占据整节。

结尾：人应主要提供 AI 无法自行决定的目的、偏好与取舍，AI 应承担调查方法、选择工具、执行与核查。更有效的委托建立在对制作过程的理解上；不能把所有不足补成用户越来越长的指令。

## 具体取舍

- 4 节按理解、决策、行动、成果递进；上下文整理并入第 01 节，多代理触发并入第 02 节，反馈纠错并入第 03 节，不恢复 v2 后两节的泛泛建议。
- 预计正文 4500—5500 字，执行机制与成果制作约占一半；有用的解释过程优先于术语数量。配置、参数、价格及模型比较不进入主文。
- 不强制一个故事贯穿全文，用少量有输入/处理/输出的例子解释具体关系，不堆媒介百科。
- 不重新写前三篇，不提前展开第五篇的部署/域名或第六篇的自动化治理。
- 本轮没有定量效率实测，不给“快几倍”的结论；不声称终端/英文/某文件格式天然最优。
- “完整思考模式”限定为公开机制、可观察动作及明确标注的解释推断，不披露或编造模型完整私有推理。

## 拟稿前待做的最小验证

选择一份可公开的小数据，记录一次从文件读取、工具计算到成果生成与检查的链条，保留实际输入、关键调用与结果。它用于让机制有具体落点，不用于宣称整体性能；不因缺少实作而伪造截图或运行记录。按用户确认后的大纲决定是否需要制作演示性文件。
