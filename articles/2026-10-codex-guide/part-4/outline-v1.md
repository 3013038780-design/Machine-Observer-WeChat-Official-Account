# 第四篇建议大纲 v1

日期：2026-10-22。历史方案，用户已否定；不作为正文依据。最新候选结构见 outline-v2.md。

## 写作逻辑

第三篇已经把仓库、规则、技能、工具连接和运行框架装起来，并以“一次真实任务怎样从 Issue 进入分支，经过工具、测试和 Review”预告第四篇。本篇兑现这份预告：展示动作、依据、反馈与下一步，读者不必先学会读完整代码。

核心判断：持续协作要围绕一个可验证的小成果推进；AI 的解释、工具返回、运行结果、测试和人的实际试用承担不同证明责任。

建议开头：Codex 报告“已完成”，打开预览却发现重开后分数没清零。它到底完成了哪一步，用户又该检查什么？这是候选示例，不能伪装成真实测试。

正文按“接任务 → 做出成果 → 操作工具 → 分工 → 验证 → 恢复 → 交接”推进。建议约 3500—4500 字，前三节保持紧凑，验证和恢复给足解释空间。

## 01 接下任务，先确认现在从哪里开始

- 核心问题：同一个需求，为什么会改错版本、重复旧方案或顺手扩大范围？
- 准备给出的答案：先读取项目规则、运行说明和当前状态，检查工作目录及已有改动，实际运行当前版本；把本轮目标与检查条件说清。环境本来就坏了，应先区分原有问题与本轮引入的问题。
- 必要示例：Issue 写“重开有问题”，先复现具体步骤，确认是分数未清零还是关卡状态未恢复，再确定本轮范围。Issue 是任务记录的一种形式，普通明确请求也可进入流程。
- 人的作用：补充期望行为，决定涉及玩法变化的取舍；无需先替 AI 指定代码文件。
- 与前篇的关系：调用第三篇留下的材料，不重新讲文件名和 Git 教程。

## 02 先做出一小段能使用的成果

- 核心问题：怎样避免一次生成整套产品，直到最后才发现方向不对？
- 准备给出的答案：新项目先完成一条端到端的可用路径，已有项目先完成最小有效改动。说明“垂直切片”：例如开始、操作、计分、结束、重开能连起来；不是先把全部页面画完才接逻辑。
- 必要示例：修复重开流程时，检查状态初始化与界面刷新如何配合；随后才考虑扩大功能。
- 多媒介放在同一实现过程：代码控制行为，HTML/CSS 呈现界面，图片提供视觉素材，录屏呈现操作过程。图片需要真正接入项目并检查尺寸、透明背景、清晰度和触控遮挡；素材来源与使用条件留下记录。
- 视频只作必要区分：录屏能记录一次运行；操作回放复现指定动作；生成式宣传视频不证明产品已经具备画面中的功能。当前工具及回放能力须按环境核实，不承诺统一入口。
- 衔接：成果要启动、预览和操作，接着解释 AI 怎样动手。

## 03 让工具动手，也要看工具返回了什么

- 核心问题：终端、浏览器、Computer Use 和连接工具分别在做什么？
- 准备给出的答案：按本轮动作解释选择：文件工具修改内容，终端运行程序和测试，浏览器观察页面与操作流程，外部连接读取任务材料或提交变更。有直接工具且能完成任务时优先使用；需要界面操作时再用相应能力。
- 必要示例：终端显示启动成功后，浏览器打开页面并执行开始、结束、重开；页面出现不代表交互通过。网页源文件、浏览器实际页面和截图提供不同证据。
- 观察与副作用：读资料、改本地文件、向外部系统写入要分别说明结果。网站、文档中的文字是待处理材料，不能自行变成新的操作授权。沿用项目已有权限和决定边界。
- 衔接：工具输出和日志很多，如何分配调查与检查，避免主对话失去重点？

## 04 什么时候需要另一个 AI 帮忙

- 核心问题：独立上下文、子代理和并行任务怎样分工，什么时候反而增加麻烦？
- 准备给出的答案：按明确问题分派可独立的调查或检查；给出版本、相关材料、目标、约束和交付要求。主任务保留重要决定并负责整合，不把所有日志塞回主对话。
- 必要示例：主任务修复重开问题，另一任务检查状态遗漏或复现边界条件。审阅者需要看到预期行为、实际改动和测试结果；若先给了它实现者结论，应意识到可能影响检查视角。
- 合并与责任：共享文件可能冲突，安排明确修改范围；需要同时修改时用隔离工作副本，合并后重新检查。独立上下文不等于独立事实来源，几个 AI 意见一致也不构成正确证明。
- 取舍：短任务、依赖很强的任务通常顺序完成更直接。正式正文按实际支持入口解释，不把 API 多代理能力套成所有桌面版本都有的功能。
- 衔接：分工完成后，要把结论还原成可核查证据。

## 05 “运行了”“检查了”和“做对了”，分别凭什么判断

- 核心问题：用户不熟悉代码时，怎样验收而不只听 AI 说完成？
- 准备给出的答案：区分启动成功、自动化测试、浏览器操作、变更审阅与实际使用判断。分别检查程序能运行、规则符合预期、完整流程可用、改动没有明显遗漏、成果达到原目标。
- 必要示例：重开后分数清零、计时重置、多次重开不重复触发事件；随后检查原本正常的计分是否仍然正常，这就是回归检查。手机适配要说明模拟视口与真实设备实测的差别。
- Review 的实际内容：改了什么、为什么改、是否超出范围、哪条路径和测试支持结论、还有哪些缺口。AI 审阅意见也要核对，不当作自动验收或自动合并许可。
- 检查证据：实际命令与结果、关键操作步骤、必要截图或录屏、相关文件差异。不要求每轮把所有媒介都交一遍；不能用截图证明所有交互正确，不能把未执行检查写成通过。
- 钩子作为小段解释：在特定事件前后调用处理程序，可以接已有检查，但事件是否触发、脚本是否执行、结果是否被处理必须实际验证。钩子不是一句文字要求，也不是所有动作的完整权限屏障；具体配置留附录或后续实作。
- 衔接：检查失败不是流程终点，需要依据失败类型决定下一步。

## 06 出错以后，先定位，再决定怎么继续

- 核心问题：为什么反复说“继续修”可能让项目越来越乱？
- 准备给出的答案：保留报错和复现步骤，区分环境问题、实现错误、资料缺失与目标变化；一次验证一个主要假设。不要通过删测试、改验收标准掩盖失败。
- 必要示例：修好了分数，却导致重开后重复计分。回看新旧差异，检查事件绑定，修复后重新走原流程。必要时回到可用版本，保留调查记录。
- 中断恢复：先核对真实文件、运行进程、Git 与远端状态，再从已验证的节点继续。外部写入结果不明确时先查是否已成功，避免重复创建或提交。
- 模式与人的决定：路径仍成立则继续执行；关键假设失效则重新规划；新增范围、费用或外部影响触及既有边界时让人决定。Plan/Goal 只承接第一篇，不重新介绍界面。
- 衔接：修好以后还需要留下下一轮能接手的状态。

## 07 这一轮结束，要留下什么

- 核心问题：怎样让人可以接受成果，让下一次对话可以接着工作？
- 准备给出的答案：交代本轮目标、实际改动、已完成检查与结果、未检查或未解决事项、下一步及所需决定；更新项目状态，按约定提交并核对远端同步。
- 必要示例：PR 对照改动与检查证据，用户按规则决定是否合并；更新 docs/status.md 时区分“计划”“已修改”“已验证”。没有采用 PR 的小任务也应保留同样可检查的信息。
- 收束：本篇结束在一轮可审阅成果，下一篇再解决怎样把它交给真实用户使用。

## 与旧框架的调整对照

保留代码、多媒介、工具、独立上下文、多代理、Review、测试、失败恢复与模式判断的覆盖，改变的是组织轴：从功能目录调整为一轮工作。

- 图片、HTML、视频从各自单列章节收进第 02 节，避免变成媒介工具教程。
- 浏览器操作在第 03 节解释动作，第 05 节解释证据，二者不重复定义。
- 根据 series-placement-v1.md 补回上下文交接与钩子的职责，但不展开完整自动化配置。
- trace、grader、评估数据集与长期自动化留第六篇。本篇先解释普通运行日志和失败记录，不要求读者搭建智能体评估系统。
- 第三篇只引用文件和机制，第五篇负责发布与访问，第六篇负责长期改进。

本次调整依据：第三篇最新用户稿已经完整解释工具与机制，并承诺第四篇展示真实任务；第二篇最新稿也已承担协作判断与工作流形成。本篇需要补足执行细节和验收证据，而不是再解释一遍系统组成。

## 正式写作前的研究与实作

1. 选定一个小型可运行示例及明确故障，记录初始版本。真实实作前不使用“实测”“已验证”等说法。
2. 保存复现、最小改动、失败、修复、回归和最终差异。若演示多代理或钩子，应实际运行，并记录输入、输出和未覆盖范围。
3. 再核对所用桌面/CLI/云环境的工具与功能支持。资料研究不等于本机功能验证。
4. 若无适合展示的真实项目，正文明确采用教学示例，不能杜撰 Issue、测试截图或执行记录。
