# 复杂项目，不能只靠聊天

和 Codex 一起工作 · 第三篇

和 AI 一起做几周、几个月的项目，文件放哪里，改坏了怎么回来，重复的工作怎样少交代几遍？把这些事情安排好，项目才更容易一直做下去。

在同一个聊天里，AI 通常能接着做。问题出现在项目变长以后。

比如，一个手机小游戏已经有了第一版。接下来还要加新玩法、修错误、换素材、适配手机、准备发布。此时，代码和素材开始分开，新的尝试和原来的版本混在一起，讨论过的方案散在聊天记录里。想让另一个任务帮忙检查，又不知道该给它哪些材料。

这时，问题不再是“AI 记不记得上一句话”，而是：

> **怎样让一项复杂工作有地方保存，有办法执行，有证据检查，也能在下一次继续？**

一条提示词负责提出这一次的要求。长期项目还需要一套能够承接工作的系统。

## 01 先给项目建立一个共同现场

最先需要解决的，是项目到底放在哪里。

做小游戏时，代码可能在电脑上的一个文件夹里，图片在另一个位置，需求写在聊天里，运行方法只记得大概，版本则靠“应该是上周那一份”。AI 可以在当前环境里帮忙，但这套工作很难交给另一个任务，也不容易回到一个确定的状态。

Git 和 GitHub 解决的是这类问题。

本地文件夹是实际工作的地方。Git 是版本管理工具；由它管理的项目及版本历史，组成一个 Git 仓库。GitHub 是托管和协作平台，可以保存远程仓库，并提供任务、权限和审阅功能。

保存文件、提交版本、同步到 GitHub，是三个不同动作。只有完成相应的提交和推送，远端才有这次变化。大型素材要另外安排存储，密钥、登录凭证和本地依赖目录也不能直接整包上传。

GitHub 还会把“谁可以参与”说清楚。个人账户适合个人项目；组织可以管理多个仓库、成员和权限。项目需要让别人查看、提交修改、审阅代码，还是只能看到公开内容，都应该在这里设置，而不是在聊天里含糊地约定。

项目开始修改以后，还需要知道：有什么问题要处理，这次改动是否应该进入正式版本。GitHub 把这段合作分成几个具体环节。

### Issue：把要做的事记成一条任务

Issue 是仓库里的问题或任务记录。它可以有标题、说明、负责人、评论和处理状态，也可以记录功能建议，不只用来报错。

比如，游戏的“重新开始”按钮失效了。建一条 Issue，写清怎样操作、原本应该发生什么、实际出了什么问题。之后的调查和修复都可以围绕这条记录进行。

为什么不只在聊天里说？因为这件事可能今天不处理，可能交给另一个人，也可能需要补充材料。Issue 让待处理的问题有明确位置，避免它被后面的对话盖过去。

### 分支：把一次修改和当前版本分开

分支是 Git 中一条有名字的版本路线。可以把主分支作为当前可用的版本，从这里建立“修复重开按钮”的分支，在这条路线上保存修改。

这样，修复还没完成时，不必把试验中的代码合并进主分支。检查通过后，再把这条分支的改动合并回去。提交则保存这条路线上的一个版本节点，用来比较变化或回到之前已记录的状态。

分支并不是文件夹副本。两个任务要同时工作，可以用 worktree 或独立克隆提供各自的工作目录；尚未提交的修改也要另外处理，不能以为创建分支后就自动保存了。[Git worktree 官方说明](https://git-scm.com/docs/git-worktree)

### Pull Request：请求把这批改动合并进去

按钮修好了，测试也跑过了，但代码目前还在修复分支上。怎样把它正式纳入主分支？可以创建一个 Pull Request，简称 PR，也就是合并请求。

它向目标仓库的维护者表达的是：**“请检查我这条分支上的改动，合适的话，把它合并到目标分支。”**可以由开发者发起，也可以让 Codex 在授权下创建。

这里不需要先执行一个叫“pull request”的拉取动作。Git 的 pull 命令是把远端变化取回并整合到本地；GitHub 的 Pull Request 是提出合并建议，两者不是同一个操作。

PR 页面把这次改动的说明、文件差异、测试结果和讨论放在一起。比较的是修复分支引入了哪些变化：删了什么、加了什么、修改了什么。它的价值是让这批改动在合并之前，有一个可以集中检查和讨论的地方。[GitHub PR 官方说明](https://docs.github.com/en/pull-requests/reference/pull-requests)

### Review：合并之前，检查这次改动

Review 是对 PR 中改动的审阅。目的不是比较谁的方案漂亮，而是检查：按钮是否真的修好，有没有误改计分，测试覆盖了什么，还有什么没验证。

为什么修完还要审阅？因为“完成了修改”不等于“改得正确”。AI 可能修好了按钮，却顺手改了其他功能；测试可能通过了，但没有覆盖手机上的操作。审阅帮助发现这些差别，再决定继续修改还是进入合并。

团队可以请同事或维护者审阅；个人项目可以自己检查，也可以请 AI 辅助看差异、核对测试和分析风险。自己检查不等同于 GitHub 中的他人批准，具体审批要求由仓库规则决定。

审阅者可以评论、要求修改或表示批准。**审阅提供检查意见，批准表示认可这批改动；真正纳入目标分支，还要完成合并。**最终由有合并权限的人，或符合仓库规则的自动流程完成合并。

一个人做的小项目，不必每次都创建 Issue 和 PR。但项目变长、需要并行尝试或多人接手时，把“待做任务、试验修改、合并提议、审阅意见”分别留下来，更容易知道现在该处理什么、哪些改动已经进入正式版本。

## 02 怎样让 AI 一直知道项目做到哪了？

仓库是为了做项目而建立的。接下来，设计、制作、检查和修改都要与 AI 一起完成。它需要持续知道：这个项目想做成什么样，你们已经决定了什么，实际做到了哪里，这次应该接着做什么。

同一个对话里的上下文能够帮助它继续，但讨论、计划和实际结果还要与项目文件对应起来。否则聊过的方案可能并没有实施，代码已经改变，记录却还停在上一轮。

### 开始时，把项目目的留下来

第二篇讨论出的方向，可以请 Codex 整理到项目材料中。你负责确认它是否准确理解了目的和重要取舍；具体文档由它根据讨论和现有文件整理。

比如，你想做一个手机小游戏，第一阶段只要能玩、能计分、能重新开始，暂时不做账号。可以这样说：

> 请根据我们已经确认的方向和现有项目，整理项目说明：为什么做、第一阶段做到什么程度、哪些事情暂不做，以及代码、素材和运行方法在哪里。已有文档先检查再更新，不重复创建；还没有决定的内容单独标出。

这类相对稳定的项目说明可以放在 README.md。它是仓库的说明入口，也可以供 AI 了解项目。[README 官方说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)

创建仓库时可以选择生成 README，项目模板或 Codex 也可能已经写好它。文件已有，就检查内容是否符合当前项目；没有，再按需要建立。无需你亲手填写，也没有固定条目数。[创建仓库说明](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository)

运行说明也要来自实际工程。例如，一个 Node.js 网页游戏可以记录：

```text
运行环境：项目要求的 Node.js 版本
安装依赖：npm ci（需有匹配的锁文件）
启动项目：npm run dev（需已定义该脚本）
运行测试：npm test（需已定义测试脚本）
配置方式：所需环境变量的名称和取得方式
```

让 Codex 核对项目后填写，并实际运行检查。依赖清单和锁文件随代码保存，真实密钥另外提供。说明过长时，拆到相关文档，README 保留入口即可。

### 做的过程中，留下决定和实际进展

项目说明回答“为什么做”，但你更常需要 AI 知道的是：“我们这几天一直在做什么？”

这需要一份会随工作更新的记录。它可以放在 docs/status.md，也可以用项目现有的计划和日志。下面是游戏项目某一轮结束后的示意：

```text
当前阶段：让第一版可以完整玩完一局。
已决定：先做好单人玩法，不加账号和排行榜。
理由：先验证玩法是否有趣，再考虑扩展。
已完成：角色移动、碰撞和计分已实现。
检查结果：自动测试通过；手机试玩发现重开失效。
正在处理：修复重开后的状态重置。
下一步：修复后重新测试，并请用户在手机上试玩。
```

这里的完成项必须对应真实文件，检查结果应能找到具体证据。计划写准备做什么，进度写实际做了什么，决定还要带上理由。AI 才能知道该沿用哪个选择、哪些地方仍然需要验证。

可以在阶段结束时请求：

> 请更新项目记录，写明本轮实际完成的内容、重要决定及理由、检查结果、未解决问题和下一步。注明相关文件与证据位置，不把讨论过的想法写成已实施，也不把待检查写成检查通过。

改变要求时，同步修改对应记录；旧决定已经失效，就标明新的决定和原因。记录变长后再拆分，重点是当前状态清楚，不是文件越多越好。

### 约定 AI 每次先读什么，结束后更新什么

文件保存了，还要让 AI 在合适的时候读取。上传到 GitHub，也不会自动把整个仓库送进每次对话。

AGENTS.md 可以保存长期协作要求。Codex 会按其查找规则读取适用的指导文件；简单项目可以先在仓库根目录放一份。把项目材料的使用方式写进去，例如：[Codex 指导文件说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

```text
开始任务时，先读 README.md 和 docs/status.md。
结合相关代码、素材和检查记录确认当前状态。
我的想法可能是初步方案，请主动评估并解释推荐。
修改后完成适当检查，报告未验证的部分。
阶段结束时，更新状态与重要决定。
发布或增加费用前，请我决定。
```

README 保存项目说明，状态记录保存持续变化的进展，AGENTS.md 告诉 AI 怎样使用这些材料、怎样与你合作。文件名可以调整，读取和更新的约定要清楚；每天的进度不必全部堆进长期规则。

下一次开始，可以直接说：

> 请先读取项目说明、协作规则和最新进度，检查相关文件，说明目前做到哪里、还有什么没验证，并建议这次从哪里继续。记录与实际文件不一致时，先指出差异。

这样，你不用每轮从头复述；AI 也要用项目材料和实际结果确认状态，而不是只沿着上次的说法继续。

协作要求仍然是文字指导。涉及文件访问、合并或发布的实际限制，要由工具、账户或审批设置落实。

## 03 好用的做法，怎样留给下次用？

项目做到第二轮、第三轮时，常会出现另一种浪费。

每次开始，都要让 AI 读取当前状态；每次修改，都要运行同一组检查；每次结束，都要整理结果和下一步。此时继续把提示词写得更长，通常不能解决问题。因为需要保存的已经不是一句要求，而是一套反复出现的做法。

这时可以考虑 Skill。打开一个 Skill，通常会看到这样的目录：

```text
game-check/
├── SKILL.md       用途、步骤和检查要求
├── scripts/       可选的检查脚本
├── references/    可选的参考资料
└── assets/        可选的模板和资源
```

其中 SKILL.md 是核心，其他目录按需要添加。文件开头写名称和用途，后面写工作要求。下面是简化示例：

```markdown
---
name: game-check
description: 游戏改动后，检查运行与关键操作。
---
先读取项目运行说明，确认本轮改动。
运行已有测试，记录实际结果。
按检查清单验证开始、计分和重开。
无法试玩时说明缺口，不把测试通过写成试玩通过。
```

它是一份 AI 可以读取的工作说明，也可以带脚本和模板；它本身不会启动整个任务。[Skills 官方说明](https://learn.chatgpt.com/docs/build-skills)

用途、输入、步骤、检查办法和异常处理，是这份说明要交代清楚的内容。需要复杂操作时，再附参考资料、脚本或模板。

它和其他东西的关系，可以这样理解：

| 它是什么 | 解决什么问题 |
| --- | --- |
| 提示词 | 这一次请 AI 做什么 |
| AGENTS.md | 长期遵守什么规则 |
| Skill | 这类工作通常怎样完成 |
| 脚本 | 怎样稳定执行一个确定动作 |
| GitHub Actions | 某个项目事件发生后自动执行什么 |

比如，公众号项目可以把“读取 brief、核对来源、检查结构、保存版本”整理成 Skill；小游戏项目可以把“启动开发服务器、运行测试、记录结果”整理成 Skill。

如果已经有成熟的专业方法、官方技能或模板，可以直接采用并检查效果，不必先自己重复几轮。自己摸索出来的做法，则适合经过几次实际使用再整理。Skill 也可以指导调查和比较，不必每一步都固定；重要的是把适用范围和需要人判断的地方说明白。

Skill 保存的是方法，不是能力本身。它可以要求 AI 查询资料，却不会凭空获得查询权限；它可以要求运行测试，却不会自动拥有终端或浏览器。

## 04 AI 知道怎么做，但手里没有工具

这就进入工具层。

一个项目可能需要读取数据库、查询外部资料、打开浏览器、操作日历、生成图片，或者调用部署服务。AI 可能知道下一步应该做什么，但当前环境并没有提供相应的数据和动作。

MCP、插件和连接应用，解决的是“能够做什么”。

MCP（Model Context Protocol，模型上下文协议）约定了 AI 应用怎样与外部服务通信。实际使用时，应用连接 MCP 服务器，取得它提供的工具、资源或提示模板。本篇主要讲工具调用；具体能用哪些能力，还取决于客户端支持和服务权限。插件可以把 Skills、MCP 连接等能力打包交付；连接应用提供相应服务的访问入口。它们可能组合在一起，不是三套互不相关的东西。

### MCP 在电脑里长什么样？

最容易看见的是连接配置。下面是连接 OpenAI 官方文档服务的一个 Codex 配置示例：

```toml
[mcp_servers.openaiDeveloperDocs]
url = "https://developers.openai.com/mcp"
```

这段文字通常放在用户级的 ~/.codex/config.toml 中，也可以按官方支持的方式放到受信任项目的 .codex/config.toml。它只告诉 Codex 到哪里连接；地址背后运行的服务器，才真正提供搜索和读取文档的工具。

另一类服务器在本机运行，配置里会写启动命令和参数。它可能是一套 Python 或 JavaScript 程序，不一定有网页界面。插件附带的 MCP 配置还可能在插件自己的文件中，不能仅凭用户级配置判断所有可用工具。

### 在 Codex 里怎么用？

先连接，再提出任务。按照当前官方文档，桌面应用可在设置的 MCP servers 中添加服务，选择本地进程或 HTTP 连接，填写命令或地址；保存后重启连接，需要登录的服务还要完成授权。不同客户端的入口以其当前界面为准。[MCP 官方配置说明](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

如果使用 Codex CLI，官方文档服务的添加与查看命令是：

```sh
codex mcp add openaiDeveloperDocs --url https://developers.openai.com/mcp
codex mcp list
```

添加完成后，在支持的客户端中用 /mcp 查看连接状态。然后正常说出任务即可：

> 请使用 openaiDeveloperDocs MCP 查询 Codex 的 AGENTS.md 读取规则，给出官方出处。连接不可用时请说明。

Codex 根据请求选择搜索工具、填写查询参数、读取返回结果，再组织回答。用户不用手写工具调用代码，也不用每轮重新添加服务器。配置存在只证明已经配置；实际调用成功并返回内容，才证明这次连接可用。[官方文档 MCP 示例](https://developers.openai.com/learn/docs-mcp)

工具也可以通过任务需要被自动选择，但想确认走的是哪个连接，就在请求里明确指定，并查看执行过程中的工具调用记录。读取本地文件或运行 Git 命令，可能使用的是文件、终端工具，不能据此认定调用了 GitHub MCP。

它们和 Skill 的关系不是替代，而是配合：

- Skill 规定什么时候需要工具；
- 工具提供实际可调用的能力；
- 项目规则说明访问要求，工具和账户权限落实限制；
- 任务结果还要经过检查。

工具也可以由应用直接提供，或由程序通过普通接口调用，不必全部经过 MCP。Skill 可以规范调用顺序，但不是使用工具的前提；模型也可以根据本轮请求选择工具。登录取得了访问资格，也不等于每次写入、发送或发布都获得了批准。

工具越多，权限和副作用越需要说清楚。连接账号、读取客户资料、发送邮件、修改线上数据，都不能因为“AI 能调用”就默认允许。第三方 Skill、MCP 或插件也不能当作可信黑盒，需要看来源、代码、权限、数据流、凭证和回滚办法。

## 05 有了工具，整套工作怎么跑起来？

接上工具以后，AI 可以读取资料、修改文件、运行检查。但一项任务通常需要连续完成好几个动作：先查什么，再改什么？检查失败以后怎么办？什么时候继续，什么时候需要人决定？

这些安排要落实到实际运行中。只把步骤写下来还不够，还需要有程序调用工具、接收结果、保存当前状态，再根据结果继续或停下。

### 一个具体例子：处理游戏里的用户反馈

假设 GitHub 收到一条 Issue：

> 第二关太难，很多人玩到这里就放弃了。请看看问题在哪里。

如果只把这句话交给 AI，它可能直接改数字、改地图，甚至增加提示按钮。但在真正修改之前，至少要先完成几步：

1. 读取 Issue、当前分支和最近一次可玩的版本；
2. 查看已有的试玩记录和测试结果；
3. 判断这是程序错误、难度设置、操作体验，还是用户还没有理解规则；
4. 如果资料不足，先要求补充试玩记录，而不是直接改代码；
5. 只有确定属于本轮范围，才创建分支并提出一个小改动；
6. 运行测试和试玩检查，记录改动前后的结果；
7. 风险较高或结果不明确时暂停，请人决定；
8. 通过检查后创建 Pull Request，把证据带回项目。

把这整条过程组织起来的运行框架，通常称为 Harness。它需要知道当前 Issue 是什么、代码在哪个版本、可以调用哪些工具、哪些动作必须批准，以及失败后从哪里继续。

使用 Codex 时，已有的运行系统就在承担其中一些工作。了解 Harness，是为了知道这套执行过程怎样被组织；普通项目可以先用现成能力，需要特殊流程时再考虑定制。

### 打开一个 Harness，会看见什么？

它没有统一的必需文件名。自己写一套简化框架，可能会把代码分成这样几部分；这些名称只是示意，不代表有了这几个文件就实现了恢复和审批：

```text
feedback-runner/
├── main.py        执行循环
├── tools.py       Issue、文件和测试工具接口
├── policy.py      权限检查、审批与次数限制
├── state.json     当前任务与进度
└── logs/          工具结果和错误记录
```

真正关键的是执行循环。下面是伪代码，用来说明机制，不能直接运行：

```text
读取任务，加载上次保存的状态
循环直到完成或达到限制：
    把材料、规则和工具说明交给模型
    如果模型请求使用工具：
        检查权限；必要时等待人批准
        执行工具，把结果交回模型
        保存当前状态和运行记录
    如果需要补资料或人作决定：
        保存状态，暂停
    如果已完成：
        检查完成证据，交付结果
```

Skill 可以写“测试失败就继续修”，但要有运行程序把真实报错交回模型，执行下一次修改。Skill 可以写“合并前请人批准”，但真正阻止未经批准的合并，需要权限控制或执行程序来实现。

**很多 Skills 放在一起，仍然是一组工作方法。Harness 负责组织它们和工具怎样运行。**它可以自动推进，也可以等人确认；可以固定部分步骤，也可以让模型根据新结果选择下一步。自动化和边界都是可以设计的能力，核心是执行循环。[运行架构参考](https://developers.openai.com/api/docs/guides/agents-api/architecture)

Harness 可以通过程序检查和权限设置落实边界：只开放指定仓库和试玩记录，允许创建分支但不允许直接合并；测试失败时带着错误继续诊断，缺少证据时交给人。

恢复也需要专门实现。程序要记录哪些动作已经完成，确认外部操作是否成功，并在重试前避免重复创建 Issue、发送消息或写入数据。只保存一份 state.json 或日志，还不能保证任务安全恢复。

这样做的价值，不是让 AI 永远自动完成任务，而是让它每次都按照同一条可检查的路径工作。哪一步出错了，下一次也能知道从哪里查。

## 06 什么时候需要自己搭框架？

项目做几个月、代码有几万行，都不是自建 Harness 的充分理由。真正要看的是：现有 Codex、Skills、脚本和任务调度，能不能可靠地组织这项工作。

**个人开发、写作和研究项目，通常先用现成运行系统。**项目规则写清楚，重复步骤整理成 Skill，确定性检查交给脚本，再按需要连接工具。仅仅想每周运行一次，也可以先考虑现成定时任务。

**需要嵌入产品、无人值守处理任务，或者必须精确管理执行过程时，才更值得定制。**例如：

- 客服系统持续接收反馈，需要按用户权限取资料、分流、重试、转人工，并保存每次处理状态；
- 批量处理几千份文件，服务中断后要从检查点恢复，避免重复写入；
- 研究代理反复进行搜索、实验和评估，需要控制预算、比较策略、完整回放失败过程。

即使是这些场景，也先检查脚本、任务队列或现成框架能否满足。规则明确的批处理可以直接由普通程序执行；只有任务需要模型持续判断并调用工具时，才涉及这里讨论的 AI 执行框架。需要自行开发的，是现成能力覆盖不了的部分。自建以后还要维护工具接口、异常处理、状态存储和评估，这也是工程成本。

可以这样请 Codex 开始：

> 请检查现有流程，判断用项目规则、Skill、脚本和现成调度能否满足。若确实需要定制 Harness，请指出具体缺口，先设计一个可运行的小样例，说明输入、状态、工具、停止条件和恢复办法。用模拟数据验证，不连接生产账号。

验收时，不只看正常任务能否结束，还要主动制造工具报错、执行中断和缺少审批的情况，检查它是否停止、能否恢复、会不会重复执行。

现成运行系统能满足要求，就先用现成能力。需要自建时，也从当前缺少的那一部分开始。

## 07 反复出现的判断，能不能交给程序？

回到前面游戏反馈的例子，修改之前要判断“反馈更像哪一类问题”。如果类似反馈经常出现，每次都需要分类并安排后续处理，就可以考虑把这个判断单独接进程序。

Jev 是 TypeSafe 提供的决策模型，可以接收材料和问题，返回程序能直接使用的选择、评分或是非判断。在这个例子里，可以问它“根据现有材料，最值得先调查哪一类问题”，从以下选项中选择：

- 程序错误；
- 难度或数值问题；
- 操作和界面问题；
- 规则没有说明白；
- 证据不足，需要人工查看。

传给它的不是一句孤立的问题，而是整理好的状态：Issue 内容、当前关卡数据、试玩记录、最近改动和已有测试结果。程序把这些材料放进固定字段，再提出一个范围明确的问题。

Jev 可以返回选中的调查方向、各选项的概率和置信信息。比如选择“难度或数值问题”，下一步是查看失败位置和试玩表现，再决定是否试改数值。**分类提供的是调查线索，不能直接证明原因。**

几类问题也可能同时存在。若需要同时识别，就分别询问各个条件，而不是强迫模型只选一个。材料不足或结果含糊时，先补充观察或交给人判断。

置信度表示候选结果分布有多集中，不等于现实中的正确率，更不代表获得了修改或发布授权。采用什么阈值，要用项目里的代表性案例验证，结合误判后果决定。[TypeSafe 置信度说明](https://docs.typesafe.ai/confidence)

TypeSafe 的公开文档把 Jev 归在 System One 模型中，强调输入状态和结构化问题，返回代码可以继续处理的选择、评分或判断，而不是生成一段长文字。[TypeSafe 文档索引](https://docs.typesafe.ai/llms.txt)

确定规则和计算交给普通代码；开放式分析、提出方案可以交给通用模型；Jev 这类模型则提供程序可以使用的语义判断。这些能力可以配合，选哪一种要看实际效果、速度和成本。

JevHarness 的公开项目说明展示了类似的组合方式：开发阶段由模型设计任务专用 Harness；运行时由代码准备状态、提出 Jev 问题，再把结构化判断组合成动作；完整轨迹可以用于后续评估和改进。[JevHarness 项目](https://github.com/TianyuCodings/JevHarness)

Jev 的采用与是否自建 Harness 是两个选择。没有清楚的判断依据和评价数据，就先把业务问题弄清楚；程序能读懂返回格式，也不代表判断一定正确。

## 08 按项目需要来选

前面几种做法解决的问题不同，可以根据当前缺口来选：

| 遇到的问题 | 先考虑什么 |
| --- | --- |
| 不知道改了什么，想回到上一版 | Git / GitHub |
| AI 不知道项目长期约定 | 项目规则文件 |
| 每次都重复同一套步骤 | Skill |
| AI 看不到资料或无法执行动作 | MCP / 插件 / 连接应用 |
| 现成系统无法满足执行、审批或恢复要求 | 定制 Harness |
| 同类判断反复发生，而且可以评估 | Jev 或其他决策层 |

### 真正做一轮，会怎样用到它们？

还是游戏反馈的例子。一轮开始时，先读取规则、当前计划和已知问题，确认是在正确的版本上工作。需要与其他任务并行，就准备独立工作副本。

接着调查原因，在分支上做小范围修改。代码测试通过后，还要试玩：游戏能运行，不等于第二关真的更好玩。随后检查差异，把改动、证据和未解决事项一起提交审阅；接受改动后再合并，并把当前决定与进度更新到项目材料中。需要远程归档时，确认推送结果。

**模型判断是否合理、工具是否执行成功、作品是否达到目的，是三项不同的检查。**工具返回成功，只能说明动作完成；成果是否有效，还要按原来的目标来判断。

规则、Skill 或工具更新以后，可以用一组熟悉的任务重新检查。比如正常反馈、缺少材料、测试失败和需要批准的情况，各走一遍，观察有没有漏掉步骤或越过边界。

长期项目不必一次装齐所有组件。先让文件、版本、运行方法和当前状态清楚可查，再按实际需要增加可复用方法、外部连接或定制执行框架。
