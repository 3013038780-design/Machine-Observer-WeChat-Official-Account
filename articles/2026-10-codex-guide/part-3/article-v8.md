# 复杂项目，不能只靠聊天

和 Codex 一起工作 · 第三篇

和 AI 一起做一个长期项目，很多东西可以交给它完成。但文件放在哪、它改了什么、留下的记录是什么意思，你得看得懂，才能知道项目是不是真的在往前走。

前两篇讲了 Codex 的工作方式，以及怎样先把问题想清楚。这一篇接着讲：决定做一个项目以后，怎样把它做下去。

你提出要求，AI 写代码、做素材、整理文档、运行检查。几轮之后，项目里可能多了 README、AGENTS.md、计划和日志，GitHub 上也出现了分支、Issue 和 Pull Request。

这些事情可以由 AI 来做。你需要理解它们各有什么用，以及 AI 交付时，该检查什么。

## 01 项目放哪里，改动怎么保存？

先把实际工作的地方确定下来。做小游戏，可以在电脑上给它一个单独的文件夹，把代码、素材和说明放在一起。选择这个项目工作时，Codex 才有明确的文件范围。

接下来经常出现两个名字：Git 和 GitHub。

**Git 是记录文件变化的工具。**由 Git 管理的项目及版本历史，组成一个仓库。AI 修改文件后，可以把一批相关改动保存成一次提交（commit），附上说明。以后就能查看改了什么，比较前后差别，或找回已经记录的版本。

**GitHub 是保存远程仓库和协作的服务。**把本地提交推送过去，GitHub 上才有这次更新。保存文件、提交版本、推送到 GitHub，是不同的动作，不能只看 AI 说了一句“已保存”。

你可以要求它在结束时说明：本轮改动在哪个目录、哪个分支，是否已经提交，是否已经同步。需要确认远端归档时，再核对 GitHub 上对应的提交。

个人项目可以放在自己的账户下；组织则方便统一管理多个仓库和成员权限。只有你和 AI 做项目，也可以从个人仓库开始。代码和文档适合随仓库保存，大型素材另外安排存储，密钥和登录凭证不要提交进去。

### 分支是做什么的？

小游戏已经能运行，你想试一种新玩法，又希望保留现在这一版。可以从当前版本建立一个分支，在这个分支上修改和提交，通过检查后再合并回主分支。

分支就是 Git 中一条单独的版本路线。它让一批试验中的改动暂时不进入主分支，但不会自动变成另一个文件夹。

如果两个 AI 任务需要同时改代码，可以用 worktree 或独立克隆，给它们各自的工作目录。尚未提交的文件变化也要妥善保存；创建分支本身不等于备份了这些内容。[Git worktree 官方说明](https://git-scm.com/docs/git-worktree)

你要确认的是：AI 正在改哪一版，现在能用的版本有没有保留，这次尝试的改动是否与其他任务分开。

## 02 AI 写的这些文档，各有什么用？

仓库是为了完成项目而建立的。接下来你不断提出要求，AI 修改文件，也会整理项目说明、计划和记录。文档可以由它生成和维护，你需要看懂这些文字在说明什么。

### README：这个项目是什么，怎样运行

README.md 是项目说明，GitHub 通常会把它展示在仓库首页。创建仓库时可以选择生成它，模板或 AI 也可能已经写好；文件已经存在，就检查和更新内容，不必重新写一份。[GitHub README 说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)

它通常交代项目用途、主要文件、运行方法和其他资料的位置。以网页游戏为例，内容可以是：

```text
项目：手机浏览器里的躲避障碍小游戏。
第一阶段：能玩完一局、计分、重新开始。
暂不做：账号和排行榜。
代码：src/；图片和音效：assets/。
运行：使用项目指定的 Node.js 版本。
安装：npm ci；启动：npm run dev；测试：npm test。
当前计划和进度：docs/status.md。
```

这是简化示例，目录和命令要按实际工程填写。npm ci 需要匹配的锁文件，启动和测试命令也要在项目里有对应脚本。

README 没有固定的篇幅。你检查它有没有把项目用途写偏，文件位置是否准确，AI 有没有按说明成功运行过项目。换台电脑后，还需要准备依赖和配置；代码上传了，不等于运行环境也自动准备好了。真实密钥另行提供，说明里只留配置名称和取得方式。

### AGENTS.md：AI 在这里工作，要遵守什么

AGENTS.md 是给 AI 的项目指导。Codex 会按其查找规则读取适用的文件，用它了解长期要求。[Codex 指导文件说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

例如：

```text
先读 README.md 和最新进度，再检查相关文件。
不要默认我的初步方案就是最好的答案。
修改后运行适当检查，说明仍未验证的部分。
阶段结束后，更新决定和进度。
发布或增加费用前，请我决定。
```

这份文件可以由 AI 根据你们的约定整理。你要看要求是否准确、有没有过时，以及它实际做事时是否遵守了。每天的任务和测试输出不用全塞进长期规则。

写上“发布前问我”是文字要求。真正限制发布，还需要账户、工具权限或审批设置，不能只靠这句话。

### 计划和记录：准备做什么，实际做了什么

计划写接下来要做的工作；决定记录写选择和理由；进度写实际结果。小项目可以先合在一份文档中，不需要起步就建很多文件。

```text
当前目标：让第一版完整玩完一局。
已决定：暂不加排行榜，先验证玩法。
已完成：移动、碰撞和计分。
检查结果：自动测试通过；手机试玩发现重开失效。
下一步：修复重开，再检查手机操作。
```

你要检查的是：记录能不能对应实际成果。讨论过排行榜，不代表已经实现；测试通过，也不代表所有操作都试玩过。

README、AGENTS.md 和记录会在不同地方发挥作用：模型接收对话和指令，再通过工具读取有关文件、修改工程、取得检查结果。仓库里的文件并不会始终全部放在模型的上下文里。

因此，AI 需要按约定读取相关资料，并在完成阶段工作后更新记录。PLANS.md、build-log.md 等名称可以自行约定，名字本身不会让文件自动读取或更新。你检查它是否读了相关材料、记录是否符合实际，比检查文件是否“都建齐了”更有用。

## 03 AI 说做完了，你检查什么？

假设你要求修复游戏的“重新开始”按钮。AI 回复“已经修复”，这轮工作还需要核对几件事。

**先看改动范围。**请它列出改了哪些文件、分别改了什么。按钮问题为什么牵涉计分？是否改动了本轮没有要求的玩法？不熟悉代码，可以让它结合具体差异解释。

**再看实际效果。**打开游戏，玩到失败，再点击重新开始。角色、分数和关卡是否回到应有状态？文字说明和测试报告不能完全代替这一步。

**最后看检查结果。**它运行了哪些测试，结果在哪里？有没有测试失败或无法运行的情况？哪些仍需要你试用？

可以直接要求：

> 请给我本轮成果、具体改动和检查结果。说明哪些已经验证，哪些还没有；告诉我怎样打开和试用。文档里的完成记录也要与实际一致。

### Issue、Pull Request 和 Review，为什么会出现？

按钮失效可以记成一条 Issue。它是 GitHub 上的问题或任务记录，写明操作过程、预期结果和实际错误。今天不处理的事，也能留下来，下次继续安排。你可以让 AI 创建和更新它。

修复在分支上完成后，可以创建 Pull Request，简称 PR。它是一个合并请求，意思是：“请检查这批改动，合适的话，把它合并进目标分支。”

PR 页面把改动说明、文件差异、检查结果和讨论集中在一起。你可以在这里检查新代码增加、删除和修改了什么，再决定是否继续修正。Git 的 pull 命令是把远端变化取回并整合到本地；Pull Request 是合并提议，两者不是同一个操作。[GitHub PR 说明](https://docs.github.com/en/pull-requests/reference/pull-requests)

Review 就是审阅这批改动。按钮修好了，可能同时影响了计分；测试通过了，也可能漏掉触屏操作。审阅是为了发现这些问题，而不是看到“完成”就直接接受。

只有你和 AI 做项目，也可以自己试用，再让 AI 检查差异和测试缺口。你不需要假装懂每一行代码，但要知道成果是否符合目的，以及哪些风险还没检查。重要问题仍需相应的专业验证。

审阅可以提出意见、要求修改或表示批准；真正把改动纳入目标分支，还要完成合并，并满足仓库的权限和规则。个人小改动未必每次都要创建 PR，但检查成果这件事仍然需要做。

## 04 好用的做法，怎样留给下次用？

项目反复修改，你可能发现，每次都要做同一组检查：读运行说明，启动游戏，检查计分和重开，记录结果。这套方法可以整理成 Skill。

Skill 是 AI 可以读取的一份工作说明，也可以带脚本、参考资料和模板。实际目录通常像这样：

```text
game-check/
├── SKILL.md       用途和工作步骤
├── scripts/       可选的检查脚本
├── references/    可选的参考资料
└── assets/        可选的模板和资源
```

SKILL.md 是核心。比如，它可以要求游戏修改后运行已有测试，检查关键操作，最后报告结果；无法试玩时，明确说明，而不是写“全部通过”。[Skills 官方说明](https://learn.chatgpt.com/docs/build-skills)

你可以让 Codex 把有效做法整理成 Skill，也可以采用现成技能。自己摸索的流程最好经过实际使用；已经成熟的专业方法则不必从头试出一遍。

检查 Skill，先看它适用于什么工作、步骤是否合理，再选一件熟悉的任务试用。AI 读了说明，不等于已经执行；仍要看它实际调用了哪些工具、检查到了哪里。

Skill 和 AGENTS.md 也不同：前者讲这类工作怎样做，后者讲这个项目长期遵守什么。确定的重复动作可以交给脚本。它们都不会凭空增加工具权限。

## 05 需要外部资料和工具，怎么接？

有时 AI 知道该做什么，却拿不到相应资料，也没有操作能力。比如，它需要查询官方文档，或者读取某个外部服务中的数据。

MCP（Model Context Protocol，模型上下文协议）是一套连接约定，让 AI 应用与外部服务器交换工具、资料和提示模板。你实际看到的，通常是一个服务器连接，以及它提供的工具。

例如，Codex 连接 OpenAI 官方文档服务的配置可以是：

```toml
[mcp_servers.openaiDeveloperDocs]
url = "https://developers.openai.com/mcp"
```

地址背后的服务提供搜索和读取文档的能力。另一类 MCP 服务在电脑上运行，配置中写的是启动命令和参数。插件则可以把 Skills 和 MCP 连接等打包提供；具体包含什么，要看插件本身。

### 在 Codex 里怎样调用？

先添加连接，需要登录的服务完成授权，再提出任务。桌面端可按当前设置中的 MCP 服务器入口添加；CLI 也可以使用官方示例命令：

```sh
codex mcp add openaiDeveloperDocs --url https://developers.openai.com/mcp
codex mcp list
```

配置通常保存在 ~/.codex/config.toml，也支持受信任项目中的 .codex/config.toml。插件提供的连接还可能由插件管理。[Codex MCP 配置说明](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

连接可用后，可以直接说：

> 请用 openaiDeveloperDocs MCP 查询 AGENTS.md 的读取规则，给出官方出处。连接不可用时请说明。

Codex 选择工具、填写参数、读取结果，再回答你。日常使用不需要你手写调用代码。[官方文档 MCP 示例](https://developers.openai.com/learn/docs-mcp)

检查时要分清：配置已添加、工具已连接、这次调用成功，是不同状态。看执行记录中的工具名称、查询内容和返回结果，不只看回答里有没有提到 MCP。

工具也可以由应用直接提供，并不全经过 MCP。读取本地文件、运行 Git 命令，可能使用文件或终端工具。连接服务时还要确认来源和权限；能读取资料，不等于可以替你发送、修改或发布。

## 06 一连串工作，是怎样跑起来的？

AI 读完 Skill 后为什么能启动游戏、运行测试，再带着报错继续修改？因为背后有程序在组织这些动作。

模型判断下一步，运行程序执行工具调用，把结果交回模型，再继续下一轮。这类组织模型与工具执行的框架，常被称为 Harness。使用 Codex 时，你已经在使用它提供的运行系统。[运行架构参考](https://developers.openai.com/api/docs/guides/agents-api/architecture)

以修复按钮为例，过程可以简化为：读取任务和文件 → 调查 → 修改 → 测试 → 根据报错继续修正，或者报告完成。需要你决定时，程序可以暂停。

自己编写一个简化 Harness，可能会分成这些文件。名称不是标准，只是说明各部分做什么：

```text
runner/
├── main.py        调用模型，组织下一步
├── tools.py       读取文件、修改和测试的工具
├── policy.py      检查权限、审批和次数限制
├── state.json     保存当前进度
└── logs/          保存结果和报错
```

**Skill 写“怎样做”，Harness 组织实际执行。**很多 Skills 放在一起，也不会自动变成 Harness。Harness 可以连续运行，也可以等人确认；它不单纯等于自动化或权限边界。

### 什么情况下需要自己搭？

项目做几个月，并不意味着你需要另搭一套。先用 Codex、Skills、脚本和现成调度；明确的固定流程，普通程序可能就够了。

如果要把 AI 接进产品，持续处理大量任务，或者现成系统无法满足你的审批、中断恢复和记录要求，再考虑定制。例如，客服任务处理到一半中断后，要恢复进度，还不能重复发消息；实验代理则可能需要控制预算，留下每次选择和失败的记录。

可以先让 Codex 解释现有能力缺在哪里，再做一个只用模拟数据的小样例。检查它遇到工具报错会不会停，重启后能否继续，未经批准能不能执行受限操作。

目录里有日志和状态文件，并不代表恢复已经做好。程序还要确认哪些动作成功过、哪些可以重试，避免重复写入或发送。自建框架也意味着要维护这些代码。

## 07 反复出现的判断，也能交给程序吗？

游戏上线以后，反馈可能越来越多。AI 不仅要读内容，还要把反馈分给不同的处理流程。这时，可以把其中一个判断单独接进程序。

Jev 是 TypeSafe 提供的模型。它接收材料和问题，返回程序可以使用的选择、评分或是非判断，而不是一篇解释。[TypeSafe 文档](https://docs.typesafe.ai/llms.txt)

比如，一条反馈写“第二关太难”。程序把反馈、关卡数据和已有试玩记录交给 Jev，问：现有材料最支持先调查哪个方向？选项可以是程序错误、难度设置、操作问题、规则说明，或者资料不足。

Jev 返回选择和相关概率，程序再安排调查。选择“难度设置”，不代表已经找到原因，更不能直接据此降低数值。还要看失败位置、复现情况和试玩结果；多个问题可能并存，就分别判断。

你检查的是：它用了什么材料，选项有没有漏掉重要情况，判断后的动作是否合理。用已经知道结果的案例验证效果；置信信息反映候选结果的分布，不等于实际正确率，也不是执行授权。[TypeSafe 置信度说明](https://docs.typesafe.ai/confidence)

确定规则和计算可以交给代码，开放式分析可以交给通用模型，Jev 提供其中的语义判断。是否采用，要看任务效果、速度和成本，不是长期项目都需要它。

JevHarness 这个社区项目提供了一种组合示例：开发阶段让模型编写任务专用程序，运行时由程序准备材料、调用 Jev，再把判断变成动作，并留下运行记录。它是外部项目，不是 Codex 内置功能。[JevHarness 项目说明](https://github.com/TianyuCodings/JevHarness)

---

做长期项目，不必先学会所有配置，也不需要自己写完全部文档。可以让 AI 建立、整理和执行，但你需要知道它做了什么，成果在哪里，还有什么没有验证。

仓库保存文件和版本，文档解释项目和进展，Skill 留下方法，工具提供动作，运行框架把它们接起来。每多用一样东西，都应该帮助你解决一个具体问题。
