# 复杂项目，不能只靠聊天

和 Codex 一起工作 · 第三篇

AI 做一次小任务，一条提示词也许够用；要和 AI 一起做几周、几个月的项目，代码、版本、规则、工具和每次决定应该怎样组织？这篇从 GitHub 讲到 Skills、MCP、Harness 和 Jev，把长期项目怎样持续推进讲清楚。

在同一个聊天里，AI 通常能接着做。问题出现在项目变长以后。

比如，一个手机小游戏已经有了第一版。接下来还要加新玩法、修错误、换素材、适配手机、准备发布。此时，代码和素材开始分开，新的尝试和原来的版本混在一起，讨论过的方案散在聊天记录里。想让另一个任务帮忙检查，又不知道该给它哪些材料。

这时，问题不再是“AI 记不记得上一句话”，而是：

> **怎样让一项复杂工作有地方保存，有办法执行，有证据检查，也能在下一次继续？**

一条提示词负责提出这一次的要求。长期项目还需要一套能够承接工作的系统。

## 01 先给项目建立一个共同现场

最先需要解决的，是项目到底放在哪里。

做小游戏时，代码可能在电脑上的一个文件夹里，图片在另一个位置，需求写在聊天里，运行方法只记得大概，版本则靠“应该是上周那一份”。AI 可以在当前环境里帮忙，但这套工作很难交给另一个任务，也不容易回到一个确定的状态。

Git 和 GitHub 解决的是这类问题。

本地文件夹是实际工作的地方。Git 仓库记录文件怎样变化。GitHub 仓库则把代码、文档、素材和版本放到一个可以访问、审阅和协作的项目空间里。三者有关联，但不是一回事：电脑上的文件可以先独立工作，Git 记录变化，GitHub 负责远程保存和协作。

GitHub 还会把“谁可以参与”说清楚。个人账户适合个人项目；组织可以管理多个仓库、成员和权限。项目需要让别人查看、提交修改、审阅代码，还是只能看到公开内容，都应该在这里设置，而不是在聊天里含糊地约定。

分支解决另一个常见问题：想试一条新路线，又不想破坏当前版本。

主分支可以保持一个当前能够接受的状态。开发新功能时，在另一个分支里尝试；试错成功，再合并回去；方向不合适，放弃这个分支即可。提交则给变化留下一个能说清楚的节点：这次改了什么，为什么改，改完检查到了什么。

GitHub 的 Issue、Pull Request 和 Review，也分别承担不同工作。

Issue 说明要解决什么问题；分支承载一次具体尝试；Pull Request 把改动拿出来比较；Review 判断是否接受。这样，“提出问题”“修改文件”和“接受结果”就不再混在同一个聊天窗口里。

这不是说每个小改动都必须走一套复杂流程。一个人做一个很小的项目，直接在本地保存版本可能已经够用。项目变长、需要并行尝试，或者要让别人接手时，GitHub 的价值才会明显起来。

## 02 项目里要保存的，不只是文件

有了仓库，下一步不是马上创建很多文档，而是分清哪些判断值得留下。

一个长期项目至少有四种内容。

**目标和范围。**为什么做这件事，这一阶段做到哪里，哪些事情暂时不做。

**长期规则。**例如项目采用什么技术，哪些文件不能修改，怎样写代码，涉及发布和费用时谁必须决定。

**决定和理由。**为什么选择当前方案，放弃过什么，哪些条件变化后需要重新判断。

**实际状态和证据。**已经做了什么，测试是否通过，实际使用时发生了什么，哪些地方还没有完成。

这些内容可以放在 README、规则文件、计划、决定记录或进度日志里。小项目可以合并，长线项目再拆开。重要的不是文件数量，而是下一次打开项目时，能够分清：

- 这是必须遵守的规则，还是本轮临时要求；
- 这是已经完成的事实，还是准备做的计划；
- 这是最终决定，还是讨论中的假设；
- 这是当前有效版本，还是已经过时的记录。

AGENTS.md 适合保存长期协作约定。它可以告诉 AI 怎样理解项目、哪些要求不能违反、什么时候应该主动检查和提出异议。但它不是计划文件，也不能代替事实记录。

同样，PLANS.md、GOALS.md 或 build-log.md 这类名字只是项目约定，不是写上名字后 AI 就会自动读取。真正重要的是把它们放到明确的位置，在任务开始时说明怎样使用，并在内容变化后及时更新。

记录的目的也不是让 AI 看起来“有记忆”。它是为了让人能够核对：当前目标有没有变，上一轮到底完成了什么，下一步为什么这样安排。

## 03 重复做法，才值得变成 Skill

项目做到第二轮、第三轮时，常会出现另一种浪费。

每次开始，都要让 AI 读取当前状态；每次修改，都要运行同一组检查；每次结束，都要整理结果和下一步。此时继续把提示词写得更长，通常不能解决问题。因为需要保存的已经不是一句要求，而是一套反复出现的做法。

这时才值得考虑 Skill。

一个 Skill 应该说明：

- 什么情况下使用；
- 需要哪些输入；
- 先做什么，再做什么；
- 可以查哪些资料、运行哪些脚本；
- 怎样判断结果合格；
- 遇到异常时什么时候停下，请人决定。

它和其他东西的关系，可以这样理解：

| 它是什么 | 解决什么问题 |
| --- | --- |
| 提示词 | 这一次请 AI 做什么 |
| AGENTS.md | 长期遵守什么规则 |
| Skill | 这类工作通常怎样完成 |
| 脚本 | 怎样稳定执行一个确定动作 |
| GitHub Actions | 某个项目事件发生后自动执行什么 |

比如，公众号项目可以把“读取 brief、核对来源、检查结构、保存版本”整理成 Skill；小游戏项目可以把“启动开发服务器、运行测试、记录结果”整理成 Skill。

但不要刚做过一次，就急着固化。一个流程至少要重复几轮，输入和输出相对稳定，检查办法也比较清楚，才值得保存。仍然需要大量现场判断的工作，先保持人工参与。

Skill 保存的是方法，不是能力本身。它可以要求 AI 查询资料，却不会凭空获得查询权限；它可以要求运行测试，却不会自动拥有终端或浏览器。

## 04 AI 知道怎么做，但手里没有工具

这就进入工具层。

一个项目可能需要读取数据库、查询外部资料、打开浏览器、操作日历、生成图片，或者调用部署服务。AI 可能知道下一步应该做什么，但当前环境并没有提供相应的数据和动作。

MCP、插件和连接应用，解决的是“能够做什么”。

MCP 可以把外部数据或动作以工具的方式提供给 AI。插件通常把一组能力、说明和权限包装在一起。连接应用则让项目取得某个外部服务里的资料，或执行它允许的操作。

它们和 Skill 的关系不是替代，而是配合：

- Skill 规定什么时候需要工具；
- 工具提供实际可调用的能力；
- 项目规则限制可以访问的范围；
- 任务结果还要经过检查。

例如，旅行网站项目需要查询日历。Skill 可以规定先读取已有行程，再检查冲突，最后给出修改建议；日历连接提供读取事件的能力。没有连接，Skill 只能提出一个无法执行的步骤；没有 Skill，工具也不知道什么时候该调用、结果怎样使用。

工具越多，权限和副作用越需要说清楚。连接账号、读取客户资料、发送邮件、修改线上数据，都不能因为“AI 能调用”就默认允许。第三方 Skill、MCP 或插件也不能当作可信黑盒，需要看来源、代码、权限、数据流、凭证和回滚办法。

## 05 有了工具，整套工作怎么跑起来？

接上工具以后，AI 可以读取资料、修改文件、运行检查。但一项任务通常需要连续完成好几个动作：先查什么，再改什么？检查失败以后怎么办？什么时候继续，什么时候需要人决定？

这些安排要落实到实际运行中。只把步骤写下来还不够，还需要有程序调用工具、接收结果、保存当前状态，再根据结果继续或停下。

### 一个具体例子：处理游戏里的用户反馈

假设 GitHub 收到一条 Issue：

> 第二关太难，很多人玩到这里就放弃了。请看看问题在哪里。

如果只把这句话交给 AI，它可能直接改数字、改地图，甚至增加提示按钮。但在真正修改之前，至少要先完成几步：

1. 读取 Issue、当前分支和最近一次可玩的版本；
2. 查看已有的试玩记录和测试结果；
3. 判断这是程序错误、难度设置、操作体验，还是用户还没有理解规则；
4. 如果资料不足，先要求补充试玩记录，而不是直接改代码；
5. 只有确定属于本轮范围，才创建分支并提出一个小改动；
6. 运行测试和试玩检查，记录改动前后的结果；
7. 风险较高或结果不明确时暂停，请人决定；
8. 通过检查后创建 Pull Request，把证据带回项目。

把这整条过程组织起来的运行框架，通常称为 Harness。它需要知道当前 Issue 是什么、代码在哪个版本、可以调用哪些工具、哪些动作必须批准，以及失败后从哪里继续。

使用 Codex 时，已有的运行系统就在承担其中一些工作。了解 Harness，是为了知道这套执行过程怎样被组织；普通项目可以先用现成能力，需要特殊流程时再考虑定制。

Harness 可以规定这样的执行边界：只能读取当前仓库和试玩记录；可以创建分支，但不能直接合并；测试失败时回到诊断步骤；缺少证据时转给人；每一步都把结果写进运行记录。

这样做的价值，不是让 AI 永远自动完成任务，而是让它每次都按照同一条可检查的路径工作。哪一步出错了，下一次也能知道从哪里查。

### 反复出现的判断，也可以单独处理

上面第三步要判断“反馈更像哪一类问题”。如果类似反馈经常出现，每次都需要分类并安排后续处理，就可以考虑把这个判断单独接进程序。

Jev 是 TypeSafe 提供的决策模型，可以接收材料和问题，返回程序能直接使用的选择、评分或是非判断。在这个例子里，可以请它从以下选项中判断：

- 程序错误；
- 难度或数值问题；
- 操作和界面问题；
- 规则没有说明白；
- 证据不足，需要人工查看。

传给它的不是一句孤立的问题，而是整理好的状态：Issue 内容、当前关卡数据、试玩记录、最近改动和已有测试结果。程序把这些材料放进固定字段，再提出一个范围明确的问题。

Jev 返回的是结构化结果，例如“更像难度问题”、各选项的概率和不确定程度。接下来的动作由代码或 Harness 决定：判断足够明确，就安排一次小范围数值调整；判断接近，或属于证据不足，就暂停并交给人。

TypeSafe 的公开文档把 Jev 归在 System One 模型中，强调输入状态和结构化问题，返回代码可以继续处理的选择、评分或判断，而不是生成一段长文字。[TypeSafe 文档索引](https://docs.typesafe.ai/llms.txt)

这里的重点不是“让 Jev 替 AI 做决定”，而是把一个反复出现、范围有限的判断单独拿出来，给它明确输入、明确选项和明确的后续动作。

JevHarness 的公开项目说明展示了类似的组合方式：开发阶段由模型设计任务专用 Harness；运行时由代码准备状态、提出 Jev 问题，再把结构化判断组合成动作；完整轨迹可以用于后续评估和改进。[JevHarness 项目](https://github.com/TianyuCodings/JevHarness)

### 什么时候不要用它们

如果项目还没有稳定流程，Issue 的信息也不完整，先用普通 AI 对话和人工检查把步骤跑通。没有清楚的候选选项，就没有必要急着做 Jev 判断；没有明确的停止条件，也不应该先搭 Harness。

Jev 不能替人定义项目目标，也不能保证判断正确。Harness 也不能把混乱的流程自动变好。它们适合把已经理解、重复发生、能够检查的工作固定下来，而不是用来掩盖问题还没有想清楚。

所以，Harness 和 Jev 应该放在工具链的后面：先有项目现场，再有状态记录和稳定步骤，最后才判断哪些执行循环和局部决策值得程序化。

## 06 不是所有项目都需要全部装上

把手机小游戏放回来看，可能只需要其中几层。

代码、素材和版本越来越多，可以先建立 GitHub 仓库，用分支尝试新功能。

多人或多个任务需要接手，就把长期规则、当前计划和实际进度写进项目材料。

“启动项目、运行检查、整理素材”重复几次以后，可以做成 Skill。

如果需要从日历、数据库或浏览器读取信息，再接入相应的 MCP 或插件。

如果任务需要持续运行、自动暂停、失败恢复和完整记录，再考虑 Harness。

只有当某类选择反复出现，而且能够定义标准并检查结果，才考虑 Jev 这样的决策层。

可以用一个简单判断来选择复杂度：

| 遇到的问题 | 先考虑什么 |
| --- | --- |
| 不知道改了什么，想回到上一版 | Git / GitHub |
| AI 不知道项目长期约定 | 项目规则文件 |
| 每次都重复同一套步骤 | Skill |
| AI 看不到资料或无法执行动作 | MCP / 插件 / 连接应用 |
| 任务要持续运行、暂停和恢复 | Harness |
| 同类判断反复发生，而且可以评估 | Jev 或其他决策层 |

这些东西不是一套必须全部采用的配置。它们像不同的补丁，分别补上保存、复用、连接、运行和判断的缺口。

复杂项目真正需要的，不是把工具都装上，而是让每一层都回答一个明确问题：

- 现在的状态在哪里？
- 这套做法怎样重复？
- 需要什么外部能力？
- 任务怎样持续运行？
- 哪些判断可以交给程序，哪些必须由人决定？

做一次小任务，聊天可能就够了。长期做一个复杂项目，就要把代码、版本、规则、工具和判断组织起来。
