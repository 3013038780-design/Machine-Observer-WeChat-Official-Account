# 第三篇写作大纲 v2：把一次协作变成可运行的项目系统

状态：候选大纲，待用户审核。日期：2026-10-14。

## 唯一命题

复杂工作不能靠一条越来越长的提示词完成。要把目标、材料、版本、工具和决策规则组织成一个可运行、可检查、可接续的项目系统。

第三篇不是 Skills 教程，也不是 GitHub 功能清单。GitHub、项目规则、Skills、MCP、Harness 和 Jev 分别解决系统中的不同缺口，文章按缺口递进，而不是按产品名称平铺。

## 与前两篇的关系

- 第一篇回答：Codex 在哪里工作，能看到什么，能改什么。
- 第二篇回答：问题还没想清楚时，怎样和 AI 共同判断。
- 第三篇回答：判断形成以后，怎样给这项工作建立一个可以保存、执行、检查和继续的系统。
- 第四篇再进入系统内部的一轮实际实现、工具调用、测试和修复。
- 第五篇处理从项目到真实用户的构建、部署和访问。
- 第六篇处理上线后的维护、自动化、评估和治理。

## 标题与开头描述（候选）

标题先说读者熟悉的困惑，不把技术名词写成目录。当前候选：

- 《复杂项目，不能只靠聊天》
- 《长期做一个项目，AI 该怎么帮你？》

推荐描述：**如果要和 AI 一起做几周、几个月的项目，代码、版本、规则、工具和每次决定应该怎样组织？这篇从 GitHub 讲到 Skills、MCP、Harness 和 Jev，把长期项目怎样持续推进讲清楚。**

标题和描述使用自然语言，正文再解释 GitHub、AGENTS.md、Skills、MCP、Harness 和 Jev。标题不承担技术目录，描述不提前塞入全部术语。

## 开头：复杂项目，不能只靠聊天

用一个具体场景进入：

用户和 AI 在同一个对话里已经把小游戏做出了第一版，工作确实可以接着进行。真正的困难出现在项目变长以后：代码、素材、运行环境和版本开始分开；一个对话里同时混着新功能、错误修复和发布准备；想尝试另一条路线，又不想破坏当前版本；需要别人或另一个任务接手时，聊天记录不能直接说明哪些是事实、哪些是决定、哪些只是讨论。

开篇判断：

> 做一次小任务，聊天可能就够了；要长期做一个复杂项目，就需要把代码、版本、规则、工具和判断组织起来。

这一段承认同一上下文的连续性，不制造“AI 立刻失忆”的假问题；再把问题推进到项目边界、版本安全、协作交接和重复执行，不先抛出 Skills、MCP 或 Jev。

## 01 先给工作建立一个共同的现场：GitHub 和项目环境

### 要回答的问题

代码、文档、素材、任务和版本，怎样放在一个能够被人和 AI 共同查看的地方？

### 叙述顺序

1. 从本地文件夹进入 Git 仓库，再进入 GitHub 仓库，解释它们分别保存什么。
2. 介绍个人账户、组织、成员和权限：项目属于谁，谁可以读取、修改、审阅和合并。
3. 解释分支：主分支保存当前可接受状态，功能分支承载一次尝试，失败时不会覆盖主线。
4. 解释提交和差异：给每次变化留下可说明的节点，知道 AI 改了什么。
5. 解释 Issue、Pull Request 和 Review：把“要做什么”“改了什么”“是否接受”分开。
6. 说明 Actions、项目看板和发布记录只作为环境的延伸出现；完整自动化和发布留到后文。

### 本节推进

读者先理解：GitHub 不是单纯的代码网盘，而是项目的共同现场和变化记录。没有这个现场，后面的规则、技能和工具很难稳定接续。

### 与第四篇的边界

第三篇解释这些对象之间的关系和使用理由；第四篇再展示一条 Issue 如何进入分支、修改、检查、Review 和合并。

## 02 让项目保存判断，而不只是保存文件

### 要回答的问题

AI 下一次怎样知道什么已经决定、什么仍是假设、什么已经完成？

### 核心内容

把项目里的上下文分成四层：

- **目标与范围**：为什么做、这一阶段做到哪里、什么暂不做；
- **长期规则**：协作约定、技术边界、写作标准和权限要求；
- **决定与理由**：选择过什么、放弃过什么、哪些条件变化后需要重新判断；
- **实际状态与证据**：做过什么、检查到了什么、哪里失败、下一步是什么。

在这里介绍 AGENTS.md、README、计划文件、决定记录、变更日志和构建日志，但不把文件名写成产品自动约定。

关键解释：

- 规则文件不是当前任务；
- 计划不是完成记录；
- 计划模式不是某个文件；
- 新对话不会自动获得旧对话事实；
- 记录的价值是减少重复判断，不是制造文档数量。

### 本节推进

读者知道为什么一个项目需要“状态和理由”，而不是把所有内容继续堆在提示词里。

## 03 当方法需要重复时，才引入 Skill

### 要回答的问题

为什么不能每次重新写一条长提示词？什么才值得保存成 Skill？

### 核心内容

从同一个任务重复三次的场景进入：每次都要读取项目状态、检查素材、运行同一组验证、记录结果。此时问题不是“提示词不够长”，而是做法已经重复。

解释 Skill 保存的是：

- 什么时候使用；
- 输入材料是什么；
- 按什么步骤推进；
- 可以调用哪些参考资料或脚本；
- 怎样检查结果；
- 出现异常时如何停下或交还给人。

区分：

- 提示词：一次请求；
- AGENTS.md：长期约定；
- Skill：可复用工作方法；
- 脚本：确定性的动作；
- GitHub Actions：项目事件触发的自动执行。

### 判断标准

只有当流程已经重复、步骤相对稳定、输入输出可描述、结果可检查时，才值得做成 Skill。仍在探索的做法应该继续人工参与。

### 本节推进

读者明白 Skill 是因为某种工作已经稳定且重复，而不是因为“高级用户都应该安装 Skill”。

## 04 当项目需要外部能力时，连接 MCP、插件和应用

### 要回答的问题

AI 知道该怎么做，但看不到资料，也没有执行动作的能力，怎么办？

### 先解释缺口

Skill 说明“怎样工作”，却不自动提供数据或动作。项目可能需要读取数据库、查询外部资料、操作浏览器、访问日历、生成图片或调用部署服务。

### 再解释工具层

- MCP 连接外部数据和动作；
- 插件提供一组经过包装的能力和权限；
- 连接应用让项目取得外部服务中的资料或执行操作；
- 工具的存在不等于应该自动调用，权限、范围、登录态和副作用仍需明确。

### 与 Skill 的关系

Skill 决定什么时候调用工具、调用顺序、输入怎样准备、结果怎样核对、失败如何处理；MCP 或插件提供“能做什么”。

### 安全边界

不把第三方 Skill、MCP 或插件当作可信黑盒。需要检查来源、代码、权限、数据流、凭证、版本、提示注入和回滚方式。

### 本节推进

读者能够判断：缺的是工作方法，还是外部能力；不再把 Skill、MCP 和插件当成同一种东西。

## 05 当一次判断变成很多次判断：Harness 和 Jev 放在哪里

### 要回答的问题

如果任务需要在很多轮执行中不断选择、评分、路由、暂停或恢复，为什么不能每次都让通用模型从头推理？

### 先介绍 Harness

Harness 是把模型、工具、环境、状态、审批、事件、失败处理和恢复组织成一条可运行的执行循环。

它适合解决：

- 每次运行都要读取哪些状态；
- 可以调用哪些工具；
- 哪些动作需要批准；
- 失败后从哪里恢复；
- 怎样留下完整轨迹；
- 什么时候交给人。

它不是更长的 Skill，也不是一个更聪明的模型。

### 再引入 Jev

在需要大量重复、局部、可评估的选择时，可以把决策从每次开放式推理中抽出来：

- 输入由项目环境提供；
- Harness 计算和整理可用特征；
- Jev 对候选方案进行选择、评分或判断；
- 结果进入下一步动作；
- 运行轨迹再用于评估和改进。

根据目前核查的 JevHarness 公开资料，它把任务专用 Harness、结构化特征、Jev 判断和可选的轨迹反思组合起来；它属于外部/社区项目，不是 Codex 内置能力。[JevHarness 项目说明](https://github.com/TianyuCodings/JevHarness)

这里必须讲清：

- Jev 不是用来替代所有 AI 推理；
- 它更适合边界清楚、重复运行、可以定义评价标准的局部决策；
- 它不能替人定义目标、承担责任或保证结果正确；
- 在没有稳定流程和评估集时，不应急着引入。

### 为什么这一节放在最后

只有前面已经有了项目现场、状态记录、可复用方法和工具连接，读者才知道 Harness 和 Jev 究竟在系统中的哪个位置；否则它们只是又一组陌生名词。

## 06 把这些层接成一个系统：一个项目如何选择所需复杂度

用“手机小游戏”作为小案例，但不把所有组件强行装上：

1. GitHub 仓库保存代码、素材、Issue、分支和可回退版本；
2. AGENTS.md 保存长期协作规则，计划和日志保存当前状态；
3. Skill 固化“启动项目、运行检查、整理素材”这类已经稳定的步骤；
4. MCP 或插件只在需要外部资料或动作时接入；
5. Harness 只在任务需要持续执行、恢复和审批时出现；
6. Jev 只在某类局部选择被重复执行且有评价标准时出现。

给出一张“问题—所需层”的判断表：

| 遇到的问题 | 先考虑 |
|---|---|
| 不知道当前版本和改动 | Git / GitHub |
| AI 不知道长期规则 | 项目规则文件 |
| 每次都重复同一套步骤 | Skill |
| AI 看不到外部资料或无法执行动作 | MCP / 插件 / 连接应用 |
| 任务需要持续运行、恢复、审批和轨迹 | Harness |
| 同类局部选择反复发生且可评估 | Jev 或其他决策层 |

## 结尾：复杂度应该被问题推出来

回到唯一命题：

> 不是因为工具多，所以要把它们全部装进项目；是因为工作出现了新的缺口，才逐层补上保存状态、复用方法、连接能力和组织决策的机制。
