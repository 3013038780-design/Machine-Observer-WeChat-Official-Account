# 复杂项目，不能只靠聊天

和 Codex 一起工作 · 第三篇

和 AI 搭档做一个要做几周、几个月的大项目，先想好三件事：文件放哪儿？改崩了怎么回来？同一句话怎么不用重复念一百遍？

你的手机小游戏第一版上线了。接下来要加新玩法、修 bug、换素材、适配机型、准备发布。然后呢？代码和素材开始分居，新想法和旧版本搅成一锅粥，讨论过的方案淹在几百条聊天记录里。想请另一个 AI 帮忙检查，你翻遍记录却不知道该塞给它哪些材料。

一条提示词管的是这一次，一套系统管的是以后每一次。这篇文章就把这套系统按顺序装起来，地图先给：

| 眼下的缺口 | 对应的做法 |
| --- | --- |
| 不知道改了什么，回不去上一版 | Git / GitHub |
| AI 不知道项目的规矩和进度 | README、AGENTS.md、状态记录 |
| 每次都重复同一套步骤 | Skill |
| AI 看不到资料、动不了手 | MCP / 插件 |
| 一连串动作没人组织和把守 | Harness |
| 同类判断反复发生且可评估 | 决策模型（文末链接） |

---

## 01 [GitHub] 给项目建立一个共同现场

最先要解决的问题很朴素：项目到底放在哪儿？

做小游戏做到第三周，事故往往这样发生：距离演示还有一小时，你发现试玩版有个致命 bug——新加的宝箱打开是空的。你让 AI 修，它要你把相关文件发给它。问题来了：宝箱逻辑在 `game.js` 还是 `game_新.js`？图片用的是 `素材包` 里的还是 `素材包(2)` 里的？你凭印象挑了几份发过去，AI 修得很认真——修的是上周的旧版本。

好，不修了，演示要紧，退回上周能跑的那版总行吧？不行。那版从来没被单独保存过，它只在某个下午真实存在过两小时，然后就被一次次的"另存为覆盖"抹掉了。

Git 和 GitHub 就是来解决这个的。不用学完全部，先搞清楚五件事。

**第一件：分清楚谁在干什么。** 本地文件夹是你实际干活的地方；Git 是版本管理工具，被它管起来的项目加上全部历史，就是一个 Git 仓库；GitHub 是托管和协作平台，保存远程仓库，还提供任务、权限和审阅功能。

**第二件：改动落地要走完三步。** 保存文件、提交版本（commit）、同步到 GitHub（push），是三个独立动作——存了不等于提交了，提交了不等于远端有了。推之前想清楚什么不该上去：大型素材另找地方存，密钥、登录凭证、依赖目录别整包丢上去，钥匙和行李不能塞进同一个行李箱托运。

**第三件：新想法，拉到分支上折腾。** 让主分支始终保持"能交差"的状态；新功能在另一条分支上试，检查通过再合并回来，方向不行就整条放弃。每次提交附说明——三个月后你会感谢自己。

**第四件：几件事同时做，得各有工位。** 分支不会自动变成另一个文件夹。两个任务要同时改代码，用 Git worktree 或独立克隆，给它们各自一个工作目录。切换或放弃分支前，先处理好没提交的修改——它们不会因为"我建了分支"就自动受到保护，就像没存盘的游戏进度，换地图就真没了。

**第五件：协作的规矩，写在网上，不写在网上。** 个人账户适合个人项目；组织（Organization）可以管理多个仓库、成员和权限。谁能看、谁能提交、谁能审阅，在设置里定清楚，别在聊天里约定一句"应该可以吧"。流程也有分工：**Issue** 说清楚要解决什么问题，**Pull Request** 把改动摆出来比较，**Review** 拍板接不接受。"提出问题""修改文件""接受结果"不再挤在同一个聊天窗口里打架。

项目有地方放了，版本能回来了。但新问题来了：**仓库里只有代码，AI 不知道这个项目的规矩，也不知道上次干到了哪儿。**

## 02 项目的记忆：README、AGENTS.md 和状态记录

仓库建好了，你以为项目终于"有地方放了"。直到某天，新会话的 AI 兴致勃勃地把你们两周前否决掉的方案又做了一遍——做得很认真，方向全错。代码它看得到，可"为什么不这么做"，仓库里没有。

一个长期项目，除了代码还要存四种内容：**目标和范围**（做到哪、不做什么）、**长期规则**（技术选型、谁说了算）、**决定和理由**（为什么选这版方案）、**状态和证据**（做了什么、测试过没过、还没完成什么）。它们分别住在三种文件里：

**README 回答"这是什么、怎么跑起来"。** 人和 AI 都先读它。除了用途和范围，一定要留运行条件，以一个 Node.js 网页游戏为例：

- 运行环境：使用项目指定的 Node.js 版本
- 安装依赖：`npm ci`（需有匹配的锁文件）
- 启动：`npm run dev`；测试：`npm test`（需已定义对应脚本）
- 需要的配置：列出环境变量名称与取得方式

仓库保存了代码，不代表换台电脑就能跑。密钥通过环境变量提供，仓库里只留不含秘密的示例。换环境后别信文档，实际启动跑一遍——能跑起来的说明书才算数。

**AGENTS.md 回答"AI 在这个项目里怎样工作"。** Codex 会主动查找和读取它，适合写长期有效的约定：开始前读哪些材料、修改范围是什么、何时必须请人决定、结束后更新哪个文件。比如"发布、增加费用或合并主分支前，请我决定"。

**docs/status.md 回答"现在到哪了"。** 当前目标、计划、决定及理由、已完成、检查证据、未完成。它变化频繁，所以和长期规则分开放。

两条提醒。其一，**写下来 ≠ 会被读到**：`PLANS.md`、`build-log.md` 这类名字只是约定，不是咒语，要在任务开始时告诉 AI 去哪读。其二，**文字约定 ≠ 实际权限**：写上"不要发布"只是提要求，账号没有发布权限才是真的限制——"闲人免进"的牌子挡不住人，上锁的门才可以。

规矩和进度都有了。可很快你会发现，有些话你每周都在重说："先读 README，跑测试，检查开始、计分、重开，再报告结果……"

## 03 Skill：把重复念叨的工作流程打包

一套反复出现的做法，就值得做成 Skill。打开一个 Skill，通常是这样的目录：

```
game-check/
├── SKILL.md       用途、步骤和检查要求
├── scripts/       可选的检查脚本
├── references/    可选的参考资料
└── assets/        可选的模板和资源
```

SKILL.md 是核心，开头写名称和用途，后面写工作要求，例如：先读取项目运行说明，确认本轮改动；运行已有测试并记录实际结果；按清单验证开始、计分和重开；无法试玩时说明缺口，不把"测试通过"写成"试玩通过"。

它就是一份 AI 能读的工作说明，把你念叨了二十遍的话写下来，一次写好，以后自动遵守。已经有成熟的官方技能或模板就直接用，不必自己先重复几轮。

流程打包好了。但 Skill 里写"检查 GitHub 上的 Issue"，AI 拿什么去看？它还需要手。

## 04 MCP：AI 有脑子，还得有手

项目做久了，光聊天不够：要读数据库、查资料、开浏览器、生成图片、调部署服务。AI 知道下一步该做什么，但没工具，就是大厨进了没厨房的房间。

**MCP 就是给 AI 装手的方式。** 为什么需要一套协议？因为 AI 应用有很多，外部服务更多——没有统一规矩，每接一个工具就得单独写一套对接代码。有了 MCP（Model Context Protocol，模型上下文协议），服务方按协议包装一次，所有遵守协议的应用都能直接用，就像插座有了国标：电器厂和楼盘不用两两谈判，插上就来电。

MCP 在电脑里长什么样？最容易看见的是一段连接配置：

```toml
[mcp_servers.openaiDeveloperDocs]
url = "https://developers.openai.com/mcp"
```

它放在用户级的 `~/.codex/config.toml`，或按官方支持的方式放进受信任项目的 `.codex/config.toml`。它只是门牌号，告诉 Codex 去哪敲门；门后的服务器才真正提供工具。另一类服务器跑在本机，配置里写启动命令，没有网页界面。插件附带的配置还可能藏在插件自己的文件里——别只翻用户级配置就断定"我就这些工具"。

**怎么用？先连接，再提任务。** 桌面应用在设置的 MCP servers 中添加服务，填命令或地址，保存后重启连接。用 CLI 的话：

```bash
codex mcp add openaiDeveloperDocs --url https://developers.openai.com/mcp
codex mcp list
```

装好后用 `/mcp` 查看连接状态，然后正常说话：

> 找到标题含"宝箱"的 Issue，按项目规则修掉，提交到新分支，提一个 Pull Request，连接不可用就告诉我。

没有 MCP 时，你是人形数据线：搜 Issue、复制、粘贴、拿回代码、手动提交、再回网页建 PR。有了 MCP，AI 自己查、自己改、自己提，你只做 Review。

两条纪律。**配置存在 ≠ 连接可用**：实际调用成功才算数；想确认走的是哪个连接，就在请求里点名，再看工具调用记录——AI 读本地文件、跑 Git 命令，用的可能只是文件和终端工具，不代表它调了 GitHub MCP。**登录成功 ≠ 每次写入都获得批准**：连账号、读客户资料、发邮件、改线上数据，不能因为"AI 能调用"就默认放行。装的手越多，越要看住这些手。

手装好了。但一项任务不是单个动作：先查什么，再改什么？检查失败怎么办？什么时候继续，什么时候必须停下来问人？

## 05 Harness：让一连串动作按同一条路线跑

接上工具以后，AI 能读资料、改文件、跑检查。但把"读 Issue → 查记录 → 判断问题类型 → 建分支 → 小改 → 测试 → 试玩 → 提 PR"这一串动作组织起来、守住边界、中途断了还能接着跑的，是运行框架，通常叫 Harness。

自己写一套简化框架，代码大概分这几块（名字只是示意）：

```
feedback-runner/
├── main.py       执行循环
├── tools.py      Issue、文件和测试工具接口
├── policy.py     权限检查、审批与次数限制
├── state.json    当前任务与进度
└── logs/         工具结果和错误记录
```

真正关键的是执行循环：把材料、规则和工具交给模型 → 模型请求工具时先查权限、必要时候人批准 → 执行并把结果交回 → 保存状态 → 需要人决定时暂停 → 完成后检查证据再交付。Skill 可以写"测试失败就继续修"，但要有程序把真实报错交回模型；Skill 可以写"合并前请人批准"，但真正拦住未批准合并的是权限控制。**很多 Skill 放在一起仍然是一组工作方法，Harness 负责组织它们怎么跑。**

它的价值不是让 AI 永远自动干活，而是让它每次都按同一条**可检查**的路径工作：哪步出错了，下一次知道从哪查。

那什么时候需要自己搭一套？项目大、代码多都不是理由。真正要看的是：现成的运行系统＋规则文件＋Skill＋脚本，能不能可靠地组织这项工作。个人项目先用现成能力；只有要嵌进产品、无人值守跑任务、必须精确管理执行和恢复时，才值得定制——而且从缺的那一小块开始，用模拟数据验证，主动制造工具报错、执行中断、缺审批的情况，看它停不停、能不能恢复、会不会重复执行。

如果某些判断反复出现、又有办法评估对错（比如"这条反馈更像程序错误还是难度问题"），也可以把判断单独接进程序，交给决策模型——这个方向的一个例子见文末链接。

零件齐了。它们在一轮真实工作里长什么样？

## 06 真正做一轮，会怎样用到它们？

还是那条用户反馈："第二关太难，很多人玩到这就放弃了。"

一轮开始，AI 先读 AGENTS.md、README 和 docs/status.md，确认在正确的版本上工作；要和其他任务并行，就准备独立工作副本。接着调查原因：查试玩记录和测试结果，判断这是程序错误、难度设置还是规则没说清——资料不够就先要补充记录，而不是直接改代码。确定属于本轮范围后，建分支、做小改动；测试通过后还要试玩，因为**游戏能运行，不等于第二关真的更好玩**。然后把改动、证据和未解决事项一起提交 PR，你 Review 后拍板合并，AI 把决定和进度写回 status.md，确认推送结果。

回头数一数这一轮用到了什么：仓库给了版本和工作副本，规则文件给了边界，Skill 给了检查流程，MCP 给了查 Issue 的手，Harness 或现成运行系统保证了顺序和审批。而你自己只做三件事：补充机器拿不到的试玩感受，在有风险的地方做决定，以及最后判断——**工具返回成功只说明动作完成，成果有没有用，要按最初的目标来验收。**

长期项目不必一次装齐所有组件。先让文件、版本、运行方法和当前状态清楚可查，再按实际需要，一次添一件。
