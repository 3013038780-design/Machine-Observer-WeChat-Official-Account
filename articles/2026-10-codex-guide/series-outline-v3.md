# 《和 Codex 一起工作：从零到交付》六篇系列重排方案

状态：待用户审核；这是对 v2 的结构重排，不是完整纯文字稿。

## 重排原则

六篇不再按“功能类别”分组，而按一个小白完成长期项目的真实顺序推进。每个概念只在它第一次成为当前问题时完整解释，后续只引用，不重新定义。

贯穿案例是一款从零开始制作、最终可以在手机上运行的简单游戏。案例不是第六篇才出现，而是从第一篇的“一个模糊想法”开始，在每篇推进一个阶段：定义目标、建立项目、实现、验证、发布、维护。

### 概念只出现一次的归属

- **Codex、工作区、任务、项目、Local/Cloud/Remote、Plan/Goal**：第一篇完整解释。
- **提示词、澄清、拆任务、验收、反馈和交接**：第二篇完整解释。
- **Git、GitHub、项目规则、AGENTS.md、PLANS.md、Skills、MCP、插件和开发环境**：第三篇完整解释。
- **代码实现、图片/HTML/视频、浏览器/Computer Use、多代理、审阅和测试循环**：第四篇完整解释。
- **构建、部署、云服务、网站、App、域名、URL、数据、监控和安全**：第五篇完整解释。
- **维护、自动化、评估、成本、团队治理和复盘**：第六篇完整解释；完整案例在这里收束，但不重新讲前五篇的定义。

# 第一篇：先认识你正在使用的系统

候选标题：《Codex 到底是什么：小白开始长期工作的第一张地图》

### 这篇解决的问题

第一次使用 Codex 时，用户不知道“我是在聊天、建项目、开任务、操作文件，还是让远程机器运行代码”。如果环境和责任边界没弄清，后面的提示词再好也会失效。

### 章节顺序

1. Codex 适合什么工作，与 Chat、Work、代码编辑器和普通问答有什么区别。
2. 工作区、项目、任务/对话、仓库、文件夹和 worktree 的关系。
3. 桌面 App、CLI/终端、IDE 集成、Local、Cloud、Remote 的差异。
4. Plan、普通提示和 Goal 的分工；何时使用 side chat、Queue、Steer 和上下文压缩。
5. 文件、终端、浏览器、语音、图片、屏幕上下文、Computer Use 和 Record & Replay 是不同输入/操作方式。
6. 模型、工具、Skill、插件、MCP、Harness 和外部生成服务分别处在哪一层。
7. 权限、网络、凭证、审批、沙箱、预览、端口和生成产物。
8. 任务开始前检查表：目标、环境、资料、权限、完成证据和停止条件。

### 案例推进

把“我想做一个能在手机上玩的游戏”记录成一个待澄清目标，暂不写代码。

# 第二篇：先让 AI 帮你把问题想清楚

候选标题：《怎样写第一条提示词：从模糊想法到可执行计划》

### 这篇解决的问题

很多小白不是不会写提示词，而是还不知道自己应该提出什么问题。第一步应当让 AI 帮忙发现未知、比较路径和设计工作流。

### 章节顺序

1. 区分问知识、要建议、要计划、要执行、要审阅和要交接。
2. 工作流发现提示：让 AI 提问、列假设、比较方案、指出风险和给出最小验证成果。
3. 六段式任务协议：背景、目标、范围、资料/工具、交付格式、验收与停止条件。
4. 先复述再执行：检查理解、未知、假设和需要人决定的事项。
5. 任务拆解：里程碑、阶段任务、依赖、输入、输出和完成证据。
6. 反馈和纠偏：怎样描述偏差、错误复现、Queue/Steer、审阅意见和允许的修改范围。
7. 不同媒介的提示词：文字、图片、HTML、视频、语音、录制和网页操作；只讲提示词差异，不在本篇讲具体工具安装。
8. 项目级上下文的预告：为什么长期工作不能只靠一条 prompt，下一篇会把稳定规则放进项目文件和仓库。

### 案例推进

让 Codex 先提出游戏平台、玩法、技术路线、学习成本、风险和最小可玩版本，再由人选择路线并形成第一版计划。

# 第三篇：把工作装进项目，而不是留在聊天里

候选标题：《从提示词到项目：GitHub、规则文件和可复用能力怎么配合》

### 这篇解决的问题

计划确定后，长期工作需要一个稳定的家：代码放在哪里、规则如何保存、改动如何回退、重复流程如何复用、外部数据如何接入。

### 章节顺序

1. 项目目录、仓库和 GitHub：代码、文档、素材、配置和版本如何归档。
2. 分支、commit、issue、Pull Request、Review、worktree 和回滚：把一次改动变成可审阅的变更。
3. `README`、`AGENTS.md`、`PLANS.md`、决策记录和变更日志：规则、长期计划、当前任务和历史事实各放哪里。
4. 开发环境：依赖、版本、环境变量、测试命令、端口、预览、沙箱和本地/云端一致性。
5. 从一次提示词到 Skill：哪些流程值得保存，怎样写短描述、按需加载、带 references/scripts/assets 并做版本管理。
6. MCP、插件和连接应用：工具提供什么动作和数据，Skill 如何规定调用时机、顺序和失败处理。
7. Harness 和 Agent Runtime 的位置：何时需要固定环境、会话状态、工具循环、审批、恢复和多代理；普通项目什么时候不需要。
8. 安全审查：第三方 Skill、MCP、插件或社区 Harness 的来源、代码、权限、数据流、版本和回滚。

### 案例推进

建立游戏仓库、分支策略、项目规则文件、第一版 PLANS、素材目录和运行说明；把“启动项目”变成可以被 Codex 重复执行和审阅的任务。

# 第四篇：在项目里持续协作、实现和验证

候选标题：《让 Codex 持续把项目往前推：实现、工具和测试循环》

### 这篇解决的问题

项目已经建立后，怎样让 Codex 一轮一轮完成代码、视觉、网页和视频工作，同时保持上下文、审阅改动并用证据验证结果。

### 章节顺序

1. 一轮工作循环：读取状态 → 选择一个阶段目标 → 修改 → 运行 → 测试 → 报告 → 审阅 → 下一轮。
2. 代码实现：从骨架到垂直切片，不把整套产品一次生成。
3. 图片和界面：图像生成、素材来源、尺寸、风格、替换方式和版权记录。
4. HTML/前端：浏览器预览、组件、响应式、交互和与后端/API 的边界。
5. 视频和录制：屏幕演示、Record & Replay、游戏宣传视频和生成式视频分别解决什么问题。
6. 浏览器、Computer Use、终端和外部工具：如何授权、观察、执行和报告副作用。
7. 多代理、子任务和 handoff：研究、实现、测试可以怎样分工，如何合并结果和责任。
8. Review、测试、trace、grader、回归和失败恢复：区分“生成了代码”“运行成功”和“产品满足目标”。
9. 何时回到 Plan，何时继续 Goal，何时暂停并要求人做决定。

### 案例推进

完成游戏的输入、状态、碰撞、计分、胜负、重开和基础界面；每一轮都保留运行证据、diff、测试结果和下一步。

# 第五篇：把成果交付给真实用户

候选标题：《从代码到产品：网站、App、云服务和网址怎样接起来》

### 这篇解决的问题

代码能运行只是中间状态。用户还需要一个可访问的网页、App、API 或服务，背后还要有构建、运行、数据、网络、安全和监控。

### 章节顺序

1. 先定义交付物：网站、网页、移动 App、API、管理后台、内部工具或自动化服务。
2. 构建和发布：依赖、构建、制品、CI/CD、预发布、生产、签名、版本、灰度和回滚。
3. 运行环境：本地机、虚拟机、容器、云服务器、云函数、托管平台和边缘运行。
4. 数据和状态：数据库、对象存储、缓存、队列、搜索、备份、迁移和恢复。
5. 网络和访问：域名、DNS、URL、页面路由、API 地址、HTTPS、证书、反向代理、CDN、WAF、跨域和认证。
6. 云服务提供者：腾讯云、阿里云以及其他服务商如何提供计算、存储、数据库、网络和监控；按需求、地域、权限、SLA、迁移成本和计费选择。
7. 用户功能：登录、支付、邮件、短信、推送、上传、分析、客服和第三方 API；说明“能部署”不等于“用户能完成任务”。
8. 可观测和安全：日志、指标、trace、告警、健康检查、密钥、个人信息、权限、许可证和隐私。
9. Codex 在每一层的职责：写配置、查日志、检查构建、准备迁移和回滚方案；哪些动作必须由人批准。
10. 上线后的责任：发布、观测、反馈、修复、回滚、备份、扩容、停用和归档。

### 案例推进

把游戏打包成测试版本，部署一个可访问的网页或测试服务，说明 App、网站、API、云资源和真实 URL 的关系；不把部署过程写成“点击一个按钮就上线”。

# 第六篇：把一次项目变成长期系统

候选标题：《项目上线以后：维护、自动化和下一次协作》

### 这篇解决的问题

项目上线不是结束。怎样处理反馈、错误、版本、成本、自动化、团队权限和工作流复用，才算真正完成一次长期协作？

### 章节顺序

1. 线上反馈进入任务系统：区分 bug、改进、新需求、事故和研究问题。
2. 维护循环：复现、定位、修复、测试、Review、发布、观察和回滚。
3. 自动化边界：Scheduled Tasks、Record & Replay、Skills、MCP、Plugins、Harness 何时适用；先稳定流程再自动化。
4. 评估和改进：trace、grader、数据集、回归、失败率、成本、延迟和人工满意度。
5. 记忆和状态：哪些内容可以长期保留，哪些必须每次重新确认；如何压缩上下文和交接任务。
6. 团队治理：权限、审批、日志、版本、技能目录、第三方连接、责任人和发布规则。
7. 成本和资源：模型、云计算、存储、带宽、第三方 API、人工审核和失败重试。
8. 端到端回顾：从“我想做一个游戏”到 App/网页/服务的完整路径，只回顾决策和交接，不重复解释前五篇术语。
9. 复盘和迁移：把有效提示词、项目规则、Skill、检查表、部署脚本和失败记录沉淀为下一次工作流。

### 案例收束

游戏完成一次发布后，收集错误和反馈，修复一个问题，发布一个小版本，记录成本与风险，并把可复用的检查和构建流程沉淀下来。
