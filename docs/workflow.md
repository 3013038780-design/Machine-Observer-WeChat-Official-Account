# 工作流与写作约定

记录日期：2026-09-12。依据当前用户指令，以及桌面“公众号/公众号写作美化”内既有流程整理。

## 当前明确要求

- 品牌：旁观机器 / Machine Observer。
- 新定位待讨论，保留历史资料但不沿用为硬约束。
- 采用客观叙述；不写作者个人背景、个人学习动机或朋友从业经历。
- 一篇围绕一条主线，先保证阅读节奏；型号、术语和价格明细可进入附表。
- 先提供 HTML 供预览和修改，最终由用户复制渲染后的正文到 135。
- 每篇文章的框架、资料、拟稿到最终稿及配套资产都进入 GitHub。

## 执行顺序

1. 选题：记录读者问题、文章主线、范围和标题候选；已确认内容不反复询问。
2. 研究：优先官方产品页、技术文档、价格页和财报，保存链接、发布时间、查询日期、事实支持范围与待核查项。
3. 拟稿：生成可审阅 HTML，同时保留 Markdown；状态标记为拟稿，用户审阅后修订。
4. 排版：使用 assets/theme.json 与 docs/style-guide.md；正文样式内联。桌面旧组件仅作视觉结构参考，统一字号、行高与字距后使用。
5. 检查：浏览器检查手机宽度与桌面预览，检查留白、标题断行、图表宽度和图片路径。未在 135 中实测时不得声称已验证粘贴效果。
6. 定稿：按用户反馈修改并记录版本；明确认可后标为最终稿。保留对应 HTML 和源稿。
7. 交付：浏览器打开 HTML，选中渲染后的文章内容并复制，粘贴到 135；不把 HTML 源码直接粘进正文编辑区。图片需要在 135 中确认显示，必要时上传。
8. 归档：在每次形成可审阅成果或完成一轮修改时提交并同步到 GitHub，核实远端提交；每次交付明确当前状态。

## 文件组织

每个专题使用 articles/<日期-专题>/，可包含：

- brief.md：需求、范围、大纲、标题候选及确认状态。
- research/：信源记录、事实核查、价格记录与合法保存的资料。
- upper/ 与 lower/：上下篇源稿、HTML 和版本说明；单篇无需分上下目录。
- assets/：本专题配图、图表及素材来源说明。
- CHANGELOG.md：稿件状态、主要修改、数据核实日期、发布状态。

研究资料以可追溯链接、必要摘录和整理笔记归档；不自动镜像第三方全文或受限资料。

## 与历史流程的区别

旧 SKILL.md 包含公众号 API 凭证配置、确认后才渲染、上传草稿箱等路径。本次用户明确要求 HTML 优先并自行复制到 135，因此本仓库不执行那些无关步骤，也不需要读取旧凭证。

桌面旧文件保留。此次不是历史资料全量迁移，也不意味着旧稿已经正式发表。

## 2026-09-12 补充质量标准

用户明确要求更严格：使用最新可获得材料，所有数字核查，兼顾可读性、信息密度、读者实用价值和排版美观。逐项数字核查记录须与稿件一起归档；出处冲突须处理后才能进入正文。历史价格、当前挂牌价和实际成交价分别标注。
